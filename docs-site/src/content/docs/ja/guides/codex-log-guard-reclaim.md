---
title: Codex Log Guard の容量回収
description: 回数を制限したインクリメンタル VACUUM により、Codex の診断ログ用 SQLite ストレージから空きページを手動で回収します。
---

容量回収は Codex Log Guard の手動による領域回収段階です。Log Guard の保護で使うものと同じ安全性チェックにデータベースと実行環境が合格した場合に限り、Codex の正規の `logs_2.sqlite` データベースを縮小します。

容量回収は**自動スケジュールされません**。Storage ページを開いただけでも実行されません。ダッシュボードは、変更リクエストを送る前に明示的な Compact 操作と二度目の確認を要求します。

## 容量回収の処理

OpenCodex は範囲を限定したオフライン保守を次の順序で実行します。

1. Codex の有効な `sqlite_home` から正規の `logs_2.sqlite` を特定する。
2. ファイルの同一性と既知の Codex ログスキーマを確認する。
3. プロセス列挙に成功したことと、対応する Codex 書き込みプロセスが動作していないことを確認する。
4. プロセス間で共有する専用の Log Guard ロックを取得する。
5. ロック保持中に Codex プロセスを再確認する。
6. 作成を伴わない読み書きモードで既存データベースを開き、SQLite の書き込みロックを直ちに取得できることを確認する。
7. `PRAGMA auto_vacuum` が既に `INCREMENTAL` であることを要求する。
8. 保守前に `PRAGMA quick_check` を実行する。
9. WAL の完全なチェックポイントを実行し、ビジー状態または未完了なら拒否する。
10. 回数を制限した `PRAGMA incremental_vacuum(N)` のバッチを実行し、各バッチ後にチェックポイントを行う。
11. 保守後に再び `PRAGMA quick_check` を実行する。
12. データベース、WAL、ページ数、フリーリスト、回収可能バイト数の前後の指標を報告する。

既定のバッチ目標は SQLite ページで約 **8 MiB** です。1 回の実行で回収するページは最大約 **256 MiB** で、反復回数にも上限があります。空きページが残れば結果は部分完了として報告され、後から Compact を再実行できます。

バイト数の上限は、データベースの実際の SQLite ページサイズでページ数に換算します。これは処理する論理 SQLite ページの上限であり、SSD/NAND への書き込み量を示すものではありません。

## 安全性の保証

容量回収は、意図的に次の操作を**行いません**。

- 完全な `VACUUM` の実行。
- 既存の Codex データベースの `auto_vacuum` モードの変更。
- Codex の `-wal` / `-shm` ファイルを直接削除、切り詰め、改名、その他の方法で操作すること。
- 診断ログ行の削除。
- Log Guard の保護トリガーや無関係なユーザートリガーの変更。
- Codex の実行が検出されている間の実行。
- プロセス列挙が不確かな場合の続行。
- 将来の未知のログスキーマでの続行。
- SQLite の整合性チェックが失敗した後の続行。

Log Guard ロック、SQLite 書き込みロック、初回チェックポイントのいずれかがビジーなら、バックグラウンドで再試行せず明示的に拒否します。インクリメンタル VACUUM のバッチが既にコミットされた後でのみチェックポイントが競合した場合、OpenCodex は変更がなかったとせず、完了済みの作業を `stopReason: "busy"` を伴う成功の部分結果として報告します。

## CLI

まず回収可能な領域を確認します。

```bash
ocx storage codex-logs status
```

範囲を限定した保守を 1 回実行します。

```bash
ocx storage codex-logs compact
```

機械可読な前後の指標を取得します。

```bash
ocx storage codex-logs compact --json
```

結果に回収可能な領域が残っていると表示されても、さらにもう 1 回実行する明確な意図がなければそこで止めてください。OpenCodex は無制限にループせず、後続の実行も自動予約しません。

## 管理 API

圧縮は変更用エンドポイントとしてのみ公開されます。

```text
POST /api/storage/codex-logs/compact
```

圧縮用の GET エイリアスはありません。成功時の応答には、前後の測定値、回収したページ数、メインデータベースファイルの物理サイズの変化、反復回数、完了状態、停止理由、整合性状態を含む `report` オブジェクトが入ります。

代表的な拒否状態は次のとおりです。

- `codex_running`: Codex が実行中
- `process_enumeration_failed`: プロセス列挙に失敗
- `busy`: ロックまたはデータベースがビジー
- `unsupported_schema`: スキーマが未対応
- `auto_vacuum_not_incremental`: インクリメンタルモードではない
- `unsafe_path`: パスが安全でない
- `integrity_check_failed`: 整合性チェックに失敗
- `database_error`: データベースエラー

整合性チェックの失敗には、保守の前後のどちらで起きたかが含まれます。`busy` による拒否は、どの VACUUM バッチもコミットされる前に競合が検出されたことを意味します。成功の報告に含まれる `stopReason: "busy"` は、後続のチェックポイントの競合で処理が止まる前に少なくとも 1 バッチがコミットされたことを意味します。

## 結果の読み方

`pagesReclaimed` と `logicalBytesReclaimed` は、その実行中に SQLite のフリーリストから取り除かれたページを表します。`physicalDatabaseBytesReclaimed` は、保守のチェックポイント後に観測されたメインデータベースファイルの縮小量です。

これらの数値は一致しないことがあります。SQLite、WAL、ファイルシステムの挙動により、論理ページの回収が同量の即時的な物理ファイル縮小を保証するわけではありません。また、どの指標も NAND 書き込み量、SSD の摩耗、消費または節約した TBW と解釈しないでください。

`complete: true` は観測されたフリーリストがゼロになったことを意味します。部分結果では、実行ごとのページ予算または反復回数の上限に達した場合は `stopReason: "page_budget"`、SQLite がフリーリストを減らせなくなった場合は `stopReason: "no_progress"`、回収がコミットされた後にチェックポイントが競合した場合は `stopReason: "busy"` となります。いずれも範囲を限定した終了状態で、自動再試行は起こりません。
