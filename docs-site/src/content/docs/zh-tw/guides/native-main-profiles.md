## 原生登入不等於 Pool 選擇

在 **Codex Set → Multi-auth** 中，開啟主帳號卡片正下方獨立的 **Native main login** 面板，並選擇 **Manage main login**。Providers 帳號工作區的主卡片旁也有相同面板。它管理實際的 Codex 登入，而非下一個 Pool 請求要選用的帳號。它不會新增 Integrations 分頁，也不會取代現有的 Pool 控制項。

畫面上的 **Effective CODEX_HOME** 屬於 OpenCodex 伺服器。使用遠端儀表板時，它可能位於與瀏覽器不同的電腦。**Registered active profile** 是加密設定檔儲存區記錄的擁有者；伺服器會在切換前驗證實際登入。因此，在 OpenCodex 外變更登入可能引發擁有權不符錯誤，而不會被悄悄覆寫。

## 儲存與切換

使用 **Save current as profile** 登記目前的 App 登入。若登入已登記為作用中的設定檔，此操作只會更新其標籤，不會加入新帳號。切換設定檔需要受支援的檔案憑證儲存區，以及可用的作業系統金鑰儲存區。診斷代碼會說明控制項不可用的原因；不要藉由把 Pool 憑證複製到原生登入檔案，來繞過金鑰儲存區或擁有權錯誤。主卡片現有的原生裝置重新驗證操作進行時，面板會停用。

在已儲存的非作用中設定檔旁選擇 **Switch**。檢查目標標籤與伺服器端 home，停止使用該 home 的原生 Codex，接著勾選已停止的確認項並提交。確認前不會送出任何憑證變更。提交前，面板會重新讀取目前的 home、作用中擁有者與復原狀態。若狀態已變更，請檢查新狀態並再次確認。現有後端仍負責鎖定、程序檢查、排空執行中的請求、啟用與回復。

成功後，依畫面顯示的重新啟動要求操作，並以該 home 重新開啟原生 Codex。面板會重新讀取設定檔狀態並更新現有帳號控制器。它不會呼叫 Pool 選擇或設定變更，也不會編輯供應商金鑰、任務或歷史記錄。現有後端仍會比照 CLI 工作流程，協調原生 `__main__` 身分。

## 復原與先前的設定檔

以下是不同的操作：

- **Recover interrupted change** 會協調未完成的後端交易。**Restore pending transaction** 則要求回復該交易。兩者都需要另行確認已停止。即使受損的設定檔清單無法讀取，只要診斷指出有待處理的復原，這些控制項仍可使用。
- 成功切換後，**Return to previously displayed** 會使用一般且需要確認的切換流程，選取切換前顯示的設定檔。這個捷徑只保存在頁面記憶體中，受 home 與預期作用中擁有者限制；重新載入頁面，或代理／擁有者變更後就會消失。API 不會回傳交易來源，因此它不是經伺服器驗證的復原記錄：其他操作員可能在預檢讀取與切換之間變更登入。重新載入後，請直接選取所需的已儲存設定檔。

網路錯誤不能證明寫入失敗或已回復。面板會在派送變更後重新讀取伺服器狀態，即使回應遺失也一樣，而且不會自動重試。如果重新整理失敗，成功的變更不會被回報為已復原。進行下一步操作前，請重新整理並檢查診斷。現有的 `ocx account main doctor` 指令可提供伺服器端診斷。

## 本階段的範圍

此面板透過現有的 `/api/native-main-profiles` 邊界，列出、登記、切換及復原既有設定檔。它不會啟動登入程序，也不會暴露暫存寫入者 token。新增另一個原生登入仍使用現有的 `ocx account main add` CLI 工作流程；透過瀏覽器加入帳號是 issue #3417 的後續工作。目前主欄位的裝置重新驗證是另一套流程，此面板不會取代它。

設定檔資料不會寫入瀏覽器儲存空間。用戶端只投影公開欄位，顯示允許清單中的錯誤碼而非原始伺服器訊息，並使用應用程式現有的已驗證 fetch 包裝器。後端的管理驗證、GUI 工作階段／CSRF 與路由准入檢查均不變。
