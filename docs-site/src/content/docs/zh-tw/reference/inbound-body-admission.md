[供應商設定參考](/zh-tw/reference/configuration/providers/) 說明了 `maxInboundBodyBytes`，也就是單一傳入 JSON 主體的最大解碼大小。預設值仍為 256 MiB，可設定的範圍仍是 1 MiB 至 512 MiB。變更上限後請重新啟動代理，讓監聽器和讀取器一同採用預期的上限。

## 提高上限會改變並行能力

當實際生效的上限超過 256 MiB，每個涵蓋的 HTTP 請求都必須在**讀取任何主體資料之前**，預留完整的單次請求額度。程序共用的准入預算已從 512 MiB 增至 **2 GiB**；同一程序中的多個監聽器也共用此預算。這項預算與 `appOwnedMemoryBudgetMb` 分開計算。

在完成有大小限制的 JSON 解析前，即使 `Content-Length` 或壓縮後的傳輸主體很小，也不會減少預留量。准入控制不會將這些值當成解碼後或正規化 JSON 大小的可靠依據。

在大小限制內成功解析 JSON 後，讀取器會將預留量降至實測傳輸位元組數與解碼後位元組數中的較大值。若轉譯器提供用於測量正規化 JSON 的預算，還會將既有的正規化 JSON 測量值納入比較，採用最大值。預留量只會減少，且始終不超過最初的單次請求額度；即使正規化測量值更大，也不會增加預留量。既有的 UTF-8 與 JSON 重新序列化檢查會保留；輸入位元組長度不會取代可能更大的正規化 JSON 大小。

單次請求上限為 512 MiB 時，在測量並減少預留量之前，共用預算最多可接受 **4 個各自預留完整 512 MiB 的上傳請求**。解析後的並行請求數並未固定為 4 個。例如，先完成解析的請求減少預留量，讓後續請求能夠進入後，在共用預算與其他限制允許的範圍內，**8 個很小的請求也可以同時串流回傳回應**。

減少後的預留量會在非同步工作及等候供應商回應期間保留，直到回應串流 EOF、發生錯誤或取消處理完成才釋放。僅完成解析不會釋放預留量。用戶端中斷連線時，也會等到回應產生端的取消處理完成才釋放。即使錯誤、中止和取消同時發生，也只會釋放一次。

涵蓋的 POST 端點包括 `/v1/responses`、`/v1/responses/compact`、
`/v1/chat/completions`、`/v1/messages`、`/v1/messages/count_tokens`、
`/v1/images/generations`、`/v1/images/edits` 與 `/v1/alpha/search`。
圖片、搜尋與 token 計數仍沿用各自可設定的單一主體上限。內部直接轉譯與 combo 呼叫不會再次預留 HTTP 額度。管理、音訊、上下文歷史及 WebSocket 的上限不變。

省略設定、設為零，或實際生效的上限不超過 256 MiB，都不會啟用這道額外的並行閘門。現有的請求數及其他資源限制仍然適用。

## 暫時拒絕與主體過大的差別

暫時無法預留完整額度時，請求可進入**最多容納 32 個等候請求的 FIFO 佇列**，**最多等候 120 秒**。等候期間不會讀取主體。測量後減少預留量或最終釋放騰出空間時，會依等候順序接受請求。等候中的請求遭中止後，會從佇列移除，未讀取的主體會被取消，不會被消費。

佇列已滿或等候逾時時，系統會在主體解析或供應商派送前回傳 HTTP **503**、`Retry-After: 1` 與錯誤碼 `server_busy`；拒絕時會取消未讀取的主體。Messages 與 token 計數用戶端會收到類型為 `overloaded_error` 的 Anthropic 格式錯誤；OpenAI 相容用戶端則會收到 `server_error`。身分驗證與 origin 檢查會在准入及加入佇列之前執行。

重試時請遵守重試標頭與用戶端退避機制。有上限的等候與依實測值減少預留量，可以減少原本可避免的容量拒絕，但不會消除所有 503。進一步提高單次請求上限，無法解決持續的容量耗盡。

超過單次請求上限的主體仍依現有的 HTTP **413** 流程處理。已宣告的超大主體也會走這條流程，不會變成忙碌拒絕。

## 預算衡量的是什麼

**2 GiB** 是准入計量預算：解析前加總完整額度，解析後加總實測預留量。它**不是程序 RSS 或已解析物件堆積的上限**，也不保證記憶體用量低於 2 GiB。解碼、字串、物件圖、請求副本與其他應用程式狀態都會使用額外記憶體。

共用預算從 512 MiB 增至 2 GiB 後，可預留總量變為原本的 4 倍。主動將上限提高至 256 MiB 以上的部署環境，現在最多可接受 4 個預留完整 512 MiB 的上傳請求，先前則只能接受 1 個，因此潛在的尖峰記憶體用量會增加。已解析物件及副本可能讓實際記憶體用量超過准入預算。預設及更小的上限不會啟用這道閘門，既有行為不變。

請盡可能維持預設的單次請求上限。長歷史記錄工作流程確有需要時再主動提高，並考慮可能增加的記憶體尖峰用量與等候上限。
