---

[供應商設定參考](/zh-tw/reference/configuration/providers/) 說明了 `maxInboundBodyBytes`，也就是單一傳入 JSON 主體的最大解碼大小。預設值仍為 256 MiB，可設定的範圍仍是 1 MiB 至 512 MiB。變更上限後請重新啟動代理，讓監聽器和讀取器一同採用預期的上限。

保留原有的 512 MiB 共用預算預設值，並不會消除下文所述的排隊和回應生命週期內保留預留量所帶來的取捨。

## 明確選擇共用預算

`maxConcurrentInboundBodyBytes` 是 `config.json` 中選用的**頂層**設定，單位為位元組。預設值仍為 **512 MiB（`536870912`）**，保留原有的共用預算。省略、設為 `0` 或使用無效值時，都會採用此預設值。有效的正整數在使用時會被限制在 **512 MiB 至 2 GiB（`536870912` 至 `2147483648`）** 範圍內。變更後必須重新啟動代理。同一程序內的所有監聽器共用一個預算；它與 `appOwnedMemoryBudgetMb` 分開計算。

若要選擇 512 MiB 的單次請求上限，並明確啟用 2 GiB 的共用預算，請將以下欄位合併至現有 `config.json` 的頂層，然後重新啟動：

```json
{
  "maxInboundBodyBytes": 536870912,
  "maxConcurrentInboundBodyBytes": 2147483648
}
```

這是操作者主動做出的選擇，會提高潛在的尖峰記憶體用量。代理不會自動偵測可用 RAM，也不會根據 RAM 自動選擇預算。

## 提高上限會改變並行能力

當實際生效的上限超過 256 MiB，每個涵蓋的 HTTP 請求都必須在**讀取任何主體資料之前**，預留完整的單次請求額度。這些預留量共用程序層級的 `maxConcurrentInboundBodyBytes` 預算，其預設值仍為 **512 MiB**。

在完成有大小限制的 JSON 解析前，即使 `Content-Length` 或壓縮後的傳輸主體很小，也不會減少預留量。准入控制不會將這些值當成解碼後或正規化 JSON 大小的可靠依據。

在大小限制內成功解析 JSON 後，讀取器會將預留量降至實測傳輸位元組數與解碼後位元組數中的較大值。若轉譯器提供用於測量正規化 JSON 的預算，還會將既有的正規化 JSON 測量值納入比較，採用最大值。預留量只會減少，且始終不超過最初的單次請求額度；即使正規化測量值更大，也不會增加預留量。既有的 UTF-8 與 JSON 重新序列化檢查會保留；輸入位元組長度不會取代可能更大的正規化 JSON 大小。

使用**預設的 512 MiB 共用預算**和 **512 MiB 單次請求上限**時，只能有 **1 個尚未解析的上傳請求**預留完整額度。即使解析後預留量降至 **1 位元組**，剩餘容量也不足 512 MiB，下一個完整額度仍須等候足夠容量釋放。因此，預設值**無法解決**單次請求上限為 512 MiB 時原有的並行問題。

明確將 `maxConcurrentInboundBodyBytes` 設為 `2147483648` 才會選擇 **2 GiB**，可在解析及依測量值減少預留量前，接受最多 **4 個各自預留完整 512 MiB 的上傳請求**。這個 2 GiB 預算不會將解析後的並行請求數固定為 4 個。例如，先完成解析的請求減少預留量，讓後續請求能夠進入後，在共用預算與其他限制允許的範圍內，**8 個很小的請求也可以同時串流回傳回應**。

減少後的預留量會在非同步工作及等候供應商回應期間保留，直到回應串流 EOF、發生錯誤或取消處理完成才釋放。僅完成解析不會釋放預留量。用戶端中斷連線時，也會等到回應產生端的取消處理完成才釋放。即使錯誤、中止和取消同時發生，也只會釋放一次。

涵蓋的 POST 端點包括 `/v1/responses`、`/v1/responses/compact`、
`/v1/chat/completions`、`/v1/messages`、`/v1/messages/count_tokens`、
`/v1/images/generations`、`/v1/images/edits` 與 `/v1/alpha/search`。
圖片、搜尋與 token 計數仍沿用各自可設定的單一主體上限。內部直接轉譯與 combo 呼叫不會再次預留 HTTP 額度。管理、音訊、上下文歷史及 WebSocket 的上限不變。

這道額外的並行閘門只在實際生效的 `maxInboundBodyBytes` 超過 256 MiB 時啟用。省略該單次請求設定或設為 `0`，會保留其 256 MiB 預設值，因此不會啟用閘門。省略 `maxConcurrentInboundBodyBytes` 或設為 `0`，則會選擇 512 MiB 共用預設值，不會關閉已啟用的閘門。現有的請求數及其他資源限制仍然適用。

## 暫時拒絕與主體過大的差別

暫時無法預留完整額度時，請求可進入**最多容納 32 個等候請求的 FIFO 佇列**，**最多等候 120 秒**。等候期間，應用程式不會讀取請求主體。測量後減少預留量或最終釋放騰出空間時，會依等候順序接受請求。等候中的請求遭中止後，會從佇列移除，未讀取的主體會被取消，不會被消費。

佇列已滿或等候逾時時，系統會在主體解析或供應商派送前回傳 HTTP **503**、`Retry-After: 1` 與錯誤碼 `server_busy`；拒絕時會取消未讀取的主體。Messages 與 token 計數用戶端會收到類型為 `overloaded_error` 的 Anthropic 格式錯誤；OpenAI 相容用戶端則會收到 `server_error`。身分驗證與 origin 檢查會在准入及加入佇列之前執行。

重試時請遵守重試標頭與用戶端退避機制。有上限的等候與依實測值減少預留量，可以減少原本可避免的容量拒絕，但不會消除所有 503。進一步提高單次請求上限，無法解決持續的容量耗盡。

超過單次請求上限的主體仍依現有的 HTTP **413** 流程處理。已宣告的超大主體也會走這條流程，不會變成忙碌拒絕。

## 預算衡量的是什麼

設定的預算用於准入計量：解析前加總完整額度，解析後加總實測預留量。它**不會預先配置 2 GiB 或設定的容量**，也**不是程序 RSS 或已解析物件堆積的上限**。解碼、字串、物件圖、請求副本與其他應用程式狀態都會使用額外記憶體，因此實際記憶體用量可能超過預算。

選擇 2 GiB 而非 512 MiB 共用預設值，會讓可預留總量變為 4 倍。單次請求上限為 512 MiB 時，這項明確選擇允許在解析前接受最多 4 個完整上傳，而非 1 個，因此潛在的尖峰記憶體用量會增加。請根據部署環境的記憶體餘裕選擇預算。單次請求上限不超過 256 MiB 時，無論共用預算如何設定，都不會啟用這道額外閘門。

請盡可能維持預設的單次請求上限。長歷史記錄工作流程確有需要時再主動提高，並考慮可能增加的記憶體尖峰用量與等候上限。
