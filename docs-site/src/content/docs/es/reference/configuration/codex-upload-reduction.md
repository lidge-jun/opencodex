---
title: Reducción de carga de Codex
description: Cargas incrementales opcionales por WebSocket y recorte con pérdida del contexto histórico.
---

Estas opciones de nivel superior, desactivadas de forma predeterminada, se aplican a las solicitudes nativas de ChatGPT Codex. Si guardas un cambio con `ocx config set`, se aplica cuando el proxy en ejecución adopta la configuración actualizada o después de reiniciarlo. `/api/sync` lee una copia independiente para integrar los clientes. Consulta la [configuración de proveedores](/es/reference/configuration/providers/) para el resto de ajustes.

| Campo | Tipo | Predeterminado | Significado |
| --- | --- | --- | --- |
| `codexWsIncrementalUpload?` | `boolean` | `false` | Reducción experimental de carga para ChatGPT Codex nativo. Implica la reutilización de sockets entre turnos para clientes identificados por una clave API. Las solicitudes locales sin clave usan un socket por solicitud y envían una creación completa. Cada ruta de proveedor tiene su propio ámbito de reutilización. Tras una respuesta completada y confirmada, un prefijo de entrada que coincide exactamente puede sustituirse por `previous_response_id` y solo los elementos de entrada nuevos. Los clientes pueden seguir usando HTTP/SSE; `websockets` solo controla las actualizaciones de cara al cliente. Los cambios de historial, ajustes, cuenta o ruta y los sockets caducados requieren un create completo. Si el backend rechaza explícitamente como inexistente un ID de continuación sintetizado por el proxy antes de cualquier actividad de respuesta, el proxy reenvía una vez la solicitud completa conservada con las mismas comprobaciones de llamador y despacho; los ID aportados por el llamador y las entregas desconocidas nunca se reenvían mediante esta recuperación. Si el presupuesto de envíos de la solicitud, el límite de envíos del flujo de trabajo o el límite de gasto rechaza ese reenvío, el cliente recibe ese `previous_response_not_found` original; su siguiente solicitud con historial completo se envía como un create completo. Con esta opción, un proveedor cuya salida explícita es un proxy HTTP envía el tráfico WebSocket de Codex a través de ese proxy en lugar de degradarlo a HTTP/SSE; SOCKS, las anulaciones directas y los ejecutores personalizados mantienen su alternativa actual. Los sockets inactivos se conservan hasta 10 minutos y hasta 50 minutos de antigüedad total; se mantienen los límites de 32 sockets en el grupo y 32 intercambios por socket. |
| `upstreamHistorySlim?` | `"off" \| "codex"` | `"off"` | Política opcional **con pérdida** para el historial nativo de Codex. Antes del último mensaje del usuario, las imágenes en línea de más de 1 KiB se convierten en marcadores de texto y el texto de salida de herramientas de más de 32 KiB se acorta a sus primeros 2 KiB y últimos 1 KiB. Los elementos del turno actual, el historial local, las URL de imágenes remotas y las referencias a archivos se conservan intactos. No garantiza que cada imagen se cargue exactamente una vez, y el modelo no puede examinar una imagen antigua omitida en una reproducción completa. Usa `off` cuando el detalle de las imágenes históricas deba seguir disponible. Las solicitudes de creación por HTTP/SSE aplican este ajuste por sí solas. El endpoint `/responses/compact` recibe el contexto completo. Los create ordinarios por WebSocket hacia el upstream solo se recortan cuando también se establece `codexWsIncrementalUpload: true`. |
