Reclaim — этап ручного освобождения места в Codex Log Guard. Он сжимает каноническую базу Codex `logs_2.sqlite`, только если база и среда выполнения проходят те же проверки безопасности, что и при защите Log Guard.

Reclaim **никогда не запускается по расписанию** и не выполняется просто при открытии страницы Storage. Дашборд требует явного действия Compact и повторного подтверждения перед отправкой запроса на изменение.

## Что делает Reclaim

OpenCodex выполняет ограниченную последовательность обслуживания при остановленном Codex:

1. находит каноническую `logs_2.sqlite` через действующий `sqlite_home` Codex;
2. проверяет идентичность файла и известную схему логов Codex;
3. убеждается, что перечисление процессов завершилось успешно и ни один поддерживаемый процесс Codex, записывающий данные, не работает;
4. захватывает отдельную межпроцессную блокировку Log Guard;
5. повторно проверяет процессы Codex при удерживаемой блокировке;
6. открывает существующую базу для чтения и записи без возможности создания и проверяет возможность немедленно получить блокировку SQLite для записи;
7. требует, чтобы `PRAGMA auto_vacuum` уже имела значение `INCREMENTAL`;
8. выполняет `PRAGMA quick_check` до обслуживания;
9. выполняет полный checkpoint WAL и отказывает, если он занят или не завершился;
10. выполняет ограниченные пакеты `PRAGMA incremental_vacuum(N)` с checkpoint после каждого пакета;
11. повторно выполняет `PRAGMA quick_check` после обслуживания; и
12. сообщает показатели до и после: размеры базы и WAL, число страниц, свободные страницы и объём места, доступный для освобождения.

Целевой размер пакета по умолчанию — около **8 МиБ страниц SQLite**. За один вызов освобождается не более примерно **256 МиБ страниц**; дополнительно ограничено число итераций. Если свободные страницы остаются, результат помечается как частичный и Compact можно вызвать позже снова.

Пределы в байтах переводятся в число страниц по фактическому размеру страницы SQLite в этой базе. Они ограничивают обработанные логические страницы SQLite, а не объём записи на SSD/NAND.

## Гарантии безопасности

Reclaim намеренно **не** выполняет следующие действия:

- полный `VACUUM`;
- изменение режима `auto_vacuum` в существующей базе Codex;
- прямое удаление, усечение, переименование или иное изменение файлов Codex `-wal` / `-shm`;
- удаление диагностических строк;
- изменение защитных триггеров Log Guard или посторонних пользовательских триггеров;
- запуск, пока Codex обнаружен как активный;
- продолжение при неопределённом результате перечисления процессов;
- продолжение с неизвестной будущей схемой логов; или
- продолжение после неудачной проверки целостности SQLite.

Занятая блокировка Log Guard, занятый пишущий процесс SQLite или занятый начальный checkpoint приводят к явному отказу без фоновых повторных попыток. Если конкуренция за checkpoint возникла лишь после фиксации пакета инкрементального сжатия, OpenCodex сообщает уже выполненную работу как успешный частичный результат с `stopReason: "busy"`, не утверждая, что ничего не изменилось.

## CLI

Сначала проверьте, сколько места можно освободить:

```bash
ocx storage codex-logs status
```

Выполните один ограниченный проход обслуживания:

```bash
ocx storage codex-logs compact
```

Чтобы получить показатели до и после в машиночитаемом виде:

```bash
ocx storage codex-logs compact --json
```

Если результат сообщает, что место ещё можно освободить, остановитесь, если только вы явно не хотите выполнить ещё один ограниченный проход. OpenCodex не запускает бесконечный цикл и не планирует следующий проход за вас.

## API управления

Сжатие доступно только через эндпоинт изменения:

```text
POST /api/storage/codex-logs/compact
```

У сжатия нет GET-алиаса. Успешный ответ содержит объект `report` с показателями до и после, числом освобождённых страниц, изменением физического размера основного файла базы, числом итераций, признаком завершённости, причиной остановки и состоянием целостности.

Типичные причины отказа:

- `codex_running` — Codex работает.
- `process_enumeration_failed` — не удалось перечислить процессы.
- `busy` — ресурс занят.
- `unsupported_schema` — схема не поддерживается.
- `auto_vacuum_not_incremental` — не включён инкрементальный режим.
- `unsafe_path` — небезопасный путь.
- `integrity_check_failed` — проверка целостности не пройдена.
- `database_error` — ошибка базы данных.

При ошибке целостности указывается, произошла ли она до прохода обслуживания или после него. Отказ `busy` означает, что конкуренция была обнаружена до фиксации любого пакета сжатия; `stopReason: "busy"` в успешном отчёте означает, что как минимум один пакет был зафиксирован до остановки из-за конкуренции за checkpoint.

## Как понимать результат

`pagesReclaimed` и `logicalBytesReclaimed` описывают страницы из списка свободных страниц SQLite, удалённые за проход. `physicalDatabaseBytesReclaimed` показывает наблюдаемое уменьшение основного файла базы после checkpoint.

Эти значения могут различаться. Из-за поведения SQLite, WAL и файловой системы освобождение логических страниц не гарантирует такого же немедленного уменьшения физического файла. Ни один из этих показателей не следует трактовать как объём записи на NAND, износ SSD или использованный либо сэкономленный ресурс TBW.

`complete: true` означает, что наблюдаемый список свободных страниц опустел. Частичный результат использует `stopReason: "page_budget"`, когда достигнут лимит страниц за запуск или предел числа итераций, `stopReason: "no_progress"`, когда SQLite перестаёт сокращать список свободных страниц, и `stopReason: "busy"`, когда после зафиксированного освобождения места возникает конкуренция за checkpoint. Все три исхода ограничены; ни один не запускает автоматическую повторную попытку.
