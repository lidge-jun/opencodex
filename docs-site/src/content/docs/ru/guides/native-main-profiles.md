## Нативный вход и выбор Pool — разные действия

В **Codex Set → Multi-auth** откройте **Manage main login** в отдельной панели
**Native main login** сразу под карточкой основного аккаунта. Та же панель есть
рядом с основной карточкой в рабочем пространстве аккаунтов Providers. Она
управляет физическим входом Codex, а не аккаунтом для следующего запроса Pool.
Она не добавляет вкладку Integrations и не заменяет существующие элементы Pool.

Показанный **Effective CODEX_HOME** относится к серверу OpenCodex. При работе с
удалённым дашбордом это может быть другой компьютер, не тот, где открыт браузер.
**Registered active profile** — владелец, записанный в зашифрованном хранилище
профилей; перед переключением сервер проверяет физический вход. Поэтому вход,
изменённый вне OpenCodex, может вызвать ошибку несовпадения владельца вместо
незаметной перезаписи.

## Сохранение и переключение

Используйте **Save current as profile**, чтобы зарегистрировать текущий вход в
приложение. Если активный вход уже зарегистрирован, обновится его метка, а новый
аккаунт добавлен не будет. Для переключения нужны поддерживаемое файловое
хранилище учётных данных и доступное системное хранилище ключей. Диагностические
коды объясняют недоступность элементов управления. Не обходите ошибку хранилища
ключей или владельца копированием учётных данных Pool в файл нативного входа.
Панель отключена, пока на основной карточке выполняется существующая повторная
аутентификация нативного устройства.

Выберите **Switch** рядом с сохранённым неактивным профилем. Проверьте метку
назначения и серверный home, остановите нативный Codex, использующий этот home,
затем отметьте подтверждение остановки и отправьте запрос. До подтверждения
учётные данные не меняются. Непосредственно перед отправкой панель перечитывает
текущий home, активного владельца и состояние восстановления. Если состояние
изменилось, проверьте новые данные и подтвердите снова. Существующий backend
остаётся источником истины для блокировок, проверок процессов, завершения
текущих запросов, активации и отката.

После успеха выполните показанное требование перезапуска и вновь откройте
нативный Codex с этим home. Панель перечитывает состояние профилей и обновляет
существующий контроллер аккаунтов. Она не вызывает изменения выбора или
конфигурации Pool и не редактирует ключи провайдеров, задачи и историю.
Существующий backend по-прежнему согласует нативную сущность `__main__`, как и
в сценарии CLI.

## Восстановление и предыдущие профили

Это разные операции:

- **Recover interrupted change** согласует незавершённую транзакцию backend.
  **Restore pending transaction** запрашивает её откат. Для обоих действий
  нужно отдельное подтверждение остановки. Эти элементы доступны, даже если
  повреждённый список профилей не читается, но диагностика сообщает о
  незавершённом восстановлении.
- **Return to previously displayed** после успешного переключения выбирает
  профиль, показанный до переключения, через обычный подтверждаемый сценарий.
  Этот ярлык хранится только в памяти страницы, привязан к home и ожидаемому
  активному владельцу и исчезает при перезагрузке страницы или смене прокси
  либо владельца. API не возвращает источник транзакции, поэтому это не
  подтверждённый сервером журнал отмены: другой оператор мог изменить вход
  между предварительным чтением и переключением. После перезагрузки выберите
  нужный сохранённый профиль напрямую.

Ошибка сети не доказывает, что запись не состоялась или была отменена. После
отправленного изменения панель перечитывает состояние сервера, даже если ответ
потерян, и никогда не повторяет операцию автоматически. Если обновление не
удаётся, успешное изменение не объявляется отменённым. Перед следующей
операцией обновите страницу и проверьте диагностику. Команда
`ocx account main doctor` даёт серверную диагностику.

## Объём этого этапа

Панель перечисляет, регистрирует, переключает и восстанавливает существующие
профили через существующую границу `/api/native-main-profiles`. Она не запускает
процессы входа и не раскрывает токены записи для промежуточного состояния.
Добавление ещё одного нативного входа остаётся в существующем CLI-сценарии
`ocx account main add`; добавление через браузер — отдельная следующая задача
по issue #3417. Повторная аутентификация устройства для текущего основного
слота — другой сценарий, который эта панель не заменяет.

Данные профилей не записываются в хранилище браузера. Клиент отображает только
публичные поля, показывает разрешённые коды ошибок вместо необработанных
серверных сообщений и использует существующую обёртку приложения для
аутентифицированных запросов. Проверки аутентификации управления, GUI-сессии,
CSRF и допуска маршрута на backend не меняются.
