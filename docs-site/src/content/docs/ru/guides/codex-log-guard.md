OpenCodex может проверять постоянную базу диагностических логов Codex и, после вашего явного выбора, сокращать набор диагностических строк, которые Codex сохраняет. Проверка выполняется только для чтения; защита явно изменяет базу и отклоняется, если не найдена известная схема логов Codex или Codex не остановлен.

## Что показывает Inspect

OpenCodex определяет действующий `sqlite_home` Codex согласно существующему порядку приоритетов Codex и проверяет находящуюся там каноническую базу `logs_2.sqlite`. Файл с большим номером или устаревший `logs_N.sqlite` никогда не подставляется вместо цели, которую можно изменять.

На странице Storage отображаются:

- размеры основного файла базы, WAL и SHM;
- общее число строк логов и доля строк уровня `TRACE`;
- крупнейшие группы целей логирования по числу строк, обозначенные рангами вместо имён целей;
- свободное место SQLite, которое можно будет освободить позже; и
- совместимость обнаруженной схемы с известной на данный момент схемой логов Codex.

Если `sqlite_home` расположен за пределами `CODEX_HOME`, диагностическая база показывается отдельно. Её размер не включается незаметно в общий объём хранилища `CODEX_HOME`.

При подготовке этих диагностических данных OpenCodex не выбирает и не раскрывает `feedback_log_body`. Уровни логов сводятся к фиксированному набору известных уровней и `OTHER`, а имена целей не сериализуются.

## Режимы Protect

Защита **по умолчанию выключена**. При включении она устанавливает один принадлежащий OpenCodex триггер `BEFORE INSERT` в каноническую базу Codex `logs_2.sqlite`. OpenCodex никогда не заменяет неизвестный триггер с зарезервированным именем и удаляет только те триггеры, чей SQL совпадает с версией OpenCodex.

Доступны два режима:

- **Compatibility** (`compat`) — рекомендуемый режим. Он закрепляет текущий набор правил Log Guard v1 за источниками большого объёма логов, которые текущий Codex уже фильтрует или переводит на более низкий уровень в постоянном хранилище SQLite. Остальные строки `TRACE` сохраняются.
- **Quiet** (`quiet`) подавляет каждую новую строку `TRACE`, сохраняя строки `DEBUG`, `INFO`, `WARN` и `ERROR`.

Защита уменьшает число строк, попадающих в постоянное хранилище SQLite. Она **не** устраняет предшествующую работу Codex по трассировке: прежде чем триггер проигнорирует строку, события всё ещё могут форматироваться, попадать в очередь, группироваться в транзакции и проверяться собственной логикой очистки Codex. Рассматривайте Protect как защиту от лишних постоянных записей, а не как отключение формирования диагностики внутри Codex.

Log Guard фильтрует только сохранённые локальные строки логов SQLite. Он не меняет обработку диагностики Codex, [транспорт адаптеров](/ru/reference/adapters/), данные провайдеров, семантику потоковой передачи, аутентификацию, маршрутизацию, квоты или состояние аккаунтов.

### Проверки безопасности

Перед тем как Protect, Disable или Repair изменят стороннюю базу, OpenCodex:

1. определяет именно канонический путь к `logs_2.sqlite`;
2. проверяет, что путь указывает на обычный файл, а не символьную ссылку, и что известная схема совпадает в точности;
3. убеждается, что перечисление процессов завершилось успешно и ни один поддерживаемый процесс Codex, записывающий данные, не работает;
4. захватывает отдельную межпроцессную блокировку Log Guard;
5. повторяет проверку процессов Codex после захвата блокировки;
6. открывает базу для чтения и записи **без** возможности создания и получает SQLite `BEGIN IMMEDIATE` без ожидания занятой базы;
7. изменяет только принадлежащие OpenCodex триггеры Log Guard и перечитывает результат до фиксации; и
8. сохраняет запрошенный режим в конфигурации OpenCodex, пока блокировка Log Guard ещё удерживается.

Если результат перечисления процессов неопределён, база занята, схема неизвестна или зарезервированное имя триггера принадлежит другому SQL, изменение безопасно отклоняется. OpenCodex не завершает Codex автоматически.

## Расхождение состояния и Repair

Запрошенный режим защиты хранится в конфигурации OpenCodex отдельно от базы логов Codex. Это важно, поскольку миграция Codex может пересоздать таблицу `logs`, а SQLite удаляет триггеры, привязанные к заменённой таблице.

Если сохранён режим `compat` или `quiet`, но соответствующий принадлежащий OpenCodex триггер больше не обнаружен, Log Guard сообщает о состоянии **drifted**. `ocx doctor` сообщает о расхождении, но никогда не исправляет его автоматически.

Восстановление запускается явно:

```bash
ocx storage codex-logs repair
```

OpenCodex намеренно не пересоздаёт защиту при каждом запуске. В следующем выпуске автоматическое восстановление можно будет рассмотреть только после накопления достаточных практических свидетельств его безопасности при миграциях Codex.

## CLI

Проверить состояние:

```bash
ocx storage codex-logs status
ocx storage codex-logs status --json
ocx doctor
```

Включить рекомендуемую политику совместимости:

```bash
ocx storage codex-logs protect
```

Явно выбрать тихий режим:

```bash
ocx storage codex-logs protect --mode quiet
```

Отключить защиту OpenCodex или устранить расхождение:

```bash
ocx storage codex-logs unprotect
ocx storage codex-logs repair
```

Добавьте `--json` к командам Log Guard для машиночитаемого вывода. Канонический синтаксис команд и поведение JSON описаны в [справочнике CLI](/ru/reference/cli/).

Существующая команда не изменилась:

```bash
ocx storage --json
```

Её ответ содержит то же состояние логов Codex, которое используется на странице Storage.

## API управления

Состояние доступно по адресу:

```text
GET /api/storage/codex-logs
```

Явные изменения выполняются через:

```text
POST /api/storage/codex-logs/protect
POST /api/storage/codex-logs/unprotect
POST /api/storage/codex-logs/repair
```

Тело запроса Protect имеет вид `{"mode":"compat"}` или `{"mode":"quiet"}`. `GET /api/storage` также включает отчёт как `codexLogs`, чтобы дашборд мог обновить обычную разбивку хранилища и диагностику логов Codex одним запросом снимка.

## Семантика снимка только для чтения

Проверка состояния открывает базу только для чтения с SQLite `immutable=1`. Это не позволяет диагностическому чтению создавать или обновлять побочные файлы `-wal` и `-shm`.

С этим связан важный компромисс: агрегаты SQL и метаданные обнаруженных триггеров описывают последний снимок базы после checkpoint. Если Codex активно записывает данные, в живом WAL могут находиться более новые строки или страницы схемы, чем в неизменяемом снимке. Успешный ответ на изменение использует состояние триггеров, которое OpenCodex проверил внутри транзакции записи; последующий запрос состояния только для чтения может временно отставать до checkpoint этих страниц схемы в SQLite.

OpenCodex показывает размер файла WAL отдельно и **не** называет результат скоростью записи на SSD, объёмом записи на NAND или расходом ресурса накопителя/TBW.

## Состояния совместимости

При известной схеме проверка и защита считаются поддерживаемыми. Отсутствующую, нечитаемую или неизвестную будущую схему по-прежнему можно наблюдать на уровне метаданных, но операции изменения для неё не поддерживаются.

Неизвестная схема не объявляется совместимой наугад. Поэтому более новая версия Codex остаётся наблюдаемой, а Log Guard не считает безопасным изменение структуры базы, которая ещё не прошла проверку.

## Reclaim остаётся отдельным этапом

Protect не выполняет сжатие SQLite. [**Reclaim**](/ru/guides/codex-log-guard-reclaim/) уже предоставляет явный, ограниченный процесс инкрементального сжатия при остановленном Codex с checkpoint и проверками целостности.

Protect никогда не запускает `VACUUM`, не усекает и не удаляет WAL Codex напрямую и не выполняет освобождение места по расписанию.
