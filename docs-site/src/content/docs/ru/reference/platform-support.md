---
title: Поддержка платформ
description: Что OpenCodex умеет на macOS, Windows и Linux и почему некоторые возможности зависят от платформы.
---

OpenCodex работает на macOS, Windows и Linux. Большинство функций ведут себя одинаково
на всех трёх системах. Некоторые зависят от возможностей ОС; здесь указано, какие
именно и почему.

## На всех платформах

| Возможность | Примечания |
| --- | --- |
| Прокси, маршрутизация, адаптеры провайдеров | Основной runtime не зависит от платформы. |
| Фоновый сервис | Три нативных механизма: launchd на macOS, Task Scheduler **или** WinSW на Windows, пользовательский модуль systemd на Linux. |
| Вход через браузер | Открывается штатным механизмом платформы. |
| Обнаружение клиентов | Установки Cursor, Claude Desktop, Kiro и Codex ищутся с учётом платформы. |

### Ключи провайдеров в хранилище учётных данных ОС

Поддерживается на всех трёх платформах, **если доступна разблокированная служба
учётных данных ОС**: Keychain на macOS, Credential Manager на Windows, libsecret
на Linux. Заблокированное хранилище или фоновая сессия без интерфейса не дают
доступа к разблокированной службе. OpenCodex сообщает об этом вместо незаметного
переключения на другой способ хранения. Правила хранения описаны в разделе
[Провайдеры](/ru/reference/configuration/providers/).

## Только macOS

### Автоматическое подключение Claude Code

Передача `ANTHROPIC_BASE_URL` и управляющих переменных Claude Code в сессию
происходит через пользовательский домен launchd; единого аналога в других ОС нет.

На Linux три возможных механизма охватывают разные процессы:
`systemctl --user set-environment` действует только на службы, запущенные systemd,
`~/.profile` — только на оболочки входа, а `~/.bashrc` — только на интерактивные
оболочки без входа. Единого места для всей пользовательской сессии нет.

На Windows аналогом служит `HKCU\Environment`, но он действительно постоянный,
а не очищаемый при перезагрузке. В этом и проблема: bearer-токен перешёл бы из
домена, который очищается при перезагрузке, в сохраняемый раздел реестра. Это
изменило бы срок хранения учётных данных на диске и круг тех, кто может их
прочитать. Такое решение требует проверки безопасности, а не простого переноса.

Всё остальное, что нужно Claude Code, работает на всех платформах. Можно задать
эти переменные самостоятельно или запустить `ocx claude`, который передаёт их
непосредственно дочернему процессу.

## Импорт или ручной ввод

### Meta Muse Code

На macOS OpenCodex импортирует API-ключ, уже сохранённый Muse Code CLI после
`muse login`, поэтому второй раз вводить его не нужно.

На других платформах ключ предлагается вставить вручную. Meta не выпускает
нативный CLI для Windows, а на Linux CLI существует, но место хранения ключа
не проверено. Поэтому OpenCodex не пытается угадать хранилище. Тот же ключ
доступен в [консоли разработчика Meta](https://dev.meta.ai). Вставленный ключ
проходит ту же проверку формата и проверку через Model API, что и импортированный.

## Примечания для Windows

Сервис Windows может работать через Task Scheduler либо как нативный сервис WinSW;
одновременно эти варианты не используются. `ocx service repair` откажется
продолжать, если обнаружит состояние обоих: угадывание здесь привело бы к двум
прокси, борющимся за один порт.

Вывод консоли на неанглоязычной Windows приходит в системной кодовой странице,
а не UTF-8. OpenCodex декодирует его соответственно, поэтому имя аккаунта с
символами вне ASCII определяется правильно.

## Если возможность недоступна

OpenCodex сообщает фактическую причину, а не просто незаметно отключает элемент
управления. Если функция недоступна на вашей платформе, ошибка или дашборд
укажут отсутствующий механизм и поддерживаемую альтернативу. Если этого не
происходит, стоит сообщить об ошибке.
