---

[Справочник конфигурации провайдеров](/ru/reference/configuration/providers/) описывает
`maxInboundBodyBytes` — максимальный размер декодированного входящего тела JSON.
Значение по умолчанию остаётся 256 МиБ; настройка допускает значения от 1 до 512 МиБ.
После изменения лимита перезапустите прокси, чтобы слушатель и обработчики чтения
одновременно перешли на нужное значение.

Сохранение прежнего общего бюджета 512 МиБ по умолчанию не устраняет описанные ниже
ограничения очереди и удержания резерва на протяжении жизненного цикла ответа.

## Выбирайте общий бюджет явно

`maxConcurrentInboundBodyBytes` — необязательная настройка **верхнего уровня** `config.json`
в байтах. По умолчанию используется **512 МиБ (`536870912`)**, как и прежде.
При отсутствии настройки, значении `0` или некорректном значении применяется этот бюджет.
Допустимое положительное целое при использовании ограничивается диапазоном
**512 МиБ–2 ГиБ (`536870912`–`2147483648`)**. После изменения перезапустите прокси.
Все слушатели одного процесса делят один бюджет, отдельный от `appOwnedMemoryBudgetMb`.

Чтобы выбрать лимит 512 МиБ на запрос и явно включить общий бюджет 2 ГиБ, добавьте
эти поля на верхний уровень своего `config.json`, затем перезапустите прокси:

```json
{
  "maxInboundBodyBytes": 536870912,
  "maxConcurrentInboundBodyBytes": 2147483648
}
```

Это выбор оператора, который повышает потенциальный пик потребления памяти.
Прокси не определяет доступную RAM автоматически и не подбирает по ней бюджет.

## Увеличение лимита меняет параллельность

Если итоговый лимит превышает 256 МиБ, каждый охватываемый HTTP-запрос резервирует
весь лимит отдельного запроса **до чтения любых данных тела**. Резервы используют общий
для процесса бюджет `maxConcurrentInboundBodyBytes`, по умолчанию по-прежнему **512 МиБ**.

До завершения разбора JSON с контролем размера ни малый `Content-Length`, ни малый размер
сжатого тела при передаче не уменьшают резерв. Допуск не считает эти значения надёжным
подтверждением размера декодированного или нормализованного JSON.

После успешного разбора JSON в пределах ограничения обработчик чтения уменьшает резерв
до максимума из фактически полученных байтов, декодированных байтов и существующего
измерения нормализованного JSON, если преобразователь передал бюджет для этого измерения.
Существующие проверки UTF-8 и повторно сериализованного JSON сохраняются: длина входных
данных не заменяет потенциально больший размер нормализованного JSON. Резерв может
только уменьшаться и не превышает исходный лимит запроса; даже большее измерение
нормализованного JSON никогда не увеличивает резерв.

При **общем бюджете 512 МиБ по умолчанию** и **лимите 512 МиБ на запрос** весь лимит
может зарезервировать только **одна ещё не разобранная загрузка**. Даже если после разбора
её резерв уменьшится до **одного байта**, свободного места будет меньше 512 МиБ.
Следующий полный резерв ждёт освобождения достаточной ёмкости. Поэтому бюджет по умолчанию
**не решает** исходную проблему параллельности при лимите 512 МиБ на запрос.

Явное значение `maxConcurrentInboundBodyBytes: 2147483648` выбирает **2 ГиБ** и допускает
до **4 загрузок, каждая из которых резервирует полные 512 МиБ**, ещё до разбора и уменьшения
резервов по измерениям. После разбора этот бюджет 2 ГиБ не задаёт фиксированный предел
в 4 запроса: например, **8 очень маленьких запросов могут одновременно передавать потоковые
ответы**, когда уменьшение резервов позволяет допустить следующие запросы,
в пределах общего бюджета и других ограничений.

Уменьшенный резерв сохраняется во время асинхронной работы и ожидания провайдера,
до конца потока ответа (EOF), ошибки или завершения отмены. Сам разбор его не освобождает.
При отключении клиента резерв сохраняется до завершения отмены на стороне производителя
ответа. Освобождение происходит ровно один раз, даже если ошибка, прерывание и отмена
возникают одновременно.

Охватываются POST-эндпоинты `/v1/responses`, `/v1/responses/compact`,
`/v1/chat/completions`, `/v1/messages`, `/v1/messages/count_tokens`,
`/v1/images/generations`, `/v1/images/edits` и `/v1/alpha/search`.
Для изображений, поиска и подсчёта токенов сохраняются их настраиваемые лимиты тела.
Внутренний прямой перевод запросов и вызовы combo не резервируют второй HTTP-допуск.
Лимиты управления, аудио, истории контекста и WebSocket не меняются.

Этот дополнительный барьер действует только при итоговом `maxInboundBodyBytes` выше 256 МиБ.
Отсутствие этой настройки отдельного запроса или значение `0` сохраняет её стандартные
256 МиБ и не включает барьер. Отсутствие или обнуление `maxConcurrentInboundBodyBytes`
выбирает общий бюджет 512 МиБ, а не отключает уже действующий барьер.
Существующие ограничения числа запросов и других ресурсов продолжают действовать.

## Временный отказ и слишком большое тело

Если весь лимит временно нельзя зарезервировать, запрос может попасть в **очередь FIFO
не более чем из 32 ожидающих запросов**, с **ожиданием не более 120 секунд**. Во время
ожидания приложение не читает тела запросов. Уменьшение резерва после измерения или его
окончательное освобождение позволяет допускать запросы в порядке очереди. Прерванный
ожидающий запрос удаляется из очереди, а его непрочитанное тело отменяется без чтения.

Полная очередь или истечение ожидания дают HTTP **503**, `Retry-After: 1` и код ошибки
`server_busy` до разбора тела и отправки провайдеру. При отказе непрочитанные тела отменяются.
Клиенты Messages и подсчёта токенов получают ошибку в формате Anthropic с типом
`overloaded_error`; OpenAI-совместимые клиенты — `server_error`. Проверки аутентификации
и источника выполняются до допуска и постановки в очередь.

При повторе соблюдайте заголовок повтора и задержку клиента. Ограниченное ожидание и
измеренные резервы сокращают предотвратимые отказы из-за нехватки ёмкости, но не устраняют
все ответы 503. Дальнейшее увеличение лимита отдельного запроса не решает постоянное
исчерпание ёмкости.

Тело, превышающее лимит отдельного запроса, по-прежнему получает HTTP **413**.
Если превышение заявлено заранее, применяется именно этот путь, а не отказ из-за
занятости.

## Что измеряет бюджет

Настроенный бюджет считает единицы допуска: полные лимиты до разбора, затем измеренные
резервы. Он **не выделяет заранее 2 ГиБ** или настроенный объём и **не ограничивает RSS
процесса или кучу разобранных объектов**. Декодирование, строки, графы объектов, копии
запросов и другое состояние приложения занимают дополнительную память, поэтому
фактическое потребление может превышать бюджет.

Выбор 2 ГиБ вместо общего бюджета 512 МиБ по умолчанию разрешает вчетверо больший
суммарный резерв. При лимите 512 МиБ на запрос этот явный выбор допускает до четырёх
полных загрузок до разбора вместо одной, повышая потенциальный пик потребления памяти.
Выбирайте бюджет с учётом запаса памяти развёртывания. Лимит отдельного запроса
не выше 256 МиБ не включает дополнительный барьер независимо от общего бюджета.

По возможности оставляйте лимит отдельного запроса по умолчанию. Увеличивайте его осознанно,
если этого требует сценарий с большой историей, учитывая больший потенциальный пик памяти
и ограниченное ожидание.
