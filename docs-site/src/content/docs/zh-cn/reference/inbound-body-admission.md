[提供商配置参考](/zh-cn/reference/configuration/providers/)介绍了 `maxInboundBodyBytes`，即单个入站 JSON 请求体解码后的最大大小。默认值仍为 256 MiB，可配置范围仍为 1 MiB 至 512 MiB。修改上限后请重启代理，使监听器与读取器共同使用预期上限。

保留原有的 512 MiB 共享预算默认值，并不会消除下文所述的排队和响应生命周期内保留预留量所带来的取舍。

## 明确选择共享预算

`maxConcurrentInboundBodyBytes` 是 `config.json` 中可选的**顶层**设置，单位为字节。默认值仍为 **512 MiB（`536870912`）**，保留原有的共享预算。省略、设为 `0` 或使用无效值时，均采用此默认值。有效的正整数在使用时会被限制在 **512 MiB 至 2 GiB（`536870912` 至 `2147483648`）** 范围内。修改后需要重启代理。同一进程内的所有监听器共享一个预算；它与 `appOwnedMemoryBudgetMb` 分开计算。

若要选择 512 MiB 的单请求上限，并明确启用 2 GiB 的共享预算，请将以下字段合并到现有 `config.json` 的顶层，然后重启：

```json
{
  "maxInboundBodyBytes": 536870912,
  "maxConcurrentInboundBodyBytes": 2147483648
}
```

这是运营者主动做出的选择，会提高潜在的峰值内存用量。代理不会自动检测可用 RAM，也不会根据 RAM 自动选择预算。

## 提高上限会改变并发能力

当最终生效的上限大于 256 MiB 时，每个受此规则约束的 HTTP 请求都必须在**读取任何请求体数据之前**预留其完整的单请求额度。这些预留量共享进程级的 `maxConcurrentInboundBodyBytes` 预算，其默认值仍为 **512 MiB**。

在完成有大小限制的 JSON 解析前，较小的 `Content-Length` 或较小的压缩传输体都不会减少预留量。准入控制不会将它们视为解码后或规范化 JSON 大小的可靠依据。

在大小限制内成功解析 JSON 后，读取器会将预留量降至实际传输字节数与解码后字节数中的较大值。如果转换器提供了用于测量规范化 JSON 的预算，还会将现有的规范化 JSON 测量值纳入比较，取最大值。预留量只会减少，且始终不超过最初的单请求额度；即使规范化测量值更大，也不会增加预留量。现有的 UTF-8 与 JSON 重新序列化检查保持不变；输入字节长度不会替代可能更大的规范化 JSON 大小。

使用**默认的 512 MiB 共享预算**和 **512 MiB 单请求上限**时，只能有 **1 个尚未解析的上传请求**预留完整额度。即使解析后预留量降至 **1 字节**，剩余容量也不足 512 MiB，下一个完整额度仍需等待足够容量释放。因此，默认值**不能解决**单请求上限为 512 MiB 时原有的并发问题。

明确将 `maxConcurrentInboundBodyBytes` 设为 `2147483648` 才会选择 **2 GiB**，可在解析及按测量值减少预留量前，接纳最多 **4 个各自预留完整 512 MiB 的上传请求**。这个 2 GiB 预算不会将解析后的并发请求数固定为 4 个。例如，先解析的请求减少预留量、为后续准入腾出空间后，在共享预算和其他限制允许的范围内，**8 个很小的请求也可以同时流式返回响应**。

减少后的预留量在异步处理及等待提供商响应期间仍会保留，直到响应流 EOF、发生错误或取消处理完成。仅完成解析不会释放预留量。客户端断开连接时，也要等待响应生成端的取消处理完成后才释放。即使错误、中止和取消同时发生，释放也只执行一次。

受约束的 POST 端点包括 `/v1/responses`、`/v1/responses/compact`、`/v1/chat/completions`、`/v1/messages`、`/v1/messages/count_tokens`、`/v1/images/generations`、`/v1/images/edits` 和 `/v1/alpha/search`。图像、搜索和 token 计数仍遵守各自现有的可配置单请求体上限。内部直接转换和 combo 调用不会再次预留 HTTP 额度。管理、音频、上下文历史和 WebSocket 的上限不变。

这一额外的并发门槛仅在最终生效的 `maxInboundBodyBytes` 大于 256 MiB 时启用。省略该单请求设置或设为 `0` 会保留其 256 MiB 默认值，因此不会启用门槛。省略 `maxConcurrentInboundBodyBytes` 或设为 `0` 则会选择 512 MiB 共享默认值，不会关闭已启用的门槛。现有请求数量及其他资源限制仍然适用。

## 临时拒绝与请求体过大

暂时无法预留完整额度时，请求可进入**最多容纳 32 个等待请求的 FIFO 队列**，**最多等待 120 秒**。等待期间，应用不会读取请求体。测量后减少预留量或最终释放腾出空间时，按等待顺序接纳请求。等待中的请求被中止后会从队列移除，未读请求体会被取消而不会被消费。

队列已满或等待超时，会在请求体解析或提供商分发之前返回 HTTP **503**、`Retry-After: 1` 和错误代码 `server_busy`；拒绝时会取消未读请求体。Messages 与 token 计数客户端收到类型为 `overloaded_error` 的 Anthropic 格式错误；兼容 OpenAI 的客户端收到 `server_error`。认证和来源检查在准入及入队之前执行。

重试时请遵守重试标头和客户端退避机制。有界等待和按实测值减少预留量可以减少本可避免的容量拒绝，但不会消除所有 503。进一步提高单请求上限不能解决持续的容量耗尽。

请求体超过单请求上限时，仍按现有逻辑返回 HTTP **413**。声明的大小已超限时，也会走这一路径，而不会变成繁忙拒绝。

## 预算衡量的内容

配置的预算用于准入计量：解析前累计完整额度，解析后累计实测预留量。它**不会预先分配 2 GiB 或配置的容量**，也**不是进程 RSS 或已解析对象堆内存的上限**。解码、字符串、对象图、请求副本和其他应用状态还会使用额外内存，因此实际内存用量可能超过预算。

选择 2 GiB 而非 512 MiB 共享默认值，会使可预留总量变为 4 倍。单请求上限为 512 MiB 时，这一明确选择允许在解析前接纳最多 4 个完整上传，而非 1 个，因此潜在的峰值内存用量会增加。请根据部署环境的内存余量选择预算。单请求上限不超过 256 MiB 时，无论共享预算如何设置，都不会启用这一额外门槛。

请尽可能保留默认的单请求上限。在长历史记录工作流确有需要时再主动提高，并考虑可能增大的内存峰值及等待上限。
