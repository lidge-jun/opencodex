# ADR-5810 — decision recorded under "Keyless Zen client identity"

- Contract owner: [providers-and-adapters.md](../providers-and-adapters.md#keyless-zen-client-identity)

## Decision record

- Purpose and intent: Reach the keyless Zen tier (`opencode-free`) through the proxy, including the Muse Spark contributor-free ids, which are the current OpenCode-house models for agentic coding on that tier.
- Existing behavior and constraints: Zen admits keyless requests only with the client identity its own CLI sends — `x-opencode-session` in the `ses_` + 12-hex + 14-base62 shape (`packages/opencode/src/id/id.ts`), a *versioned* `opencode/<version>` User-Agent plus `x-opencode-client` (`packages/opencode/src/session/llm/request.ts`; the bare default is refused even with a valid session, verified live 2026-09-26), and `Bearer public` for the anonymous pool (`packages/console/app/src/routes/zen/util/handler.ts`, which also strips `x-opencode-*` before forwarding and pins sticky replicas to the session id). The turn must additionally declare `(shell|bash)`+`read` function tools — tool-less turns, `exec`-only (Codex 0.153.x) turns, either name alone, and capitalized `Bash`+`Read` are all refused; `web_search` alongside the pair is fine. The Muse Spark contributor-free ids are deployed on `/v1/responses` only (Zen docs endpoint table; `/v1/chat/completions` answers 500). There is no third-party integration contract for the keyless tier, and admission may change without notice.
- Alternatives considered: A bespoke `opencode-free` adapter wrapping both wires (rejected: ~30 call sites branch on the `openai-chat`/`openai-responses` adapter strings for failover, combo-native routing, eligibility, and tier policy, so a rename silently changes those paths); registry `modelWireDefaults` alone (rejected: routing without the session header still fails the gate); a single process-wide static session (rejected: one sticky replica for all threads means one broken replica breaks every conversation until restart); leaving the refusal in place (rejected: the operator explicitly asked for keyless Zen access through Codex).
- Chosen approach: `src/adapters/opencode-free-session.ts` mints a stable-per-Codex-thread session (`_codexOwnThreadId ?? _clientThreadId`, hashed; process-scoped random fallback) plus anonymous `Bearer public`, and repairs exactly the bare default User-Agent to a verified versioned one, applied from the shared Chat transport (translated adapter and native fast path alike) and the Responses passthrough, only for the canonical Zen endpoint and only when the operator has not set those values. `src/adapters/opencode-free-tools.ts` appends the missing `shell`/`read` gate declarations — worded never-to-invoke after OpenCode's own `_noop` precedent — from all three builders, keyless only; the registry routes the two Muse Spark ids to `openai-responses` on every inbound via `modelWireDefaults`.
- Why this approach: No adapter is renamed, so every wire-keyed behavior keeps its existing classification; no new factory or allow-list widening is needed; per-thread sessions preserve Zen's sticky routing across turns; operator headers and keys always win, so keyed use is untouched.
- Benefits, drawbacks, and impact: Streaming Codex turns on keyless Zen models work, with thread-stable stickiness. Non-streaming sends still face the upstream gate unchanged. The declarations satisfy admission, not execution: if the model calls one instead of the client's own tools, the client answers "unknown tool" and the turn fails visibly — there is deliberately no call translation, since a `shell` JSON call cannot be faithfully rewritten into an arbitrary client's native tool surface. Keyless quota/retention terms still apply (see the provider note). If OpenCode changes admission, these routes fail with honest upstream errors rather than silently degrading.
