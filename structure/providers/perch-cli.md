# Perch CLI

`src/adapters/perch-cli/adapter.ts` serves the `perch-cli` row by running the Perch CLI (`perchai-cli`) once per request: `perch run <prompt> --json --mode agents|ask --cwd <staging> --thread ocx-<uuid> --model <tier>`. It is a `runTurn` adapter with `codebuddy` as its contract parent, like `claude-cli`, and reuses the [Claude CLI stable replay](claude-cli-replay.md) and the capture-only bridge in `src/adapters/codebuddy/tool-bridge.ts`. `tests/providers/perch-cli-adapter.test.ts` covers these rules against recorded `perch run --json` documents and a fake CLI; it never starts Perch or reaches its API.

## Input and isolation

`perch run` has no system-prompt or stdin channel, so each turn is staged under a short `mkdtemp` root. The fixed session rules, the bridge's name map, the client's system and developer instructions and any correction go to `.perch/PERCH.md` and `.perch/rules/10-instructions-NN.md`; the stable replay, unwrapped from its stream-json frame, goes to `20-conversation-NN.md`. Perch loads at most 40 rule files of 64,000 bytes in unsorted `readdir` order (name order on NTFS, hash order on ext4), so each rule file opens with `[<series> part NN of MM]` and PERCH.md tells the model to read each series in part order. Files are cut at 60,000 bytes and input that needs more fails with 400 `context_length_exceeded` before spawn. History is capped by the window (as `claude-cli` caps it) and by the bytes the rule files hold, measured with the conversation's own bytes per character; the current input is never cut, so its bytes come out of the history. A staging failure removes the staging root. The registry publishes the 1M tiers at 512K so Codex compacts first. A run whose snapshot shows a client row other than `sent_raw` fails closed with `context_length_exceeded`.

The argv prompt is fixed apart from the client's working directory (the last `<cwd>` in user or developer context) and the tool rule; the staging path never reaches the model as the project. The child runs with `baseScopedEnv()` (no proxy variables, as for the other CLI adapters) plus `HOME`/`USERPROFILE` pointed at an empty staging home, while `PERCH_CLI_AUTH_DIR` keeps the operator's sign-in (on macOS that also selects the file sign-in over the Keychain, so the sign-in error there names the `PERCH_CLI_AUTH_DIR=~/.perch perch login` form). Staged `skills.json` disables Perch's built-in skills, and a `disabled` `courtlistener` entry in both `mcp.json` files keeps Perch from seeding and starting that server. Each turn uses a fresh `--thread`; without one Perch derives the thread from the cwd and replays its own history.

## Tool capture

With tools, `.perch/mcp.json` names the capture-only server over the request's catalog. The server declares no annotations, so Perch treats every bridge tool as a write: it reports the batch as `tool_call_requested` and ends the run with `approval_required` before calling the server. Only names in the bridge's `emittedNameMap` become client tool calls. A bare name is a Perch built-in; the run is repeated once (`repair` send class) with a correction naming the client tools, and a second violation fails with `undeclared_tool_call`. Nothing reaches the client before the CLI exits, so a rerun never follows partial output. Bridge calls in a `completed` or `incomplete` run were never captured and fail with `tool_call_not_captured`. Read-class built-ins (staging-folder reads, web search, web fetch) execute inside Perch before the adapter sees them. Perch holds MCP schemas back behind its own `loadMcpTools` once their JSON passes 10% of the context limit, so a catalog over 7% of the window keeps one-line descriptions and moves the full ones into the instructions; a catalog still over that fails with 400 `tool_catalog_too_large`. A completed run whose `tool-schemas` row carries no bridge name fails with `tool_bridge_init_missing`.

## Outcome and retry

`perchOutcome` maps the final JSON document. Failed, blocked and cancelled runs report their own failure before any tool-use check; `turn_failed.errorCode` selects the code (`context_overflow` → 400, `provider_limit` → 429, `provider_transport` and `turn_preparation_stalled` → retryable 503, `turn_aborted` → 499). After those codes, a failed run without a `tkt-` turn ticket, or that reports Perch's keyless fallback ("model is busy", "missing API key"), is a retryable 503 `perch_cli_unavailable` while the sign-in file exists and a 401 once Perch has deleted it. An `incomplete` run reporting `max_iterations`, `turn_incomplete` or an unfinished-answer reason ends with stop reason `max_tokens`, so it reads as truncated; any other reason, such as `clarification_required`, ends the turn with `end_turn`. A first `perch_cli_unavailable` attempt is repeated once with the `transient` send class (reported as recovery `transient-5xx`); without send budget the first outcome is reported and recovery is withheld. The adapter sets `reportsPhysicalSends`, admitting and reporting every run itself. Usage is Perch's `turnApiUsage` with cache reads and writes folded into input, summed across attempts and carried on whichever `done` or `error` ends the turn. An abort after spawn or between attempts ends with 499 `turn_aborted`, carrying earlier attempts' usage; a launch failure reported after spawn is 500 `cli_spawn_failed`; stdout past 64 MiB stops the run with `perch_cli_output_too_large`. Error text is redacted, bearer tokens, JWTs and token fields included. On Windows the process tree is killed with the shared runner's `killWindowsProcessTree`; elsewhere only the direct child is signalled, SIGTERM then SIGKILL.

## Unmodified CLI

The CLI runs as shipped: nothing is loaded into its process, its requests are not intercepted, and its environment carries no hooks (`NODE_OPTIONS` holds only the heap flag, and only for a volta shim). The CLI's node entry is run directly, with the `--max-old-space-size` the CLI's launcher would otherwise re-execute itself for: the package manager's shim is bypassed so newlines in argv survive Windows, and the bin script is read from the quoted path in the package manager's `.cmd` or POSIX shell shim (separators normalized, so a `.cmd` shim resolves on any host), falling back to npm's layout. A volta shim that does not resolve to `perchai-cli/bin/perch` is run as is with the heap flag in `NODE_OPTIONS` and `VOLTA_HOME` kept; asdf shims resolve versions from the staging home and are not supported. `perch run` prints one JSON document at exit, so a turn's text and reasoning are emitted then; nothing is streamed. Its `cli-turn` and `cli-learning` uploads reach Perch, and the account's durable memories enter the turn, as in any CLI session.
