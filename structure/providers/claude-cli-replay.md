# Claude CLI Replay

`src/adapters/claude-cli/stable-replay.ts` supplies a Claude-only replay builder to the shared `src/adapters/coding-agent/turn.ts` runner through its `conversationInput` slot; CodeBuddy keeps the default projection; Qoder opts into its image-omission markers through the same slot. It emits one legal user frame with a label per message and text and native image blocks in their original order, using identical formatting for a current message and its later history form. User and tool-result images reuse `imagePart` from `src/adapters/coding-agent/protocol.ts`; unsupported references fail explicitly, and a whole-message checkpoint also drops its images. History is trimmed at whole-message checkpoints. Developer messages remain in the system prompt; the cut skips orphan historical results and retains a current result's originating call. Checkpoints are at most 20k characters apart; the cut can also discard the boundary message and any leading orphan tool-result blocks. The model-derived soft cap counts labelled history text plus each image payload/reference string length, excluding the current input and truncation notice; the same sizes drive checkpoint removal without serializing extra image copies. This is a coarse replay-memory guard, not token accounting or a bound on decoded remote images. Retaining the current tool group's originating call can exceed it. Qoder CN image admission and Qoder-only omission markers follow the [coding-agent image contract](../providers/chat-compat.md#unmapped-modalities-are-recorded-not-dropped).

Canonicalization accepts only plain JSON, preserves arrays/literal values, and sorts object keys, including schema object keys and historical tool arguments. Instruction changes intentionally invalidate that prefix. Tools and schema object keys serialize deterministically, preserving catalog membership, MCP aliases, tool choice, and array order. Object-key sorting intentionally changes model-visible property order while preserving JSON values; integer-like keys follow JavaScript's numeric-key ordering. Invalid non-JSON history supplied by an internal caller fails at the runner's stdin projection as a 502, after launch, and the owned child is terminated. Ordinary HTTP JSON requests cannot carry cycles, accessors or undefined properties.

Images in system or developer instructions are refused before helper calls, quota preflight and launch because those instructions are folded into a text-only system prompt. `src/adapters/claude-cli/instruction-images.ts` detects them in the original Chat and Responses bodies before conversion or vision preprocessing can discard them; the ingress carries only a boolean to the selected Claude CLI attempt, including combo children. Expanded Responses history is inspected as well, since parsing folds system items to text. File-backed Responses images in messages, agent messages or tool results are likewise refused before helpers, since parsing otherwise replaces them with text; a usable image URL takes precedence. The value-free 400 never remaps images into user content and does not change other providers. Its locally authored message retains proxy provenance through combo and Chat error translation, so it stays actionable without trusting provider error text. `tests/providers/claude-cli-client-http.test.ts` covers both routes, leading and later instructions, streaming and direct encoders.

## Tool capture

A request that carries tools gets the shared capture-only MCP bridge (`src/adapters/codebuddy/tool-bridge.ts` and its server). `--tools ""` and `--strict-mcp-config` stay on, `--allowedTools` lists only the exact `mcp__opencodex__*` names of the selected catalog, and `tool_choice: none` advertises nothing. The runner returns the first assistant tool batch to the client and terminates the CLI at `message_stop`; the MCP handler never executes a call. Historical tool calls are replayed under the MCP names advertised in the current turn. With `acceptWireToolNames`, a tool_use that names an exact selected wire tool is accepted as that tool; the alias is output-only and never enters `--allowedTools`, and any other name ends the turn with `undeclared_tool_call`.

Claude Code controls actual cache breakpoints, so stable replay alone is not a measured savings claim. `tests/providers/claude-cli-efficiency.test.ts` checks replay stability against the legacy negative control, checkpoint behavior, catalog ordering and instruction authority; `tests/providers/claude-cli-tool-capture.test.ts` and `tests/providers/claude-cli-client-http.test.ts` cover capture ownership through the adapter and through real Responses and Chat Completions requests.

## Usage admission

The shared runner's `onCliOutputError` callback carries accepted CLI error-result text or captured stderr on unsuccessful completion, after redaction. Claude records usage refusals only from that callback; local setup, spawn, stream, replay, and bridge-validation failures retain their client error semantics without recording a subscription reset. Login guidance is applied separately to the emitted client event.

`src/adapters/claude-cli/usage-admission.ts` gates every `claude-cli` launch on the local Claude Code subscription quota. The adapter checks it before spawning the CLI, and the Responses executor checks it before dispatch so an exhausted plan returns 429 `claude_subscription_cooldown` with `Retry-After` instead of a generic 502; Chat Completions keeps that code. Admission and cache invalidation share one window selection (plan windows plus custom windows in scope for the requested model family) and one `>= 100` threshold, so an expired window of another family never forces a re-read. A limit the CLI itself reports with a parseable reset ("resets 3pm (Zone)") is remembered until that time. The requested model id is caller input the CLI can reflect inside its own error wording, so a model id that itself carries the reset-clock phrase makes the message unattributable - real limit or echoed model - and the turn records nothing: the error still reaches the client and recorded or probed limits still gate, but a genuine limit seen only on such a turn is not newly cached.

A probe re-reads the account before it commits: an account switch mid-probe discards the answer (`unknown`, nothing persisted), and the newest refusal is merged at commit time with no await between that read and the write, so a CLI-reported reset is never overwritten. The file has one writer per `OPENCODEX_HOME`, the same single-owner topology as the spend ledger. `src/providers/claude-cli-usage-state.ts` owns the snapshot path, validation and in-memory copy so the quota facade can read it without importing the adapter. The check reads the CLI's own sign-in in memory (`detectClaudeCodeTokenAsync`: Keychain without blocking the event loop, or `<CLAUDE_CONFIG_DIR>/.credentials.json`), caches the resolved identity for one minute, and sends the access token only to Anthropic's usage endpoint through `src/providers/claude-cli-usage.ts`, the same reader the account-pool quota probe uses. `CLAUDE_CONFIG_DIR` is passed to the child so the CLI and the check read one profile. The cache file `<OPENCODEX_HOME>/claude-usage-admission.json` stores only percentages, reset times and a hashed identity key. Every failure (no sign-in, malformed credential, unreachable endpoint) fails open as `unknown`, and a test process (`OCX_TEST_HOME_GUARD`) never resolves the real sign-in. If the executor's check throws or refuses, it releases the web-search sidecar's probe lease first; `tests/responses/responses-claude-preflight-lease.test.ts` and `tests/providers/claude-cli-usage-admission.test.ts` cover both.

The same snapshot is what `/api/provider-quotas` publishes, as an `observed` row from `fetchClaudeCliObservedQuota` in `src/providers/quota/vendor-probes-oauth.ts`: fetching this row never spawns the CLI or probes upstream, and a forced quota refresh re-reads the local sign-in and this file rather than Anthropic's endpoint. Other providers retain their normal probes. The row is bound to the signed-in account: the reader lazily imports `currentClaudeIdentityKey` from the admission (keeping the Keychain reader off the core import path), publishes only that identity's snapshot, and returns authoritative empty when signed out, when the sign-in cannot be read, or when that account has no snapshot with windows, which clears any other account's cached report. Each sign-in read, a turn's admission included, records its hashed key through `recordClaudeSignedInIdentity` in `src/providers/claude-cli-usage-state.ts`; a cached row stops being current once a later read names another account or none. An unforced `fetchProviderQuotaReports` calls `refreshClaudeCliSignIn` (same file as the reader) before its cache fast path; with a `claude-cli` provider configured it re-reads the sign-in through the one-minute identity cache, so a plain dashboard poll drops a superseded row within a minute without forcing other providers to re-probe. `tests/providers/provider-quota-claude-cli.test.ts` covers sign-out and account switch on forced refresh, after a later sign-in read, and on a plain read past the identity cache, plus newer observation timestamps.

These display-only rows are excluded from `notifyProviderQuotaSnapshot` in `src/providers/quota.ts`: they carry no reset authority, so a later snapshot cannot generate a surprise reset across sign-ins.

Report collection reconciles Claude rows and authoritative empty results against the latest recorded identity after its asynchronous work completes. Cached and passive reads likewise rebuild only Claude rows from that identity and its latest snapshot, including after an empty result or before the report cache is populated, while retaining other providers' cached readings. Passive reads do not resolve the sign-in, read credentials, or probe upstream; they reflect an external account switch only after another operation records it.
