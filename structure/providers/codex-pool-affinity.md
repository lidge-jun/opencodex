# Durable Codex Pool Affinity

This doc owns how Codex pool session pins and conversation-state issuers survive a proxy restart.
`src/codex/routing/thread-affinity.ts` keeps the live maps and calls the store at every bind, delete, clear and lookup.
The conversation key, cohort anchors and lineage are owned by [OpenAI Provider Account Modes](openai-tiers.md);
the single-writer lease is owned by [Responses spend](../transports/responses-spend.md).

`src/codex/routing/thread-affinity-store.ts` restores eligible pool bindings after a graceful proxy restart for up to 24 hours idle. Session-bearing requests and session-less requests anchored on their immediate parent have derivable anchors. Deeper session-less chains, keys derived under another config home, legacy raw-parent keys and evicted anchors remain memory-only. Removed, re-logged, expired or identity-less accounts are not restored; normal selection and usability rules still apply.

The config home contains `codex-affinity.sqlite`, mode 0600 with a hardened Windows ACL. Before the store creates or opens the database, `src/lib/private-sqlite-path.ts` requires the database and its `-journal`, `-wal` and `-shm` names to be absent or private regular files: a symbolic link, junction or other Windows reparse point, directory, hard link or (on POSIX) foreign-owned file disables persistence without creating or writing what it names. On Windows ARM64, whose Bun build cannot run the native attribute query, only the symbolic links, junctions and app execution aliases that `lstat` reports as links are seen. On Windows ownership is not compared; the boundary there is the hardened ACL of the config directory and file. Before every write transaction the store checks the sidecar names again and that the database path is still the single-link file it opened; a refusal there is a failed flush: three in a row poison the store, and when the store is poisoned or its final flush is refused the clean flag stays unset, so the next owner discards rows. The check comes before the create because Windows creates a new file through a link at its name, and SQLite opens Windows sidecars by name; an entry planted between the check and SQLite's own open is outside this guarantee. `tests/codex-integration/codex-affinity-restart-matrix.test.ts` (which emulates the Windows create-through-link behaviour on other platforms) and `tests/lib/private-sqlite-path.test.ts` cover it. Its v1 schema has `meta` (store secret and clean flag), `threads` (scoped bindings), and `issuers` (conversation state issuers). Row keys are domain-separated HMACs of the cohort anchor under the store's own secret. Each row stores the local pool account id (the label that config.json and the credential store in this directory already key the account by, as the Claude affinity store does), an identity fence digest and timestamps. Session ids, conversation keys (raw or process-local), emails, ChatGPT account ids and tokens are not stored; a keyed digest of the pool id would hide nothing from a reader of this directory, which holds both the store secret and the account list. The identity fence derives from `quotaHistoryIdentity`, captured at bind and at issuance. Issuance requires both generation and `chatgptAccountId` to match the current record. `__main__` pins and issuers are never persisted. Request-owned keys (`isRequestOwnedAffinityKey`, from `src/codex/request-owned-affinity-key.ts`) are refused at the store's row-key derivation and anchor observer, so they are never anchored, written or restored, as the [request-owned persistence contract](codex-request-owned-affinity.md#persistence-contract) requires. An unknown restored issuer scrubs continuation state; uploaded files are refused when the stored account differs from the serving account, as for known account changes and prior-account moves.

The spend-ledger lease is the single-writer authority. The final releasing hook flushes pending work and marks the store clean before ownership is released; it does so even when the release happens inside a passive read, because it commits only work recorded outside one. A crash, failed final flush or poisoned store leaves the clean flag unset, so the next owner discards rows. Structural changes use an ordered write log; UPDATE-only touches read live timestamps at flush, avoiding stale timestamps and resurrection. The 24-hour idle limit bounds reuse. Expired rows are removed by the next prune that commits: one is attempted when the store opens at lease acquisition, on an hourly timer while it stays open, and after every failed flush, including in a poisoned store. A prune can still be delayed or fail: a lease acquired inside a passive read does not open the store, a store that failed to open is disabled and cannot prune, a prune transaction can roll back, and timers can run late. SQLite secure_delete overwrites freed pages in the database file, but not filesystem snapshots, backups or storage remapping; its transient rollback journal is removed after each commit. The store secret pseudonymizes row keys and does not protect integrity from a local process that can already read the config directory. Pruning also removes future-dated rows and bounds each table to 2,048 entries, evicting model detours first. Other passive reads do not open, adopt or mutate the store. Live affinity survives a lease change in one process. A persistable change to pins or issuers made while the home's database is not writable (between two leases of one process, or while a scope could not open it) marks that database stale; the next scope that opens it clears it before use, so a restart restores nothing rather than a row the process had replaced or deleted. This also drops rows for conversations the process never loaded, which loses pins but never revives one; a serving proxy holds one lease for its whole life and does not reach this path. Row keys and anchors carry across a lease change in the same home, including past a scope that failed to open, so deletes still find their rows after an anchor is evicted. A change made after the final release, before the process exits without taking the lease again, cannot be saved: the lease is gone and another process may already own the database, so the next process can restore the row that change replaced. Such a row still has to pass the identity fence and the resolver's usability checks, and a serving proxy releases its lease only after its listeners have stopped. A manual account switch deletes saved pins and keeps saved issuers, matching the live maps; a full reset deletes both.

`src/lib/config-ownership.ts` includes the database and sidecars in `INITIAL_OWNED_PATHS`; existing homes use `recordOwnedConfigPath`, which updates the manifest under the cross-process ownership lock ([config ownership](../config-ownership.md), #8093). A home without an ownership manifest, created before ownership tracking, still uses the store; uninstall removes nothing from such a home, as for every other file in it. `tests/codex-integration/codex-affinity-store.test.ts`, `tests/codex-integration/codex-affinity-restart.test.ts` and `tests/codex-integration/codex-affinity-request-owned.test.ts` cover store, restart and request-owned exclusion behavior.
