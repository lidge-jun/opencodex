## The evidence gate

Apertis is described in its own note as a **multi-provider API** — an aggregator.
That is a materially different risk class from WP1–WP3, which are first-party
inference services selling their own capacity. For an aggregator, "their public
terms let customers use the API" does not answer the actual question:

> Does STIMA AI LLC / Apertis have the authorization to serve the upstream
> models it resells, and does it authorize a third-party client application to
> route a customer's traffic through `api.apertis.ai`?

The PR author states this plainly in the PR body: "Public endpoint/API/terms/
legal-entity evidence does not prove private routing/resale authorization." The
reviewer reached the same conclusion independently. The submitter and the
reviewer agreeing that the decisive evidence is absent is itself strong signal.

### Research task (dispatched to an independent terra-high subagent)

Hunt for PRIMARY-SOURCE evidence, opened and quoted, not snippets:

1. Apertis / STIMA AI LLC terms of service, acceptable use policy, developer
   agreement, or API terms — any clause addressing third-party applications,
   client integrations, or embedding the API in another product.
2. Official Apertis documentation showing a supported integration path for
   external clients (SDK/proxy/gateway guidance, an OpenAI-compatible base-URL
   swap instruction of the kind Vultr publishes).
3. Any first-party statement identifying which upstream providers Apertis
   resells and under what authority.
4. Corporate identity: is STIMA AI LLC a real registered entity, and does it
   publicly own the Apertis service?
5. Counter-evidence: complaints, provider ToS violations, or reports that
   Apertis resells access obtained outside vendor terms.

Each finding gets a claim-ledger row: claim, URL, date, source type, status
(`verified` / `contradicted` / `unreachable` / `candidate`). Snippet-only
findings stay `candidate` and cannot close the gate.

## Evidence result (2026-08-06)

> Heading corrected after audit round 2. This section originally read "the gate
> resolves to Branch A". It does not; see the Verdict below. The findings in
> this section stand — only the conclusion drawn from them was wrong.

An independent evidence hunt (terra high, `cxc-search` Tier 2 open-the-source)
plus two Luna discovery lanes returned the following, every decisive item read
from the primary source rather than a snippet.

### The decisive finding

Apertis publishes a **first-party integration guide for OpenCode**, a
third-party open-source coding client, instructing the user to point it at
`https://api.apertis.ai/v1` with their own Apertis key:

> "Replace `your_apertis_api_key` with your actual API key from Apertis
> Dashboard."
> — <https://docs.apertis.ai/installation/opencode/>

`https://apertis.ai/integrations` documents the same for Cline, CLIProxyAPI,
Kilo Code, and Roo Code; the homepage additionally names Claude Code and Cursor.

This is the same authorization signal the accepted first-party presets rely on.
It is, in fact, stronger: Vultr's evidence is a generic "replace your base URL"
pipeline-integration note, whereas Apertis names the exact class of client
opencodex is and publishes its configuration.

### Terms of service (opened, effective 2026-04-30, updated 2026-05-19)

Two clauses matter, and they point in opposite directions until read carefully:

> "Sharing, reselling, or transferring your account or API keys to third parties
> is prohibited."

This does not bar the opencodex preset. opencodex is a **local proxy running as
the user, holding the user's own key, sending it to the user's own Apertis
account.** The key does travel to `api.apertis.ai` — the preset's own test sends
`Authorization: Bearer <key>` there
(`refs/tmp/pr812:tests/apertis-provider.test.ts:111`) — but it goes to the
destination the user chose, with no custody by opencodex, no hosted relay, and
no redistribution to another party. The clause bars the user from handing their
key to someone else, which is not what a local preset does.

(An earlier draft of this paragraph claimed "no key leaves the user's machine".
That was wrong and is corrected here rather than left standing.)

> "Apertis operates as an intermediary platform that routes API requests to
> third-party AI providers." / "You are also required to comply with the
> acceptable use policies of all applicable upstream AI providers."

Apertis self-describes as an intermediary and pushes upstream-AUP compliance
onto the customer.

### Corporate identity (government registry, opened)

STIMA AI LLC is an active Wyoming domestic LLC, filing ID `2025-001692804`,
initially filed 2025-06-04. Apertis publicly identifies STIMA AI LLC as its
operator. The entity is real and the ownership claim is consistent.

### Live endpoint (no key sent)

`api.apertis.ai` resolves behind Cloudflare. Unauthenticated
`GET /v1/models` returns HTTP 401 `API Key not provided`. The endpoint the
registry entry names is real and Bearer-gated, matching the preset.

### Counter-evidence: searched for deliberately, none found

Targeted GitHub issue searches for `Apertis resell`, `Apertis "account sharing"`,
`Apertis "reverse proxy"` returned no matches. Hacker News returned zero hits.
No upstream vendor takedown, complaint, suspension, or enforcement action naming
Apertis or STIMA AI LLC was found. The only third-party report located is a June
2026 Cloudflare 524 outage issue — a reliability report, not an abuse
allegation. Reddit and X search surfaces were blocked by human-verification
challenges and are recorded as `unreachable`, not as evidence of absence.

### The residual, stated honestly

What is NOT established: that Apertis holds upstream authorization to resell
every model it exposes (OpenAI, Anthropic, Google, and others). No reseller
agreement or partnership announcement is public, and Apertis's own provider list
is not proof of it.

That residual does not block this preset, for a reason that must be stated
plainly rather than waved through: **it is the identical residual carried by
every aggregator preset already shipping on `dev`.** Verified by executing the
registry — all present with `authKind: "key"`:

```
openrouter PRESENT   cline PRESENT   cline-pass PRESENT
orcarouter PRESENT   bizrouter PRESENT   commandcode PRESENT
(agentrouter is free-directory only, not a registry preset)
```

None of those has a public upstream reseller agreement either. Applying a
stricter bar to Apertis than to the aggregators already merged would be
inconsistent, and consistency is what makes a registry policy defensible.

The bar this project can actually apply is: a real legal entity, a first-party
documented integration path for third-party clients, a Bearer-gated endpoint the
user's own key reaches directly, and no counter-evidence of abuse. Apertis meets
all four.

### Verdict — REVISED after audit round 2: Branch C, not Branch A

The round-1 verdict claimed Branch A on a consistency argument. The independent
auditor called that a false equivalence, and the auditor is right. The argument
is withdrawn, and the reasoning is recorded here rather than quietly deleted,
because the way it failed is the useful part.

**What the evidence actually establishes.** The OpenCode guide answers ONE of
the two questions the gate asks: may a third-party client route a customer's own
key to `api.apertis.ai`? Yes — Apertis publishes the configuration itself. That
part of the reviewer's blocker #2 is genuinely answered.

**What it does not establish.** Whether Apertis is authorized to resell the
Anthropic, OpenAI, and Google inference it lists. A vendor documenting how to
point a client at its own API says nothing about its rights to the upstream
models behind it. Those are independent questions and the evidence only closes
the first.

**Why the consistency argument fails.** It rested on "the merged aggregators
carry the same residual", supported only by the observation that they exist in
the registry with `authKind: "key"`. Presence is not provenance. Checking what
those rows actually carry:

- `cline-pass` (`src/providers/registry.ts:1114`) carries a primary-source
  comment block stating that Cline "explicitly authorizes using the full slugs
  through Cline's external API" — an authorization citation, dated 2026-08-02.
- `orcarouter` (`:1164`) carries live-verified behavior notes dated 2026-07-20.
- OpenRouter operates a public provider application, onboarding, and review
  program — a documented upstream-relationship process that Apertis has no
  published equivalent of.

So the merged aggregators are not a set of unexamined precedents. Some carry
explicit authorization citations; the weakest of them still predate the written
policy. Reasoning from "we already merged some" toward "so merge this" is
precedent-mining, not evidence.

**The decisive point: the project has a written rule and it is not silent here.**
`MAINTAINERS.md:50-58` and `docs-site/src/content/docs/contributing.md:160-188`
require, for a canonical preset, five things — documented endpoints, ToS and
legal entity, **"Resale or routing authorization for aggregators"**, a named
maintenance owner, and a citable verification date. The contributing doc states
the rationale in terms this exact case answers:

> "A gateway that sells access to Claude, GPT, Gemini, or other third-party
> models should show its authorization to route to them. Users read a built-in
> preset as a maintained route, not as an unverified reseller."

and prescribes the remedy:

> "When the evidence is incomplete, the honest home is a reference row in
> `src/providers/free-directory.ts` rather than the canonical registry."

Apertis satisfies four of the five requirements — endpoints (verified live, 401
without a key), ToS and legal entity (STIMA AI LLC, active Wyoming LLC, filing
`2025-001692804`), a maintenance owner, and a verification date. It fails
exactly the aggregator clause. The rule already names what to do about that, and
the first reviewer independently reached the same fallback.

**One further correction.** The round-1 text said "no key leaves the user's
machine to a third party". Too loose: the preset's own test sends
`Authorization: Bearer <key>` to `api.apertis.ai`
(`refs/tmp/pr812:tests/apertis-provider.test.ts:111`). The accurate statement is
that the key goes to the destination the user chose, with no custody by
opencodex. That distinction matters and the original phrasing blurred it.

evidence is incomplete against a written rule, and one specific artifact would
complete it. Ambiguity resolves to "not merged" because the asymmetry is real: a

2. reports that the third-party-client question IS now answered by Apertis's own

3. names the remaining gap precisely: the aggregator resale/routing

4. does **not** promise the free-directory fallback (see correction below);

5. notes the `gui/package.json` lint-runner rewrite and the nine `openspec/**`

### Correction (audit round 3): the free-directory fallback does not apply here

`MAINTAINERS.md` and the contributing guide name an inert
`src/providers/free-directory.ts` row as the remedy for incomplete evidence, and
round 2 repeated that offer. Audit round 3 showed it is not available for
Apertis as a matter of code, not policy.

`FREE_PROVIDER_DIRECTORY` is generated from `FREE_PROVIDER_ACCESS_GROUPS`
(`src/providers/free-directory.ts:1-30, 164`), and every row must belong to one
of four **free-access** groups: `recurring-or-keyless`, `recurring-uncapped`,
`recurring-credit`, `signup-credit`. The directory is a catalog of ways to use a
model at no cost, not a general "providers we know about" list. Apertis's own
FAQ describes plan- or PAYG-balance-backed access, with free models included
inside a paid plan — that is not a documented no-cost access group.

Offering a fallback the contributor cannot actually take would be worse than
offering none. So the comment offers the honest alternative instead: the custom
OpenAI-compatible provider flow already works for Apertis today and needs no
change to this repository.

### Is the ask actionable? (audit round 3, named honestly)

The remaining artifact — authorization to route to the Anthropic/OpenAI/Google
models Apertis exposes — is **external-provider evidence, not contributor work**.
An affiliated contributor could obtain it; an unaffiliated one plausibly cannot.
The comment must say so, rather than framing it as a task the contributor is
expected to complete. Anything else is a rejection dressed as a request, and the
contributor deserves the straight version: this is blocked on Apertis, not on
them.

### Rule applicability, tested against the strongest counter-reading

The counter-reading considered: Apertis's FAQ claims paid multi-provider routes
rather than resold consumer subscriptions, so perhaps it is a first-party
service rather than the "gateway selling access to Claude, GPT, Gemini" the
clause targets. That reading does not survive Apertis's own description — one
key, unified billing, a multi-provider catalog, and explicit routing to
third-party providers, with its Terms stating "Apertis operates as an
intermediary platform that routes API requests to third-party AI providers."
That is the clause's subject regardless of whether the underlying access is
PAYG or subscription. The rule requires authorization, not a claim that the
routes are paid for.
