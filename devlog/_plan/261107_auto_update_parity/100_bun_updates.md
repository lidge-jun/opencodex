# Signed Bun-owned updates — draft unit

**Status:** follows the common signed supply, idle admission and npm-owned
stage/recovery work. The current Bun-owned update runs a global add
(`src/update/index.ts:354`); that is not evidence of independently staged,
publisher-verified activation or rollback.

## Proposed implementation slice

1. Add `src/update/bun-prepared-install.ts` and an owner record for the selected
   Bun global package root, bin links, global manifest/lock state and exact
   signed candidate. Use `detectInstallOwnership` and fail closed on unknown,
   foreign or changed ownership (`src/update/orchestrated-plan.ts:21`).
2. Materialize the verified signed executable closure into a disposable Bun
   global layout with scripts disabled and network denied. Bun's installed
   help exposes `--offline` and `--ignore-scripts`, but the exact invocation,
   global metadata behavior and relocation semantics must be proven in isolated
   fixtures before they are claimed as supported. Validate every installed file
   and link against signed inventory; preparation must not write to the live
   global tree or execute a downloaded helper.
3. At activation reacquire the existing home sync/update guard and service
   ownership lease. Obtain installation-wide coordination only after `020`
   designs and proves it; revalidate stage, policy and owner, then obtain the `020`
   idle update-stop reservation. Journal a manager-mediated selected-root
   transition and verify its package, metadata and bin links before execution;
   do not claim that the manager changes those files atomically. Retain the
   signed previous installation until health and probation complete.
4. Extend `src/update/orchestrated-entry.ts` and the automatic coordinator with
   a separately versioned prepared operation. Preserve current explicit update
   output and existing ownership/supervisor refusals while requiring verified
   supply for installation. Never fall back to an
   unverified global add when offline preparation or rollback cannot be proven.

Add domain-registered `tests/update/update-bun-prepared.test.ts` and use
isolated homes, a signed test closure, fake manager workers and network denial.
Cover changed owner, global lock/bin drift, script and unsigned dependency
refusals, expired stage, interrupted worker, rollback after each mutation,
health readback and concurrent sync. Update `structure/runtime.md`,
`structure/ops/service-and-sidecars.md` and affected user docs/translations.

Run failing-first focused tests, typecheck, privacy/structure, test-layout and
file-size gates, the Lab boundary test, relevant platform CI and a separate
independent security PASS. Actual Bun global layout, cache isolation,
manager-compatible durable transition and signed rollback remain proof blockers
before this unit can be enabled.

## Isolated feasibility observation

On 2026-11-07, Bun `1.4.4` installed an inert local fixture into an isolated
`BUN_INSTALL` root with `--global --offline --ignore-scripts --no-env-file`;
the command exited 0 and the fixture's postinstall sentinel was absent. A
macOS `sandbox-exec` profile denied network and writes outside the temporary
root, and separate probes confirmed those denials. The observed output included
a global manifest/lock, a nested package directory and a relative bin symlink.
This proves only that one local package can be prepared without its lifecycle
script in that fixture. A separate offline fixture round trip changed versions
1.0.0 → 1.1.0 → 1.0.0 with the sentinel absent. Copying the global root
retained an absolute `file:` source in its manifest, so naïve relocation was
not established. These experiments do not prove signed dependency closure,
atomic activation, verified recovery or runtime health.

Pre-audit research investigated a manager-supported transition and recovery
with a locally signed dependency fixture. Exact commands, publisher-signed
versus manager-generated bytes, root/bin ownership, interruption and cleanup
evidence are retained under `.tmp/`; no real install was touched.

The follow-up isolated macOS arm64 investigation with Bun 1.4.4 used a signed
local two-package fixture and showed offline selected-owner install and
restoration, plus `--lockfile-only` preparation followed by frozen
materialization. A separate Bun 1.4.3 fixture did not satisfy the selected-root
contract; it does not establish a general supported-version floor. Interrupted
and competing manager operations showed that package, metadata and bin changes
cannot be treated as one atomic transition. The selected direction is a
journaled manager-mediated operation under the installation-scoped exclusion in
`020`, with exact signed prior/candidate inputs, bound root/bin/cache identities,
complete output/link verification before execution and verified recovery.
Resolve custom global roots explicitly, preserve unrelated global packages and
retain operation-owned recovery material through probation. Prove process
termination, every relevant interruption boundary, cross-platform behavior and
cleanup before enabling the owner. A lockfile, successful manager exit or this
fixture is not authentication or crash-safety proof; detailed negative
evidence remains in the private research packet.

For the observed Bun 1.4.4 fixture, classify global manifest/lock, `.bun-tag`,
cache metadata and bin links as manager-generated state, separate from signed
package files. The adapter accepts only version-specific parsed schemas and
expected link targets bound to the selected root/bin/cache and verified
payload; no unrecognized generated executable, metadata form or escaping link
is accepted. A recorded digest detects later drift but does not turn local
metadata into a publisher signature. Bun 1.4.3 and all untested layouts remain
unavailable until separately proven. Test foreign entries, custom roots,
changed bins, unrelated global packages and interrupted recovery before any
candidate executable is launched.
