# Сохранение долгосрочной квоты: экспериментальная стратегия

## Цель и утверждённый объём

Добавить Codex-only стратегию `preserve-long-quota`, сохраняющую долгосрочный запас при смешанных наборах quota windows. Пользователь утвердил реализацию стратегии и тестов без запуска экспериментального прокси с рабочими аккаунтами.

Официальное приложение, updater, live config, credentials и клиентские интеграции не изменяются. Работа ведётся в отдельной ветке `feat/preserve-long-quota`. Исходный checkout — 2.100.0; установленная официальная версия — 2.100.2. Перенос на последующие версии — отдельное осознанное действие, не автоматическое обновление экспериментальной установки.

## Рассмотренные подходы

- Ближайший недельный сброс: решает исходную пару short+weekly / weekly-only, но ставит short-only аккаунты в невыгодное положение.
- Сохранение долгосрочного запаса: сначала short-only, затем weekly, затем monthly; выбран пользователем. Это эвристика без предположений об абсолютной ёмкости разных подписок.
- Внешний контроллер или plugin: не выбран; plugin API не регистрирует native account selectors, внешний контроллер не участвует в каждом placement.

## Поведение

Существующие eligibility, priority, per-account thresholds, manual preference, scoped health и cache-affinity остаются авторитетными. Новый picker применяется внутри полученного списка допустимых аккаунтов.

1. Как в reset-first, предпочитать аккаунты с quota headroom. Если таких нет, использовать существующий lowest-usage fallback.
2. По известным account-family quota observations определить самый длинный ограничивающий период: short-only, weekly (в том числе short+weekly), monthly (в том числе weekly+monthly).
3. Предпочитать short-only перед weekly, weekly перед monthly. Отсутствие длинного окна в неполных или неизвестных данных не доказывает short-only. Нераспознанные данные идут после известных категорий, но остаются fallback.
4. Внутри категории предпочитать ближайший будущий reset самого длинного окна. Отсутствующий, нечисловой или прошедший reset не превращает weekly/monthly аккаунт в short-only; deadline считается неизвестным.
5. При равном основном deadline сравнивать будущие короткие resets, только если оба известны. Иначе использовать существующий usage tie-break и стабильный входной порядок. Реализация должна избегать нетранзитивного comparator: фильтровать кандидатов последовательно; короткий tie-break применять только при наличии будущего short reset у всех оставшихся кандидатов.
6. Времена в секундах/миллисекундах нормализовать существующим resetAtToMs.
7. Для independent model-quota scopes использовать прежний quota fallback: shared snapshots не описывают эти лимиты.
8. Preview, resolve и alternate/failover используют один picker. Живые bindings сохраняются по существующей cache-affinity policy; пересчёт разрешён только при прежних условиях освобождения и наличии измеренного headroom у замены.
9. Старые стратегии не меняются; default остаётся quota. Anthropic и generic pools новую стратегию не принимают.

Для классификации использовать реально имеющиеся поля наблюдений, не имя тарифного плана. При неизвестных/custom-only данных не обещать оптимальность или отсутствие других ограничений. Пользователь отдельно одобрил расширение provenance: shortOnlyObservedAt сохраняет время полного разрешённого WHAM-наблюдения с измеренным коротким primary, явно null secondary/tertiary и без additional limits. Частичные headers не создают и не продлевают доказательство; новый long/custom snapshot отменяет привилегию. Доказательство действует шесть часов, как legacy disk cache TTL; после этого требуется новое полное наблюдение. Оно хранится только в памяти и привязано к quotaHistoryIdentity пула или live main writer; после перезапуска подтверждается заново. Штатный refresh той же identity сохраняет его, замена или ABA identity — нет. Явно противоречащая топология (включая additional limits и длинные окна без процента) отменяет прежнее доказательство. Существующие long windows не удаляются новой стратегией: normal quota merge остаётся авторитетным.

## Пользовательская поверхность

CLI/API принимают и возвращают `preserve-long-quota` только для Codex. Dashboard показывает «Сохранять долгосрочную квоту» только у Codex, с локализованным объяснением порядка и сохранения bindings. Existing reset-first остаётся неизменным. Обновляются существующие руководства по конфигурации/CLI и контрактный документ account routing.

## Проверки

- Short+weekly со сбросом short сегодня и weekly через пять дней проигрывает weekly-only со сбросом завтра.
- Short-only проигрывает недоступности, но при одинаковых priority и доступном headroom выигрывает у short+weekly независимо от близости short reset последнего.
- Weekly выигрывает у monthly; monthly сравниваются по monthly reset.
- Unknown/custom-only/partial evidence не превращается в привилегированный short-only; прошедший long reset не меняет категорию.
- Preview без mutation совпадает с resolve и failover; cache-affinity, threshold=0, priority и independent scope сохраняют прежние контракты.

## Следующий этап, не включённый в эту реализацию

Подготовить безопасный source/Bun launch с отдельными proxy/client homes, owner registry и выключенными интеграциями. Один OPENCODEX_HOME и другой порт не гарантируют отсутствие общих startup side effects. Не запускать второй прокси и не копировать OAuth credentials до отдельной проверки изоляции.
