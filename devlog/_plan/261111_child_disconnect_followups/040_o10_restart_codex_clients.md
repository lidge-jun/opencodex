# O10 — restarting running Codex clients after sync (proposal, not built)

## What happens today (source-checked)

- `ocx sync` on a Child takes the connected path (`src/cli/sync-command.ts` → `syncConnectedClient`). After it, `handleConnectedSyncCatalogWrite` runs the restart scope only when that sync wrote the catalog or the models cache (`if (!result.catalogWritten && !result.cacheSynced) return`).
- Without a restart flag, the same write path calls `afterCatalogWriteHandleAppServers({ restart: false })` (`src/codex/app-server-processes.ts`), which prints "WARNING: N Codex app-server process(es) still running … Re-run with `ocx sync --restart-codex`" for app-servers started before the catalog's mtime. `ocx status` reports `clients=pending-restart(pid …)` from the same stale-client observation (`src/codex/autostart-health.ts`).
- Why the advice did not apply: the re-run writes nothing (the catalog is already current), so the restart scope never runs. The registry already says so for `ocx system codex-restart`: "`sync --restart-codex` is not a substitute: it restarts only as a side effect after a catalog, cache, or changed configuration write".
- `ocx system codex-restart --yes` restarts on request, but it posts to `/api/system/codex-restart` on the running runtime's management API. A Child's client runtime serves only the machine listener (`src/client/machine-listener.ts`: `/healthz`, the bound `POST /api/system/restart`); nothing under `src/client/` serves `codex-restart`, so on a Child this command has no endpoint to reach (to confirm with a test before relying on it).
- The Home's `ocx link restart-codex` and `ocx link sync --restart-*` send a second pinned `ocx sync --expect-link <id> --json --restart-codex` to the Child (`src/link/ssh-argv.ts` `remotePinnedSyncArgv`). That goes through the same write-gated path, so a second sync that writes nothing restarts nothing. That is likely the same gap and needs a test to confirm. The Home withholds the restart while a relayed model request for that Child is in flight (`src/link/sync-then-restart.ts`, `restart-skipped:link-active`).
- Idleness: OpenCodex sees a turn only as a request through its own proxy (`getActiveTurnCount()` in `src/server/lifecycle.ts`, used by `src/codex/catalog-self-heal.ts`; the link's in-flight count on the Home). It cannot see a Codex app-server's own state: a turn waiting on an approval prompt, or a composer draft, has no request in flight.

## Proposal

1. **Restart what is actually stale, on request.** When `ocx sync --restart-codex` / `--restart-app-server-only` writes nothing, still restart the app-servers that `computeCodexAppServerCatalogStatus` classifies as stale (started at or before the current catalog's mtime). That makes the command the warning prints do what it says, and makes the Home's second pinned sync effective. Processes are the ones `listCodexAppServerProcesses` already selects (same user, Codex app-server / code-mode-host argv), narrowed to the stale set. A fresh process is never touched. The desktop app is quit only for the full `--restart-codex` scope, as today.
2. **Idle gate.** Before restarting, the Child checks its own client runtime for active turns, which needs a small `activeTurns` field on the client `/healthz`. If a turn is active it withholds the restart and reports `restart-skipped:active`, matching the Home's `link-active`. Because app-server-internal state stays invisible, the explicit flag (and `--yes` for the desktop scope) remains the consent. "Idle" here means no proxied request in flight, not "safe to discard UI state".
3. **Where it belongs.** Child-local: `ocx sync --restart-*` (the code path above), so a person on the Child, the Home's pinned sync, and `ocx link restart-codex` all share one implementation. `ocx system codex-restart` on a Child should either run the same local module or refuse with a message naming `ocx sync --restart-app-server-only`, instead of reaching for a management API the client runtime does not serve.
4. **Hints.** `clients=pending-restart` in `ocx status` and the sync warning on a Child should name the command that works there.

Not built in this PR: (1) changes Home fan-out restart behaviour and needs its own tests across the three entry points. (2) adds a field to the client health contract.
