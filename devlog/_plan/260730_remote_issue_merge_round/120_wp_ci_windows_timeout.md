교훈: run 단위 `conclusion`만 보면 안 되고 **잡 소요 시간**을 봐야 타임아웃과 동시성
취소를 구분할 수 있다. 취소에는 최소 두 가지 원인이 있다.

## 변경

`.github/workflows/ci.yml` 1파일, `timeout-minutes: 12` → `20` + 근거 주석.

주석에 측정값과 함께 "이 숫자를 또 올리는 건 답이 아니다"를 명시했다. 기존 주석이
8분→12분 상향을 기록하고 있었고 그 12분도 소진됐으므로, 다음에 또 근접하면 2.5배 격차
자체를 고쳐야 한다.

`npm-global-smoke`는 8분 그대로 두었다. 1~2분에 끝나 한도에 근접한 적이 없다.

검증: `yaml` 파서로 `test=20`, `npm-global-smoke=8` 확인. `git diff`가 해당 한 줄과
주석만 보여준다. 검증 중 임시 설치한 `yaml` devDependency는 제거해
`package.json`/`bun.lock`을 원복했다.

## Windows 2.5배 격차의 유력 후보 (미조치)

`ci.yml:85` — `bun test --isolate tests`. `--isolate`는 CI에만 있고 `package.json`의
로컬 `test` 스크립트에는 없다. 테스트별 프로세스 격리는 Windows 프로세스 생성 비용이
비싸 격차의 원인일 가능성이 높다.

**의도적으로 건드리지 않았다.** 격리를 끄면 테스트 상호 오염 가능성이 생겨 신뢰성 성격이
바뀐다. 타임아웃 완화와 같은 커밋에 넣을 변경이 아니고, 오너 판단 사안이다.

## 부수 발견: 사용자 커밋이 privacy 게이트를 깨뜨린다 (#710 코멘트)

검증 중 `bun run privacy:scan` 실패를 발견했다.

```
tests/kiro-windows-cli-db-path.test.ts:62 home-path: /Users/u/
```

범위를 격리 확인했다: `origin/dev` `d24c5233f`는 통과, `14d58ec1d` 적용 시에만 실패,
무관한 워킹트리 변경을 전부 stash해도 재현. 즉 그 커밋이 원인이다.

원인은 `scripts/privacy-scan.ts:60`의 허용 목록 — 테스트 픽스처는 `example`, `test`, `x`만
허용하는데 새 픽스처가 `u`를 쓴다. macOS 픽스처 2곳(58, 62행)만 해당하고 Windows
픽스처(`C:\Users\u`)는 정방향 슬래시 패턴에 걸리지 않아 무해하다.

파일이 사용자 작업분이라 수정하지 않고 #710에 코멘트했다(5124463056). `u` → `x` 두 곳
치환이 최소 수정이다. 푸시 전에 고쳐야 CI가 빨간불이 되지 않는다.
