## Where PR1 differs from 030

- **Part B's closing sample.** The 6 s hold is measured between port sample starts, and the window floor is also 6 s, so the last sample starts at the window's end and can run up to its 0.5 s cap past it. The budget counts this; the current admission minimums are 48.5 / 56.5 / 50.5 s, including the later WinSW wrapper check. The Desktop drain case becomes 70.5 s, which still fits in 72 s.
- **WinSW wrapper evidence.** WinSW-only Part A enumerates and binds wrappers, including with the service stopped, so the own-wrapper guard and stray evidence apply. "Proxy still alive after WinSW stopped" is an injected `proxyAlive` check inside the 1 s manager-state step. An answer of "cannot tell" leaves the decision to Part B.
- **Terminates share the wait cap.** 030's tables do not price the terminate calls themselves. They share the 3 s handle-wait window, which matters for the ARM64 script (about 1 s each).
- **Unbound wrappers with nothing registered.** Binding finds no bound wrapper but an unbound one is alive. The result is `survived` / `unbound-wrapper`, not `absent`, matching 040's bullet; the 030 "absent" definition reads as "nothing bound" alone. Nothing is changed either way.
- **Unreadable candidates with nothing registered.** An unreadable wrapper image above the child counts only while a manager is registered. A hand-started proxy under an elevated shell would otherwise lose the stop it gets today. A matching wrapper without a creation time stays `unknown` even with nothing registered.
- **Snapshot type.** The snapshot type is `WindowsStopProcessEntry`, which is `WindowsProcessEntry` plus `startTime`, in the evidence module. `windowsProcessList` and the guarded inspection stay untouched until PR2 switches them.
- **The Schedule PID is read before admission.** Part A reads the Task Scheduler host PID from the SCM (cap 2 s) right after the registration probe, before admission, whenever a task is registered or a stray sweep runs. 030's tables do not list this read. Admission measures the time left on the caller's deadline, so the read's actual elapsed time is already taken out of what admission sees, the same way the step 1 stray enumeration is.
- **Not every effect is capped.** The registration probes, enumeration, Schedule PID, `/end`, WinSW stop and poll, terminates, manager state and `proxyAlive` run under caps. `openWatch` and the authorizer do not. `openWatch` is one `OpenProcess` per wrapper with no wait in it. The authorizer runs before each manager stop and before each terminate, inside the shared 3 s terminate-and-wait window, so a slow authorizer eats that window: the next terminate gets less time, and an authorizer that never returns hangs Part A. PR2's authorizer (the updater's `mutationGate` check) has to be bounded by its caller.
- **Fractional timeouts.** A cap derived from the deadline (`windowEnd - now`) is fractional on the real clock. The spawned terminate fallback floors it to whole milliseconds before building the script and calling `execFile`, and spawns nothing when it floors to 0, because `execFile` reads a 0 timeout as "no timeout".

## ARM64 decision for PR2

050 requires an ARM64 device run before the bounded fallback ships; without one, ARM64 ships the strict variant (report `unknown`, kill nothing). No ARM64 device run exists, so PR2 ships the strict variant. PR1 still contains the fallback script, and `terminateWindowsProcessBound` reaches it on its own: on win32 without the FFI primitive (ARM64, or an x64 whose DLL load failed) it runs the PowerShell script. PR2's terminate adapter therefore has to gate strict itself, for example by answering `unavailable` whenever `windowsProcessNative()` is null, and must not call `terminateWindowsProcessBound` there. Without a native API `openWindowsProcessWatch` already answers `unavailable`, so the wait reports `unknown` rather than proving an exit.

## Notes for PR2

- **The route's caps.** 030 caps the `/api/stop` route's stray sweep at 4 s and its receipt-less Part A at 6 s. `stopWindowsServiceChecked` has no overall cap: its own caps add up to more (the stray path alone has a 5 s enumeration), and it never returns before its steps do. The route needs an outer race on its deadline that answers `service_state_unknown` on overrun, or cap overrides passed in, such as a 4 s enumeration for the sweep.

## Where PR2 differs from 030

PR2 wires every caller listed above; `structure/ops/windows-checked-stop.md` ("Callers") is the contract. Points where the wiring makes a decision 030 leaves open, or departs from it:

- **Route caps.** The outer race lives in `runWindowsServiceStopPartA({ capMs })`: an overrun answers `unknown` at once, and from then on the live `/end` and WinSW stop are gated off and the authorizer refuses every terminate, so nothing changes after the answer. A step that already started (a `/end` in flight) still completes.
- **The receipt record is checked against registration only.** The route skips Part A when the record's managers match a fresh registration probe (2 s each). It does not re-enumerate the recorded wrapper set; that would be the second enumeration 030 rules out.
- **The ancestry guard (r2 review).** The binding rule excludes the stopper but not its ancestors, so interactive callers refuse a Part A whose stopper descends from this home's wrapper. `/api/stop` and the updater opt out because both run beneath that wrapper by design. The check reads the bind snapshot (or the guarded snapshot), so it costs no extra enumeration.
- **Updater WinSW stop.** The updater now runs the same authorized checked Part A for both backends and aborts unless the result is stopped or absent; a WinSW error cannot be treated as success.
- **Absent service stop.** Before restoring shared config, `ocx service stop` proves every candidate endpoint dead; live or unknown evidence keeps the receipt.
- **Receipt target.** Service stop, removal and install resolve the proxy once, claim only for that target's exact endpoint, and send the same endpoint to the child stop. No target means no receipt or POST.
- **The guarded evidence snapshot (r1 review).** The guarded inspection reads `windowsProcessSnapshot` and the Schedule PID once per inspection instead of the CIM-only `windowsProcessList`, and `stopManager` binds on the revalidation's copy. A CIM-only table would make the x64 terminate answer `reused` and Part A report a live wrapper as exited.
- **Absent counts as a pass for the updater and for install.** 040 says call sites abort on a non-`stopped` outcome. `absent` (nothing registered, nothing bound) has nothing that could relaunch the proxy, so the updater, install and switch continue on it, as `ocx stop` does. Refusing it would block every update on a machine whose recorded service was deleted.
- **`ocx service stop` on Part A failure** refuses before the receipt and the child stop, the same rule as plain `ocx stop`, so it never restores under a wrapper that can relaunch the proxy.
- **Part B's foreign result** fails install and switch (030) but not `ocx stop`, `ocx service stop` or uninstall, which only need our processes gone.
- **Not capped here.** The guarded path's own pre-steps (`runResolve`, the tracked-record check, the two inspections and their 5 s snapshot) run before admission and are measured, as 030 says. `proveLiveProxyOwnedByHome` is not capped separately; orphan discovery's `findLiveProxy` is capped at 3 s, and a missed orphan is caught by Part B. `revertSystemEnv` returns at once off macOS, so its 1 s cap holds on Windows without a change. `restoreSharedClientStateAfterStop` and `performStopTeardown` were not measured on a device; 040 keeps those measurements.
- **The manager-state read.** `schtasks /query /fo CSV` first, `Get-ScheduledTask` within the same 1 s cap when the status word is localized. On a slow or non-English machine that can overrun and report `unknown`; the 040 device run decides whether the cap needs to grow.
- **ARM64 ships strict** as recorded above; `windowsStopTerminate` enforces it whenever the native API is missing.
- **The deadline's origin depends on the caller.** 030 prices `ocx stop` from process start, which is right for an operator's command and wrong for every other caller: `installFreshWindowsSchedulerSafely` reaches the stop only after registration and the UAC prompt, so a 60 s budget measured from process start can already be spent and admission refuses `unverified-budget` a stop that has its whole budget left. `windows-stop-deadline.ts` therefore keeps an explicit command deadline (set by the dispatcher from `--deadline-ms`/`OCX_STOP_DEADLINE_MS`) separate from a phase deadline that the first read in a stop phase arms. One deadline governs a phase; a later read does not slide it forward, and setting or clearing the command deadline re-arms.
- **The port wait is skipped on both Windows paths.** `windowsPartBDue` is snapshotless-only because it also gates the legacy respawn re-poll, so keying `skipPortWait` to it left the guarded path and `ocx uninstall`'s two `stopProxy` calls running the legacy 15 s `waitForStoppedPort` on top of Part B. `windowsPartBOwnsPortWait` (any Windows Part A `stopped`) now drives `skipPortWait`; the respawn semantics stay snapshotless.
- **Service removal claims its receipt first.** Part A leaves the scheduler task registered, so `stopTrackedProxyForServiceCommand`'s receipt-less POST answered `respawnable_service` (409) and the removal refused. `windowsServiceRemovalStop` now claims a receipt carrying Part A's record before the child stop, keeps it until the shared restore succeeds, and sends no child stop when the claim fails — the same rule `ocx service stop` already had.
- **Orphan discovery takes the cap its caller admitted.** `stopTrackedProxyIfRunning` hardcoded 7 s, which is more than the 3 s admission priced, so discovery could overrun the budget admission had just proven and Part B's window with it. The helper takes `orphanDiscoveryCapMs`; the checked Windows callers pass `WINDOWS_STOP_CAPS.orphanDiscovery` and the default keeps macOS and Linux unchanged.
- **Listener identity is tri-state.** `verifyPidIdentity`'s null covers both "not an ocx process" and "the probe could not answer", and mapping it to `foreign` reported a listener we merely could not read as another program holding the port — `portHeldByForeign` then let the caller restore shared config with the proxy possibly alive. Only `inspectOcxStartProcessIdentity`'s `mismatch` is foreign; `unverifiable` is unknown.
- **The Part B port sample honors its timeout.** `sampleWindowsStopPort` called the synchronous `scanListenPids` and ignored `timeoutMs`, so the closing sample could stall the stop past its cap. It is now async over `netstat.exe` through `execFile` with the caller's timeout and `SIGKILL`; a timeout or an unreadable scan samples `unknown`, and the timeout is floored because `execFile` reads 0 as unlimited.
- **A not-running task needs its registration proof before `bound-stray`.** The state word says the task is inert, not that it is ours; promoting on the word alone let a same-named foreign task make this home's hand-started wrappers terminable. The promotion now follows `winTaskXml` and `winRegistrationOurs`, and anything else keeps the previous verdict.

- **Uninstall's proxy stop claims its receipt before the child stop.** `handleUninstall` sent `/api/stop` without a teardown receipt, so the route finished the shared teardown while the wrapper respawn window had not been checked yet; a failed `verifyUninstallStopWindow` then left shared config restored under a wrapper that could relaunch the proxy. On Windows the uninstall proxy stop is now `src/cli/uninstall-stop.ts`: it claims a receipt carrying Part A's record before the child stop, sends its nonce, and discharges it only after Part B and the shared restore. A failed claim sends no child stop; a failed later step keeps the receipt for recovery.
- **Uninstall never forces a stop its Part A could not prove.** When Part A did not end `stopped` or `absent`, the uninstall proxy stop still sends the graceful POST but passes `allowForcedFallback: false` to `stopProxy`, so a POST timeout, transport error or non-409 answer cannot fall through to `taskkill /T /F`. The uninstall failure stays recorded. A 409 refusal already forbids the forced path; this closes the remaining ones.
- **An absent Part A is not proof the proxy is down.** `windowsServiceRemovalStop` returned `ok` on Part A `absent` without checking the endpoint, and `findLiveProxy` answers null when its 3 s discovery cap runs out even while the endpoint is live. Removal now probes every candidate endpoint (the runtime record and the configured endpoint, the same set `ocx uninstall` proves, plus the resolved stop target) with the tri-state contract (`endpointLiveness`, the same one `endpointProvenDown` uses in `uninstall-stop` and `proxyEndpointProvenDown` in `src/cli/index.ts`); `proxyStillLiveAfterStop` looked down on a null, which its own probe produces on a timeout as well. Only `"dead"` on every candidate permits deleting the task — `"live"` refuses and `"unknown"` (a timeout or transport failure) refuses too, and both keep the receipt. No respawn hold is needed: a wait would price removal at Part B's 6 s for a manager that is not registered.
- **Uninstall's receipt names the endpoint its stop contacts.** `stopUninstallProxy` claimed the receipt first and resolved its target afterwards, and `defaultReceiptEndpoint()` marks any runtime record "exact" — so a stale record plus a proxy discovered on another port left a receipt for a port the stop never contacted, and a failed Part A with no proxy left a "guessed" obligation outstanding that recovery refuses. It now resolves the target first (the tracked pid with its own runtime endpoint, or the discovered live proxy's endpoint), claims only when a stop will be attempted, and hands the receipt and `stopProxy` the same endpoint. No target, no receipt.
- **An unconfirmed stop removes no tracked state.** The tracked-pid path called `removeTracked(pid)` regardless of the stop's result, so a failed stop deleted the record that a rerun needed. It runs only when the stop was proven, and the step reports `changed` only when state actually changed.
- **A forbidden forced fallback waits without killing.** With `allowForcedFallback === false`, `waitForStoppedPort` still called `reclaimListenPort` with `killOcxHolders`/`onlyKillPids: [pid]`, so the wait could kill through `killProxy` — the path the flag exists to close. The wait now runs observationally (the reclaim dependency is injected, and the forbidden case passes a mode that samples without kill eligibility); `stopProxy` keeps its literal `killProxy(pid)` call, which `tests/providers/xai/grok-lifecycle.test.ts` reads as order evidence.
- **A foreign WinSW registration survives `ocx uninstall`.** Two gaps: on Windows the "service removed" step called `uninstallServiceDetailed()` even when Part A failed to stop the manager, and the native branch stopped and deleted whatever carried the fixed `opencodex-proxy-native` ID — including another installation's service. Removal is now gated on a Part A that ended stopped or absent (`serviceRemovalAllowed`, Windows only; other platforms unchanged), recording `failed` otherwise so the shared teardown stays blocked as `ocx service uninstall` already refuses. Immediately before the native removal, `uninstallServiceDetailed` re-reads `sc qc` `BINARY_PATH_NAME` and compares it with this home's WinSW executable: foreign leaves the registration untouched, unreadable refuses and keeps install state.
- **Install preparation resolves the stop port before Part A.** `windowsServiceStopPort()` ran after the tracked cleanup had already removed the runtime record, so Part B confirmed the wrapper's baked port (10100) while the proxy's runtime port (12000) was never checked. `prepareServiceInstall` resolves the port once before Part A (`windowsStopPort` is the test seam) and carries it into Part B.
- **Part A proves the WinSW registration is this home's.** `sc query` answering "running" says a service exists under the fixed `opencodex-proxy-native` ID, not that it is this installation's. The live probe now reads `BINARY_PATH_NAME` through `sc qc` and requires this home's `winswExePath()`, the same proof `inspectWindowsWinswManager` uses; an unreadable registration is `unknown` (`evidence-unreadable`, nothing changed) and a foreign executable is reported as `nonexistent`, so Part A does not stop it and reports `absent`.
- **Install preparation claims its receipt before the stopped-Part-A stop.** Part A leaves the scheduler task registered, so the tracked stop's receipt-less POST answered `respawnable_service` (409), `stopProxy` threw, and the install aborted while the old proxy kept serving. `prepareServiceInstall` now claims a receipt carrying Part A's record before the stop and forwards its nonce. An install replaces the proxy, so shared config stays pointed at OpenCodex and `installServiceSafely` (and the fresh-scheduler path) clears the receipt only after the new service is installed and started; an install that fails after the stop keeps it for the next `ocx stop`. A failed claim sends no child stop.
- **An absent Part A still proves every endpoint down before install.** With no manager registered, Part B is skipped and the tracked stop can return `"none"` after its orphan-discovery cap while an unresponsive proxy still holds the port. `prepareServiceInstall` resolves `endpointsToProve(readRuntimePort(), loadConfig())` before cleanup and requires every candidate to be definitively dead; live or unknown throws like a Part B failure. The candidate and tri-state helpers live in `windows-service-stop.ts` so removal and install share them.
- **Windows removal probes before it deletes.** `uninstallServiceDetailed` deleted the scheduler task before reading the WinSW status and `sc qc` ownership, so an unreadable probe left a half-removed install with no task to retry from. Both probes now run first; unknown refuses with the existing error and removes nothing.
- **An unconfirmed uninstall stop asks the endpoint.** `stopProxy` answers false without contacting the endpoint when the tracked pid is already dead, so `confirmed(false)` reported `provenDown` with no endpoint check and a different proxy on the configured port was missed. The step now requires the tri-state `endpointProvenDown()` unless the forced fallback is forbidden, and still never forces.
- **Part B clears only the exited owner's TCP rows.** After a listener PID was found exited, the sampler called `dropWindowsTcpRowsForLocalPort(port)`, which resets every IPv4 row on the port — including rows of a program that took the port between scans. `parseTcpQuadsForLocalPort` and `dropWindowsTcpRowsForLocalPort` take an owner PID filter and the sampler passes the exited PID(s); the hard-kill path still clears the whole port.

## Open questions

- Is the closing-sample accounting acceptable, or should the hold be measured differently, for example by shortening the final enumeration to 4.5 s to keep 030's totals?
- WinSW-only stops enumerate and bind wrappers as well; the WinSW row includes the enumeration and termination window.
- `GetLastError` after a failed `OpenProcess` through Bun FFI separates "gone" from "denied". If the runtime clobbers it, the answer degrades to "unavailable" (`unknown`). The live x64 test in `tests/windows/windows-process-evidence.test.ts` checks this on the Windows CI lane.
