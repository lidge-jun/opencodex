# Single-branch releases from green dev commits

**Owner scope clarification, 2026-11-08:** retain the existing desktop signing,
notarization, MSI and updater flows for a reviewed commit reachable from `dev`.
Do not redesign their existing credential boundaries in this PR. Regressions
introduced by selecting a source or exposing secrets to unreviewed PR code remain
blockers. Authenticate the current npm channel floors and refuse ambiguous newer
evidence; do not require old legacy tags to match old npm `gitHead` values. Earlier
signing-redesign proposals below are historical and superseded by this decision.

Release preview and stable artifacts from a tested `dev` commit without moving a release branch or committing a version bump. Maintainers choose a channel and, optionally, an exact source SHA; the release workflow uses the current reviewed workflow revision to build that source, stamps the selected version in its temporary checkouts, and publishes a tag at the source commit. This removes release freezes while retaining explicit cross-platform, service, ordering, and publication checks.

**Work shape:** satisfy the release contract in one integrated change. **Trigger:** owner request on 2026-11-08. **Goal:** green-commit publication without a promotion PR. **Non-goals:** production publication, settings changes, or branch deletion. **Verifier:** focused release/CI tests, layout, ratchet and Lab guards, typecheck, structure and privacy gates, independent technical and security review, exact-head hosted CI, and an actual Actions dry run. **Stop:** deliver a reviewed PR and dry-run evidence; merge only after the owner's current no-regression gates pass and human maintainer change requests are resolved. Automated bot reviews are not merge gates. **Record:** this unit and the PR Verification section. **Terminal outcomes:** reviewed and validated change; or documented failing/missing evidence and a draft PR. **Escalation:** irreconcilable historical source lineage, permissions or cutover settings require a maintainer decision; never manufacture an attestation.

## Contract

1. **Green.** A qualifying run is this repository's `ci.yml`, `workflow_dispatch`, `head_branch=dev`, completed with conclusion `success`, full `lane=all`, and an exact full source SHA. Give full runs a machine-readable immutable run name or receipt that distinguishes the lane; reject missing, malformed, failed, cancelled, skipped, scheduled, PR, wrong-branch, and narrower evidence. Confirm the aggregate and required job graph succeeded. The lookup walks all relevant pages, not a fixed ten-run window. Select the newest qualifying commit by ancestry on current `origin/dev`; a supplied full SHA must itself qualify. Build the chosen SHA even if dev advances. Recheck eligibility immediately before publish.
2. **Lineage.** Fetch complete history and tag refs. Candidate must be reachable from current dev. Every new release must contain the most recently published source across channels; same SHA is allowed for preview-to-stable and a verified identical resume, otherwise older/divergent/unresolvable lineage fails. Legacy promotion commits need the explicit transition baseline above. Tag `v<version>` and GitHub release target the source SHA, not the workflow SHA. A release uses current reviewed dev workflow logic even when source is older; trusted guard scripts are also read from workflow revision. Hosted release runs from PR-controlled workflow revisions are prohibited.
3. **Versions.** The four committed sources are a consistent plain planned base. Candidate base is the higher of that base and the patch after the highest published stable; major/minor advances require a normal reviewed manifest edit. Stable is `X.Y.Z`; preview is `X.Y.Z-preview.YYYYMMDD.N` with UTC date and an ordinal that advances for that date. Check the global published version floor and npm dist-tags again at publish; a preview never sorts below an existing stable and neither channel can regress. Each build checkout runs sync then check before installation, building, signing or packaging; artifacts and receipts report the stamped version and source SHA. Update the dev version-line oracle so an intentionally unchanged base is valid after a release; retain checks against malformed or conflicting sources.
4. **Service.** Compare all lifecycle-sensitive paths from the last applicable reachable release baseline to the entire candidate tree; the initial baseline compares the complete tree. If changed, require a successful full Linux/macOS/Windows `service-lifecycle.yml` dispatch bound to the exact source SHA, not a PR run. Make dispatch accept a validated SHA independently of its workflow revision so a historical green candidate can be tested after dev moves; validate the exact tested SHA and job graph. Missing evidence fails with the command to obtain it. No dev push trigger is added.
5. **Serialization and recovery.** Preview and stable share the existing `release` concurrency group, with cancellation disabled. GitHub can replace a pending run; never claim FIFO or that an unstarted run published. Recheck registry state, version ordering, tags, source lineage, CI, service, and artifact receipt immediately before publication. Preserve dry-run behavior and immutable source/version/digest verification; a resume after npm publication must bind the identical source, version and registry `gitHead`, never republish npm, and never overwrite different release assets. Rerun failed jobs may reuse verified artifacts only while available; if proof is unavailable fail closed and document operator recovery. Recheck preview-versus-stable ordering under the shared lock.
6. **Branch and default policy.** Set `dev` as default only through coordinator action after landing and cutover checks. Retain `main` and `preview` as protected historical branches; do not automatically mirror `main`, because its protection and divergent promotion commits make a fast-forward unreliable. Retire them only after consumer inventory and separate authorization. Switch docs deployment to a manually dispatched stable-source build, preserving stable documentation without a branch push; verify Pages workflow and environment restrictions. Remove release-branch CI push triggers and the full nightly CI schedule: manual dev dispatch is the full cross-platform path; PR fast Ubuntu checks remain unchanged. Adjust service and catalog workflow triggers accordingly, with no dev push or PR macOS/Windows. Audit CodeRabbit, branch rulesets, required checks, `enforce-target`, issue/PR default-base behavior, workflow schedules, Actions default-branch availability, Pages, and release automation before requesting settings changes.
7. **npm identity.** Publish remains in `.github/workflows/release.yml`, job `publish`, `id-token: write`, with no GitHub environment. Coordinator must verify npm trusted publisher repository owner `lidge-jun`, repository `opencodex`, workflow filename `release.yml`, and no environment. Retain pinned actions and least-privilege permissions. No secrets are printed.

## Evidence authentication and credential boundary

- Pin the release workflow and its guard revision once for the run and retain it alongside the candidate source SHA. The trusted guard owns an explicit versioned policy allowlist for CI and service workflow policy: require the exact workflow path, source repository ID, workflow revision's blob hash, and policy version to match an approved entry. The policy fingerprint also covers all local helpers and actions that produce evidence or select required jobs, or executes those from an authenticated trusted revision; a matching YAML alone is insufficient. A future policy change updates that reviewed allowlist; an unknown revision fails closed. A title, job name, or artifact alone is never authentication. The run must be on `dev`, be a manual dispatch, and GitHub's run API must report the expected repository, workflow, head SHA, run ID, **actual attempt**, completion and success. Validate the jobs of that attempt, including every expected matrix leg and the aggregate result; fail on a missing or skipped required leg. The CI identity binds `lane=all` and tested SHA to this same attempt. Exercise forged titles, old policy revisions, altered helpers, wrong source repo and mismatched attempts.
- For service, the authenticated trusted workflow renders the validated full source SHA directly from its dispatch input into each platform job's GitHub job name before candidate code runs, then checks out that exact SHA on Linux/macOS/Windows. The verifier reads the GitHub run and attempt-specific jobs APIs, checks the approved workflow and helper policy, exact SHA-bearing names, each platform's success, and the full single-attempt graph. A candidate-generated receipt or run-scoped artifact alone is never proof of its producer or attempt; if API data cannot prove the binding, fail closed. Test changed inputs, stale/mismatched names, duplicate jobs, full and partial reruns and wrong workflow revisions. Never use a service run's workflow `head_sha` as its tested source when dispatching an older commit.
- Build and package candidate-controlled scripts and local actions without OIDC or write permissions; inventory every execution path including npm lifecycle hooks. The OIDC publisher consumes only a previously verified immutable package artifact and trusted workflow-revision guard, verifies source/version/digest, and invokes npm publication without executing candidate lifecycle scripts (for example publish the verified tarball with scripts disabled). Do not run candidate-controlled code after granting OIDC or GitHub write permissions. Verify packed metadata, npm `gitHead` and provenance really identify the selected commit using an actual dry run and subsequent publication checks; do not claim that dry-run alone proves registry provenance. Any unavoidable write-capable code must be separately documented and reviewed.
- Preserve the existing Apple, SignPath and updater signing paths and their existing
  credential boundaries. Only trusted, reviewed `dev` ancestors may be selected;
  a PR-controlled workflow must not gain access to release credentials. Independent
  security review checks whether the new source-selection flow worsens the existing
  boundary. Never print secret values.
- Production publish requires repository variable `OCX_DEV_RELEASE_PUBLISH_ENABLED` to equal exactly `true`; missing, empty or other values fail closed immediately before any irreversible publish. Dry runs do not require it and cannot publish. The coordinator alone enables or disables the variable after the post-merge dry run and settings checks, and verifies both missing/false refusal and true behavior using publication-disabled tests before enabling. This is an operational hold controlled by repository administrators, not a barrier against an administrator changing the variable or workflow.

## Independent plan audit amendments

The first independent plan audit returned FAIL with seven high-severity findings; all are accepted for the implementation and must be re-audited:

1. **CI attempts:** a qualifying attempt must contain the entire required graph in that same attempt. `Re-run failed jobs` is insufficient even if GitHub reports overall success; operators must select `Re-run all jobs` or start a new full dispatch. Tests distinguish full reruns from partial reruns and reject absent legs.
2. **Graph:** make a manual `lane=all` select a fixed, versioned list of required jobs and matrix legs regardless of path filters, while preserving fast PR behavior. Verify this specific graph against the authenticated policy and attempt; any required skip or missing leg fails. Test every fixed leg and PR exclusions. Do not claim a conditional graph is fixed without implementing and proving it.
3. **Resume identity:** a fresh dispatch derives a new version; a resume must instead supply the original source, channel and version plus a durable receipt identifying workflow/run, artifact digests and publication state. Validate receipt, registry package version and source identity, existing tag, release and assets before allowing the exact original tuple; only then bypass new-version derivation. Test failures after npm publication, tag creation and partial asset uploads, including missing/expired receipt and mismatched digest. An unverifiable case stops for manual reconciliation.
4. **Historical tag permissions:** before irreversible npm publication, verify that the selected credential can create a tag/release at a candidate whose workflow differs from default. The dry run must check the applicable capability without creating production tags or releases; a dedicated sandbox publication experiment is coordinator-authorized separately. If the GitHub token cannot do it, fail closed until the coordinator provisions a reviewed least-privilege GitHub App credential with only necessary repository contents/workflow permissions, or choose a documented safe alternative. Do not assume this credential or change settings.
5. **Untrusted dry runs and secrets:** do not dispatch hosted release workflows from a PR branch: branch-controlled YAML can request credentials regardless of its own conditions. The required hosted dry run runs only from trusted `dev` after merge; its source SHA is validated independently. Test a candidate changing workflow YAML and local helpers to request release secrets or write permissions; trusted-policy execution must refuse candidate policy and credential-bearing jobs must not execute candidate-controlled code. Production credential inventory includes Apple, SignPath, Tauri updater and notarization keys; isolated signing or an explicitly reviewed exception applies to all of them.
6. **Legacy cross-channel mapping:** inventory actual publication order, tag commits and source trees for both stable and preview before the first new release; the currently fetched `v2.99.0-preview.20261108` commit is not a dev ancestor. Record reviewed, narrow mappings for every legacy source that the cross-channel comparison actually requires; no one stable-only mapping silently exempts a later preview.
7. **Provenance experiment:** trusted verifier code comes from the pinned workflow revision, never the candidate checkout. The immutable package receipt binds source SHA, workflow SHA, run/attempt, version and tarball digest; publish verifies it before obtaining OIDC. Resume accepts only registry metadata identifying the exact package version and original source under an experimentally verified `gitHead` rule and an independently verifiable trusted-publisher provenance statement. Perform a safely isolated npm/GitHub publication experiment only with coordinator authorization, document observed metadata and credential limitations, and keep production disabled if exact source binding or provenance cannot be established. A local or hosted dry run alone cannot establish registry provenance.

**Second audit amendments:** npm's configured publisher has no environment restriction, and branch-controlled workflow YAML cannot protect secrets from a repository writer who can dispatch a modified `release.yml`. This design explicitly trusts such repository writers; the no-PR-dispatch rule is an operator policy, not an enforced credential barrier against them. The coordinator retains the existing no-environment publisher; a protected environment and a matching npm publisher configuration would be a separate coordinator-controlled hardening decision. CI/service job names and conditions also do not defend against an administrator or writer who can change the trusted policy allowlist.

The cross-channel publication floor includes acknowledged npm-only partial publications, not merely GitHub releases. Before new publication, reconcile the authoritative ledger against npm versions/dist-tags, successful and partially acknowledged prior release runs and retained authenticated receipts. Establish the original source, version and ordering from receipt and registry metadata; if an npm-only publication, missing receipt, uncertain ordering or unverifiable source prevents this, fail closed until the coordinator reconciles it. Test a newer npm-only publication followed by an attempt to publish an older source, including missing and forged receipts. The shared workflow lock and operator-controlled reconciliation are required for this ledger; GitHub release tags alone are not its authority.

## Cutover and rollback

1. Inventory the current stable and preview publication floors. The validator checks the fixed 2.99.0 legacy sources and dev baseline against exact SHAs and verifies that their trees differ only in the four expected version values; the evidence is recorded above. The mapping is narrowly scoped to those commits, not a general ancestry override. If the exact comparison or ancestry cannot be demonstrated, stop publication and reconcile the history. Subsequent releases require direct cross-channel ancestry.
2. Merge only after the owner's local validation, fresh independent technical and security reviews, required exact-head CI and resolved human maintainer change requests. Bot reviews and cosmetic or pre-existing findings are not merge gates. Hosted release dry-run is a documented pre-merge limitation: run it from trusted dev after merge. Keep production publishing disabled until that full post-merge dry-run and cutover checks pass.
3. Coordinator verifies npm publisher identity and inventories `dev` ruleset bypass actors, required check names, CodeRabbit, Pages environment/ref restrictions, branch targeting and default-branch-dependent jobs. Coordinator switches the repository default to `dev`; verify those settings and manual workflow availability before enabling release publication. If verification fails, leave publication disabled and restore the prior default/settings under coordinator control. The old workflow relies on the default branch's dispatch guard: it is a rollback option only after the coordinator restores the old default and verifies the old workflow, guard, CI/service evidence, npm identity and settings; do not assume it remains usable after switching defaults.
4. Manually dispatch one `lane=all` on dev and, when required, service lifecycle for that exact candidate; run the release with `dry-run=true`, inspect all artifact/platform verification and source/version receipts, and validate Pages by deploying stable-source documentation through its approved manual path. Only then enable normal release operation. If dry-run or Pages fails, keep the old release runbook and historical refs available; do not silently fall back to a weaker gate.
5. Preserve `main`, `preview`, old releases and tags until downstream consumers and recovery are audited. Disable redundant push/schedule triggers in the merged workflow rather than deleting branches. Resume requires the same source/version plus verifiable registry identity and artifact digests; if artifact evidence has expired or differs, stop and have the maintainer reconcile the partial publication instead of overwriting assets or republishing.
