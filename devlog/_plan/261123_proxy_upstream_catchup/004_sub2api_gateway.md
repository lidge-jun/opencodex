# 004 — sub2api gateway core (L4)

기준은 sub2api `328db26f450edbdf9f8d4344a3ea903ac6396842` (2026-11-20), OpenCodex `origin/dev` `9e0e298ef9720cfeaa1209f090a68e4d1965d2a1` (2026-11-21)이다. `s2a:`는 `.tmp/chase/sub2api/`, `ocx:`는 `.tmp/chase/opencodex-dev/`에서 읽은 소스다. 표의 판정은 해당 행의 동작 범위에 한정한다.

## 1. 요약

1. Codex와 Claude Code를 동시에 쓸 때 가장 직접적인 차이는 sub2api가 실제 동시 사용량과 대기열을 보고 계정을 고른다는 점이다. OpenCodex의 Codex·Claude pool 선택은 세션과 quota 정책을 우선하고, Kiro 경로에 계정별 lease가 있다.
2. sub2api의 일반 스케줄러는 가용 계정에서 priority, load, LRU를 차례로 적용한다. OpenAI의 queue·실패율·TTFT 가중 점수는 별도 설정을 켰을 때 쓰인다.
3. 두 프로젝트 모두 Codex와 Claude의 세션 affinity를 유지한다. Gemini에서 sub2api는 첫 사용자 입력을 포함하는 안정적인 prefix로 일반 요청을 묶고, 명시적 cache 리소스에는 생성 계정을 고정한다.
4. sub2api의 user slot은 같은 사용자의 여러 API key가 공유한다. 여러 사람이 proxy를 쓸 때 한 사용자의 fan-out이 다른 사람의 처리 용량을 잠식하는 문제에 대응한다.
5. HTTP SSE와 Responses WS 모두 계정을 바꾸기 전에 출력과 replay 상태를 확인한다. OpenCodex는 전송 결과가 불명확한 reset에서 명시적 허용과 self-contained 입력을 요구한다.
6. sub2api는 계정마다 upstream proxy를 선택한다. OpenCodex는 provider 단위 proxy를 제공하므로 같은 provider의 여러 계정에 각기 다른 네트워크 경로가 필요한 경우가 비교 대상이다.
7. 429의 적용 범위는 provider마다 다르다. Antigravity는 근거가 부족한 429로 한 요청이 계정 여럿에 냉각을 걸지 않도록 제한한다.
