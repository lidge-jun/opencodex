# 005 — sub2api 플랫폼과 OpenCodex의 팀 공유 기능

L5 · 2026-11-23 · sub2api `328db26f450edbdf9f8d4344a3ea903ac6396842` (2026-11-20, shallow) · OpenCodex `9e0e298ef9` (2026-11-21, origin/dev export). `s2a:`, `ocx:`는 각 스냅샷 루트 기준이다. 상태는 행에 정의한 기능의 범위에 적용한다.

## 1. 요약

- 소규모 팀의 공용 proxy에 가장 가치 있는 차이는 **발급 키별 소비 한도**다. sub2api는 누적 비용 및 5h/1d/7d 비용 window를 검사한다. OpenCodex의 기존 spend ledger는 workflow root와 upstream identity/pool을 기준으로 한다.
- **OpenCodex에 이미 키별 사용량과 모델 제한이 있다.** 관리자 `GET /api/usage?apiKeyId=…`, 키 목록의 요청 수, Hub 역할의 키 자체 집계, 최종 provider/model 기준 제한이 출발점이다.
- 단기 팀원·자동화에는 발급 키 만료가 유용하다. 회전 후보 secret의 만료와 발급 키 자체의 만료는 다른 수명주기다.
- 개인 사용자에게도 유용한 관측성은 실패·지연·429와 거절 이유다. OpenCodex에는 liveness/readiness와 인증된 metrics export가 있고 sub2api에는 내장 규칙·이벤트·silence가 더 있다.
- Codex Responses HTTP/WS와 Claude Code Messages/SSE에서 인증된 키 귀속과 종료 사용량 기록을 확인했다. 한도 설계에서는 타임아웃·재시도·종료에 따른 사용량 증거의 품질도 중요하다.
- 팀 관리 이력은 키 발급·폐기·스코프 변경의 구조화된 이벤트부터, 관리 MCP는 진단 읽기부터 고려할 수 있다.
- 사용자 계정 플랫폼, 상품·구독, 잔액 차감·결제·환불, 리딤, 공지, DB 설치 wizard와 Postgres/Redis 의무화는 단일 사용자 로컬 proxy 범위 밖이다.
