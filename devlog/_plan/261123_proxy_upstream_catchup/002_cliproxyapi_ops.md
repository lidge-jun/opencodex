# 002 — CLIProxyAPI 운영 계층 대조

## 1. 요약

- **Vertex 서비스 계정 gap은 닫혔다.** OpenCodex는 Vertex용 JSON 등록, OS credential store, OAuth JWT 교환 및 bearer 전송을 구현한다. 기존의 “key/ADC만” 분류는 ADC가 제공하는 OAuth 경로도 놓쳤다.
- **xAI OAuth는 양쪽에 있다.** CPA는 device flow, OpenCodex는 callback PKCE·device flow·기존 Grok CLI 세션 가져오기를 제공한다. xAI wire/WS/replay 판정은 L1 소관이다.
- **개인용 로컬 프록시에서 가장 구체적인 차이는 credential별 egress다.** CPA는 로그인 때 지정한 경로를 해당 credential에 보존한다. OpenCodex egress는 provider 단위다.
- **pool의 기본 전략과 quota failover는 이미 겹친다.** 같은 이름의 fill-first라도 CPA는 우선순위 후보 중 첫 credential을 사용하고, OpenCodex에는 소진 임계치와 quota window 방향을 반영하는 전략이 있다.
- **재시작이 잦거나 여러 명이 쓰는 프록시에는 cooldown 보존과 credential 진단이 유용하다.** CPA는 선택적으로 cooldown을 복원하며 management에서 auth별 모델·검증·refresh를 다룬다.
- **로컬 사용량 분석과 소규모 공유의 요구를 구분한다.** OpenCodex는 자체 usage ledger와 하위 client key 관리가 있고, CPA는 단기 소비형 usage queue와 plugin sink를 제공한다.
- **Home control plane, native plugin 배포, 외부 credential storage는 별도 운영 범위다.** 단일 로컬 설치의 추격 우선순위에는 넣지 않는다.

기준은 CPA `0d251842d2539194ebd55ef0cdcf9c08f9c4908a`, OpenCodex `9e0e298ef9720cfeaa1209f090a68e4d1965d2a1`이다. `cpa:`는 gitignored clone, `ocx:`는 `origin/dev` archive를 가리킨다. 비교 결과는 실행 검증을 포함하지 않는다. `OBSERVED-partial`은 양쪽 계약의 일부 또는 한쪽 구현만 읽은 행이다. 이 경우 상태는 `unknown`으로 유지했다.

## 3. 기능 인벤토리

### 요청에서 credential 선택까지 읽은 경로

- **Codex Responses.** CPA의 POST Responses는 non-stream에서 `ExecuteWithAuthManager`, SSE에서 `ExecuteStreamWithPreFTKeepAlive`로 들어간다. WS도 `ExecuteStreamWithAuthManager`를 호출하고 성공 상태의 auth를 연결에서 기억한다. 로컬 manager는 후보 credential을 선택하고 시도 결과를 `MarkResult`에 전달한다. OpenCodex의 POST와 별도 gate가 있는 WS는 모두 Responses 처리 경로에 들어가며, `resolveResponsesCodexAuth`가 route의 `codexAccountMode`를 account 선택에 전달한다. pre-output 거절은 Codex pool health에 반영된다. [cpa:sdk/api/handlers/openai/openai_responses_handlers.go:997,1087,1159; cpa:sdk/api/handlers/openai/openai_responses_websocket.go:456,652,1093–1095,1211; cpa:sdk/cliproxy/auth/conductor_execution.go:1230–1275,1452–1496; ocx:src/server/index/serve-options.ts:562–579,1411–1419; ocx:src/server/index/websocket-handler.ts:359; ocx:src/server/responses/core-auth.ts:234,309; ocx:src/server/responses/core-codex-account.ts:146–156]

## 5. OpenCodex 선행

- 내장 Kiro 로그인·adapter와 xAI OAuth flow 선택지가 `CAP-oauth-kiro`/`CAP-oauth-xai`의 관찰된 우위다.
- OpenCodex는 요청 이력과 관련된 downstream key ID rollup을 지속 ledger에서 제공한다. CPA의 관리 API key usage는 upstream auth bucket이다. 이 차이를 “CPA usage 없음”으로 표현하면 CPA의 plugin sink/queue를 누락하게 된다.
- reset-near weighted Codex/Anthropic 및 quota-based fill-first는 `CAP-credential-pool-weighted`의 operator 지정 static weight와 다른 기능이다. 로컬 계정 소진·재사용에 이미 쓰는 정책을 유지한 채 소규모 팀의 고정 배분을 검토할 수 있다.
