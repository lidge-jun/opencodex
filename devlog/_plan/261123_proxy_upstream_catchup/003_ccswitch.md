# 003 — CC Switch 클라이언트 전환과 로컬 라우팅 (L3)

## 1. 요약

- 비교 기준은 CC Switch `f19a9d4f4f08bda03106a7be87c77cbcdf55b019`과 OpenCodex `origin/dev` `9e0e298ef9720cfeaa1209f090a68e4d1965d2a1` export다. 아래 `ccs:`와 `ocx:`는 각각의 고정 트리를 가리킨다.
- Codex·Claude Code 사용자에게 우선순위가 높은 차이는 앱별 현재 목적지와 전환 결과를 한곳에서 보는 경험이다. CC Switch는 직접 연결과 로컬 라우팅의 선택을 별도로 유지한다. OpenCodex에는 이미 `sync`, 네이티브 토글, Claude 실행기와 설정 복구 경로가 있다.
- 직접 전환은 Codex의 TOML·인증·카탈로그, Claude의 JSON 키, Gemini의 dotenv·JSON처럼 클라이언트의 파일 계약을 따른다. 같은 파일을 여러 기능이 쓸 경우 공용 쓰기 조정과 중단 복구가 중요하다.
- 소규모 팀에는 키를 따로 넣는 공급자 가져오기와 설치 직후의 연결 진단이 유용하다. OpenCodex는 CC Switch 파일을 읽는 키 없는 미리보기를 이미 제공한다. URL 열기로 시작하는 공급자 가져오기는 별도 기능이다.
- CC Switch의 세션 기반 비용 집계는 프록시를 거치지 않는 실행까지 포함한다. OpenCodex의 프록시 사용량에는 이미 기기·요청 출처가 있으므로 두 데이터의 중복과 추정치를 표현하는 것이 선행 과제다.
- CC Switch의 WebDAV/S3는 관리 DB와 Skills 스냅샷을 복원한다. OpenCodex Remote Link는 Home과 Child의 라우팅·카탈로그를 맞춘다. 클라우드 백업과 팀용 라이브 라우팅의 필요를 각각 평가할 수 있다.
- Codex Responses WebSocket은 OpenCodex가 구현한다. CC Switch의 같은 경로에서 GET 업그레이드는 426을 반환하고 POST는 HTTP/SSE로 처리한다.

## 3. 기능 인벤토리

### 세 클라이언트의 종단 경로

**Codex.** CC Switch 앱 폼은 Codex 프리셋에서 config/auth를 구성하고 전환 시 `switch_provider` → `ProviderService::switch` → 장치의 direct/proxy 모드를 읽는다. Direct는 등록된 공급자와 이전 소유자에 따라 TOML 관리 키·공급자 표를 투영한다. `codex_direct`가 판정한 인증 동작, 카탈로그, 소유 기록을 파일 계획에 넣고 같은 작업에서 현재 포인터를 확정한다. `preserve_codex_official_auth_on_switch` 기본은 false이고, 보존을 켠 경우 기존 공식 로그인과 공급자 인증 위치를 분리한다. 이 구현의 실패 복구는 `mode/operation.rs`의 pending을 따라간다. `write_codex_live_atomic`에 있는 auth→TOML 실패 보상은 별도 helper다. `ccs:src/config/codexProviderPresets.ts:209`, `ccs:src-tauri/src/commands/provider.rs:198–240`, `ccs:src-tauri/src/services/provider/mod.rs:7544–7579`, `:7769–7804`, `ccs:src-tauri/src/services/provider/codex_direct.rs:393`, `:591`, `:1329–1396`, `ccs:src-tauri/src/settings.rs:775`, `ccs:src-tauri/src/codex_config.rs:853–902`.

OpenCodex `ocx sync`는 로컬에서 `syncModelsToCodex` → owned catalog refresh → `injectCodexConfig`로 간다. 외부 공급자나 사용자 소유 `openai_base_url`을 감지하고 보호하며, 표준 경로에서는 `openai`의 목적지와 catalogue 포인터를 관리한다. native 토글 기본값은 ON이고 역할 gate가 별도로 있다. 명시적 sync의 OFF 경로는 카탈로그만 갱신할 수 있다. `codex-shim install|status|uninstall` 및 기존 shim의 update 후 자동 복구도 별도 표면이다. 연결 모드의 `sync`는 Home catalog/설정 적용 경로를 택한다. `ocx:src/cli/dispatch.ts:418`, `:612–652`, `ocx:src/cli/sync-command.ts:52–123`, `:145–165`, `ocx:src/codex/desired-state.ts:63–85`, `ocx:src/codex/sync.ts:167–175`, `:231–236`, `:308`, `ocx:src/codex/inject.ts:194–273`, `:817–866`, `ocx:src/cli/codex-shim-autorestore.ts:52–64`.

**Claude Code.** CC Switch는 앱 프리셋을 선택한 뒤 같은 전환 IPC로 들어온다. Direct는 이전/새 카드의 관리 키만 교체하고 다음 공급자 포인터를 함께 반영한다. `settings.json`을 기본으로 선택하며 기존 legacy 경로를 고려한다. MCP는 `~/.claude.json`에 따로 투영한다. Proxy 모드에서는 필요한 클라이언트 계약만 갱신하고 라우트 포인터를 바꾼다. OpenCodex `ocx claude`는 기본으로 로컬 runtime을 준비하고 `ANTHROPIC_BASE_URL`, 인증 및 모델 슬롯을 자식 환경에 구성한다. 로컬 설정 또는 실행 중인 서비스의 Claude 토글이 꺼져 있으면 네이티브 실행으로 분기한다. 지속 파일 쓰기는 UI의 모델 기본값 preview→fingerprint apply 또는 별도로 활성화한 intercept의 소유 `env` 쓰기에 있다. `ccs:src/config/claudeProviderPresets.ts:77`, `ccs:src-tauri/src/config.rs:286–310`, `ccs:src-tauri/src/services/provider/mod.rs:7544–7579`, `:7740–7759`, `ccs:src-tauri/src/services/provider/claude_direct.rs:51`, `ccs:src-tauri/src/live/project/claude.rs:128–148`, `:250–258`, `ocx:src/cli/dispatch.ts:921–938`, `ocx:src/cli/claude.ts:247–297`, `:332–381`, `:849–879`, `ocx:src/server/management/agent-settings-routes.ts:1518–1538`, `ocx:src/claude/intercept/settings.ts:224–269`, `ocx:src/claude/intercept/runtime.ts:118`.

**Gemini CLI.** CC Switch Gemini 프리셋 → 선택된 카드 → `switch_normal`의 Gemini 분기 → `gemini_direct::switch_to`다. 제3자 카드는 설정과 API-key 요구를 먼저 검증하고 공식 카드는 Google OAuth 종류를 사용한다. `.env`의 Gemini 목적지/인증/모델 키와 `settings.json`의 `security.auth.selectedType`, `model.name`을 따로 계획한다. dotenv와 JSON의 주변 값을 보존하면서 두 파일과 현재 포인터를 같은 pending 작업으로 반영한다. Gemini 모드를 라우팅으로 전환하면 `/gemini/v1beta/*path` 등 로컬 HTTP로 들어온다. OpenCodex에서는 Gemini wire와 업스트림 OAuth 및 Agy connector가 각각 등록돼 있다. Gemini CLI의 이 두 파일을 프로젝션하는 진입점에는 아래 `GEM` 영수증을 적용했다. `ccs:src/config/geminiProviderPresets.ts:36`, `ccs:src-tauri/src/services/provider/mod.rs:7616–7619`, `ccs:src-tauri/src/services/provider/gemini_direct.rs:38–113`, `ccs:src-tauri/src/live/project/gemini.rs:19–45`, `:131–135`, `ccs:src-tauri/src/proxy/server.rs:428–431`, `ocx:src/server/index/gemini-routes.ts:59–94`, `ocx:src/integrations/gateway-clients/index.ts:14–19`.

## 5. OpenCodex-ahead 항목

- **확정 `CAP-wire-responses-ws`.** OpenCodex는 native WebSocket upgrade와 메시지 처리를 제공한다. CC Switch의 등록 handler는 426 응답으로 HTTP/SSE fallback을 유도한다. `ocx:src/server/index/serve-options.ts:560–600`, `:1924`, `ocx:src/server/index/websocket-handler.ts:359`, `ccs:src-tauri/src/proxy/handlers.rs:1125–1139`.
- **OpenCodex에서 관찰한 확장.** SSH Home/Child lifecycle, 실행 중인 서비스의 route intent 및 카탈로그/설정 sync는 cloud snapshot과 별도 용도를 해결한다. `CAP-fleet-link`는 CC Switch 등록 범위의 대응 기능 유무를 전수 검증하기 전까지 `unknown`이다. `ocx:src/cli/sync-command.ts:60–123`, `ocx:src/link/supervisor.ts:272–299`.

## 7. Deferred checks

- 나머지 13종 클라이언트의 전환 전후 원문 비교, vendor별 최초 입력/설정 경로 override, Windows/WSL/portable 권한·파일 잠금, tray와 CLI의 동일 상태 전이. OpenCode는 V1/V2 추가와 OMO 입구까지 비교했다.
