# 052 — i3152: dashboard log panel jittering

One issue, one cycle.

## What #3152 reports

Dashboard 2.39.0, viewed on Windows 11. The Logs table "quivers" — and the report contains
the two observations that identify the mechanism:

1. **It jitters when scrolled to the top** and stops after scrolling down a little.
2. **At a certain scroll position the layout alternates** between two states (images 1 and 2).

The reporter noted the jitter could not be screenshotted and photographed the screen instead,
which is itself a signal: it is a per-frame oscillation, not a static misalignment.

## Mechanism

The Logs table is virtualized (`useVirtualizer`, `gui/src/pages/Logs.tsx:522`) inside a real
`<table>` using **automatic** table layout — `table-layout` is set nowhere in `gui/src`
except one unrelated file, so `.tbl` (`styles.css:1026`) inherits `auto`.

Under auto layout the browser computes column widths from the **content of every row in the
table**. The virtualizer renders two spacer rows to represent the off-screen extent:

    {paddingTop > 0 && (
      <tr><td colSpan={10} className="logs-virtual-spacer" style={{ height: paddingTop }} /></tr>
    )}

That is the feedback loop:

1. The virtualizer measures each rendered `<tr>` via `ref={rowVirtualizer.measureElement}`.
2. Measured heights change the padding spacers.
3. The spacers are table rows, so changing them re-runs auto column-width computation.
4. New column widths change how cells wrap — the model column is `max-width: 16ch` with
   `overflow-wrap: break-word` (`styles.css:1985`), so a width change alters row **height**.
5. Changed heights feed back into step 1.

## Why the top specifically

At `scrollTop === 0` the `paddingTop > 0` guard is false, so the leading spacer row is
**removed from the table entirely**. Removing a row changes the set of rows auto layout
considers, which shifts column widths — and the shift re-triggers measurement, which
re-adds the row. That is the oscillation the photograph captured, and it explains why
scrolling down a little stops it: past the top, `paddingTop` stays positive and the row set
is stable.

The "layout changes between image 1 and 2 at a certain scroll position" is the same effect at
the boundary where a wide model name enters or leaves the rendered window.

## The fix

Pin column widths so row content cannot feed back into column geometry:

**MODIFY `gui/src/styles.css`** — give the virtualized logs table fixed layout:

    table.logs-table {
      width: 100%;
      min-width: 1100px;
      table-layout: fixed;   /* NEW */
    }

`table-layout: fixed` computes widths from the first row and the explicit column
constraints only, so neither the spacer rows nor a long model name can move a column. Every
`log-col-*` rule already carries `min-width`/`max-width`, so the columns have the
constraints fixed layout needs.

Scope: `table.logs-table` only. `.tbl` is shared by every table in the dashboard and must
not change — those are not virtualized and rely on auto sizing.

## TESTS

`gui/tests/` — a jsdom test cannot observe browser layout, so the honest regression is a
**contract** test: assert the virtualized logs table declares fixed layout, with the reason
in the assertion message. That is what keeps a later edit from silently restoring `auto`.
