## Changes

### T1 identity: fixture and Windows separator equivalence
Product (src/update/orchestrated-identity.ts): on win32, `/` and `\` are the same separator. Compare the rebuilt `join(root, "src", "cli", "index.ts")` against the source with only its separators normalized (`process.platform === "win32" ? source.replace(/\//g, "\\") : source`). Do not apply `normalize()` here, because it would also collapse `.`/`..` segments and duplicate separators, and those should keep failing closed. `servingRoot` stays `realpath(root)`, which is native on every platform. Every other rule stays as it is: the absolute-path check, the length bound, the exact `src/cli/index.ts` suffix, attestation, and the record-unchanged check.
Test (tests/update/update-orchestrated-identity.test.ts): build the fixture with `node:path` under `const fixtureRoot = process.platform === "win32" ? "C:\\fixture" : "/fixture"`, and expect `servingRoot: join(fixtureRoot, "install")`. Add assertions to the same test: a mismatched suffix (`.../src/cli/other.ts`) and a dotted source (built by string concatenation so `join` cannot collapse the `..`: `<root>/install/src/x/../cli/index.ts` with native separators) return `unknown` on every platform. On win32 only, the same native path written with `/` separators returns `live` with the same `servingRoot`, which is the regression for the product change. These win32 assertions run on Windows CI. On macOS the separator form cannot be expressed, and `.tmp/research/win32-identity.ts` is the reasoning aid. Update structure/ops/service-and-sidecars.md (the orchestrated-identity sentence) to say Windows separators are treated as equivalent.

### T2 Bun lease fixture (tests/helpers/update-bun-ownership-child.ts)
In the `spawnSync` mock, recognize the Windows bridge: `args[0] === "--input-type=module" && args[1] === "-e"`, with `options.input` parsing to `{ invocation: { file, args }, timeoutMs }` whose `invocation.args` names `@bitkyc08/opencodex`. Validate it the same way the POSIX supervisor request is validated (marker `update-orchestrated.json` in phase `mutating` for this pid, when the POSIX branch requires it), classify it as `replacement`, and return `{ status: 0, stdout: JSON.stringify({ status, processTreeExited: true }) }`, using the same per-scenario installer `status` as the POSIX supervisor. For `supervisor-unconfirmed`, return empty stdout so the bridge reports unconfirmed, matching the POSIX branch. An unrecognized bridge shape throws instead of being classified `ancillary`. The test file itself does not change. Real Windows Job Object coverage of the bridge (confirmed failure, unconfirmed exit) is out of scope here because a mock cannot prove it, and is recorded as a follow-up. structure/ops/update-supervised-recovery.md is updated if its description of this fixture names the POSIX-only supervisor.
