# 원격 연결(허브·클라이언트 링크) PRD — r2

상태: Plan r2 (Interview r1 + r2 사용자 결정 반영). Luna Mind 3개(contrarian, simplifier, ontologist, 모델 gpt-6-luna) 반대 관점 검토 반영. auto 모드라 사용자 답변 없이 에이전트가 기본값을 골랐다. U1은 사용자 확정, U2·U3은 기본값(열린 가정). 구현 전 문서.

## 문제

`http://localhost:10100/#remote`는 허브 모드가 아니면 "허브 모드에서 OCX_REMOTE_WORKSPACE_ENABLED=1로 허브를 시작하면…" 경고만 보여 준다. 여러 컴퓨터를 한 OpenCodex 설정으로 묶으려면 지금은 CLI로 `runtimeRole`, HTTPS `hub.managementPublicOrigin`(Tailscale Serve 등), `hub.dataPublicOrigin`, `corsAllowOrigins`를 맞추고 `ocx hub invite` → 상대 기기에서 `ocx connect`를 쳐야 한다. Codex 앱의 원격 호스트처럼 화면에서 고르고 끝나는 흐름이 없다.

## 목표

- G1 허브 컴퓨터의 `#remote`에서 스위치를 켜고, SSH로 로그인되는 기기를 골라 클라이언트로 붙인다.
- G2 양쪽 모두 사용자가 보는 포트는 10100이다. 클라이언트의 Codex는 계속 `localhost:10100`을 본다.
- G3 사용자는 토큰을 보거나 입력하지 않는다. 내부적으로는 클라이언트별 키가 자동 발급·저장되고 허브 목록에서 회수할 수 있다.
- G4 연결 중 클라이언트 설정(서비스 토큰, 카탈로그, Codex 라우팅)은 바뀌고, 연결을 해제하면 연결 전 상태로 정확히 복구된다. (r0의 "설정 파일이 안 바뀐다"는 기존 connect 동작과 맞지 않아 폐기)
- G5 적용 후 수동 새로고침 없이 양쪽 화면에 연결 상태가 뜬다.

## 결정 (r1)

| ID | 결정 | 바뀐 이유 |
|---|---|---|
| D1 | 코드 용어: 역할 hub/client, 새 연결 방식은 `link`(transport `ssh`). 코드 식별자에 home 금지. 링크를 여는 기계의 runtimeRole은 바꾸지 않는다(hub 승격 시 자기 Codex 동기화가 꺼짐, src/codex/desired-state.ts:80). 화면 용어는 r2 U3 | ontologist: home 충돌 |
| D2 | `#remote` 첫 화면은 흑백 꺼짐 스위치 + 흐린 미리보기. 경고문은 원격 워크스페이스 안으로 한정해 유지 | ontologist: 실제 전제 조건을 숨기지 않기 |
| D3 | 두 흐름 모두 v1. 허브 시작: 허브 대시보드(변경 허용)가 SSH로 클라이언트의 `ocx` CLI를 실행. 클라이언트 시작(D3b, 스택 맨 위): 연결 전 standalone 클라이언트 대시보드가 SSH로 허브의 `ocx link issue`를 실행하고 -L 터널을 소유 | 연결된 클라이언트 대시보드는 변경 불가(machine-listener.ts:110-123). CLI 실행이면 기존 보안 규칙 준수 |
| D4 | SSH는 시스템 OpenSSH, 키/agent만, BatchMode. 모르는 호스트 키는 "연결 테스트" 단계에서 지문을 보여 주고 확인 후에만 known_hosts에 기록 | simplifier: 단계 수에 포함 |
| D5 | 허브가 `ssh -N -R 127.0.0.1:<P>:127.0.0.1:<L> <client>`를 소유. P=클라이언트 쪽 터널 포트(자동 할당), L=허브 링크 리스너 포트 | contrarian: 명령 형태·바인드 명시 |
| D6 | 허브 링크 리스너: 127.0.0.1:L, `/v1/*` 데이터 경로만, 클라이언트 키 필수(루프백 신뢰 미적용), 관리 API·GUI·세션 부트스트랩 없음. 링크가 하나 이상일 때만 활성(코어 경로 비활성 규칙) | contrarian: 관리 부트스트랩 차단 |
| D7 | 페어링 코드 없이 허브가 관리자 권한으로 클라이언트 키를 직접 발급하고, SSH stdin으로 `ocx connect --link --key-stdin --server-url http://localhost:<P>`에 넘긴다 | contrarian: 임의 포트와 페어링 origin 규칙 충돌 회피 |
| D8 | 클라이언트 10100 machine listener가 link 모드에서 `/v1/*`를 `localhost:<P>`로 중계. Codex 라우팅 대상은 `http://localhost:10100` 유지 | G2 |
| D9 | link 모드 클라이언트 대시보드는 읽기 전용 연결 상태만 보여 준다(허브 관리 화면 중계 없음). 해제는 허브 목록 또는 클라이언트에서 `ocx disconnect` | ontologist/simplifier: 권한 모델 일치 |
| D10 | 채널 이름 고정: inference(클라이언트 10100 → 터널 P → 허브 L), local GUI(클라이언트 10100, 읽기 전용), control(허브 → SSH exec, 설정·해제·상태) | ontologist: 채널 혼동 |
| D11 | 클라이언트에 ocx가 없거나 버전이 낮으면 "막힘" 상태와 설치 명령을 보여 준다. 원격 자동 설치는 v2 | simplifier |
| D12 | 후보 호스트: ~/.ssh/config의 구체 Host + 설치돼 있으면 Tailscale 피어. 목록은 후보일 뿐, SSH 프로브(키 로그인 + 호스트 키 + 원격 ocx 버전) 통과 후 선택 가능 | contrarian |
| D13 | 상태 기계: connected → reconnecting(요청은 503 + Retry-After, 앰버) → failed(인증 실패나 5분 초과, 빨강, 조치 필요) → connected. 조용한 로컬 provider 대체 금지 | contrarian/simplifier: D12·S5 모순 |
| D14 | 터널 수명은 허브 서버 프로세스 소유. 허브 기동 시 저장된 링크를 다시 연다. 허브 재시작 중에는 클라이언트가 reconnecting | contrarian: 재시작과 터널 |
| D15 | 허브 쪽 적용은 재시작 불필요(링크 리스너 지연 활성). 클라이언트는 `ocx connect`가 자기 서비스를 재시작 | S2 단순화 |
| D16 | 원격 워크스페이스는 기존 컴포넌트 그대로 별도 경로로 두고, 사용 가능할 때만 내비게이션에 노출 | simplifier/ontologist: 범위 밖 유지 |
| D17 | v1 플랫폼: 허브·클라이언트 모두 macOS/Linux. Windows 클라이언트는 후속 | 서비스 수명 미검증 |
| D18 | 링크 추가·해제·키 발급은 허브의 정식 대시보드 세션만. Tailscale 신원 세션(읽기 전용)은 불가 | 기존 규칙 |

## 성공 기준

- S1 허브 화면에서 클라이언트 추가가 호스트 선택 → 연결 테스트(지문 확인 포함) → 변경 내용 확인 → 적용, 4단계.
- S2 적용 후 허브 목록은 15초 안에 connected. 클라이언트 대시보드는 재시작 후 자동 재연결해 상태를 보여 준다. 세션이 끊기면 루프백 재부트스트랩으로 복구(검증 항목).
- S3 클라이언트 Codex 요청이 사용자 토큰 입력 없이 허브 provider로 처리된다.
- S4 해제 후 클라이언트의 서비스 토큰·카탈로그·Codex 설정이 연결 전과 같다.
- S5 네트워크 단절 후 백오프로 재연결되고, 단절 중 요청은 503으로 실패한다.
- S6 모르는 호스트 키는 확인 없이 저장되지 않는다(테스트).
- S7 터널로 들어온 요청은 관리 API·GUI·세션 부트스트랩에 닿지 않는다(테스트).
- S8 링크가 없는 설치에서는 링크 코드가 로드되지 않는다(코어 경계 테스트 확장).

## r2 사용자 결정 (2026-09-25)

- U1 → 좁히지 않는다. 허브 시작 흐름과 클라이언트 시작 흐름을 모두 만들고, 스택 PR로 쌓는다. 클라이언트 시작 흐름은 스택 맨 위 레이어.

- U2 → 답 없음. 기본값 D9(link 모드 클라이언트 대시보드는 읽기 전용 상태) 유지.
- U3 → 답 없음. 화면: 한국어 "홈 / 자식", 영어 "Home / Child". 코드: hub / client / link (D1).

## 버전 구분

- v1(이번 스택): SSH 링크, 허브 시작 + 클라이언트 시작, macOS/Linux.
- v2: 원격 ocx 자동 설치, Windows 클라이언트, 비밀번호 SSH 여부 재검토.
- v3: 허브를 공개 HTTPS 앞단(Cloudflare Tunnel + Cloudflare Access, 일반 리버스 프록시)으로 노출하는 연결 방식.
  - 지금도 `hub.managementPublicOrigin` / `hub.dataPublicOrigin`은 특정 서비스에 묶이지 않은 HTTPS origin이라, Cloudflare Tunnel 앞단은 기존 초대 흐름(`ocx hub invite` → `ocx connect`, 클라이언트별 키)으로 수동 구성할 여지가 있다. 실제 동작은 검증하지 않았다.
  - 자동 신원 세션은 Tailscale 전용(`Tailscale-User-Login`, src/server/gui-session.ts)이다. Cloudflare Access의 `Cf-Access-Jwt-Assertion`을 신뢰하려면 JWT 서명 검증, 팀 도메인·audience 설정이 필요하고 인증 경계 변경이라 보안 검토 대상이다.
  - ocx 자체를 Cloudflare Workers에 배포하는 것은 범위 밖이다. Bun 런타임, 하위 프로세스, 로컬 자격 증명 저장소에 의존한다.
