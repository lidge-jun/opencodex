# Link WebSocket: what opening the Child gates still needs

Both Children can carry Codex's Responses WebSocket over a Remote Link, and both ship with that path switched off. The TypeScript Child (`src/client/link-websocket.ts`, merged as #8614, #8619, #8620 and #8658) waits on `linkWebsocketChildReady()`; the lightweight `ocx-child` (`native/ocx-child/src/link_ws*.rs`, merged as #8653) waits on its own gate, which no build without the `link-ws-test-gate` Cargo feature can open. The Home side (#8593) has its own release gate. `structure/remote-link.md` describes what holds today. This unit lists what the change that opens each Child's gate still has to carry, so none of it is lost between that change and the reviews that found it. Nothing here is implemented yet.

## ocx-child

1. **Control-frame deadline.** Every frame write registers an absolute deadline before it takes the leg's write lock: 600 s for data, 30 s for a pong or close. A pong that waits behind a long data write on the same leg can therefore reach its 30 s deadline while the data write is healthy, and the reaper then cuts the socket. A close cannot: every close write follows a close bound of at most 5 s (1 s on a stop), registered in the same state-lock section that starts the terminal transition and kept while close I/O is in progress, so the reaper cuts through that bound before a close's own 30 s deadline. A waiting pong should inherit the remaining deadline of the write holding the lock, or the Child should answer only the latest ping. The Home's link socket sends no pings (Bun `idleTimeout: 0`), but the worker answers a ping from Codex on Codex's leg, whose write lock the Home reader holds during Home-to-Codex data writes of up to 600 s, so a ping from Codex meets the same limit. Nothing in this repository shows whether the pinned codex-rs (88c5856) sends pings: check it with the pinned binary before the gate opens.
2. **Reaper wakeups.** Each frame write registers and clears a reaper deadline, which wakes the reaper twice per frame. Optional; measure first.
3. **Autobahn.** Run the Autobahn suite against the frame reader in both roles (`link_ws_frame.rs`).
4. **Memory.** An RSS acceptance against the 32 MiB reservation per socket, with maximum-size messages in both directions at once.
5. **Pinned Codex.** Run the release-gate scenarios with the pinned codex-rs (`tests/fixtures/link-gate-codex.json`) through `ocx-child`.
6. **Split `link_ws.rs`.** A pure-move split of the module (handshake and headers; registry and reaper; the socket, frame writes, terminal transition and pumps; open, serve and stop; tests into `link_ws/tests.rs`), with no behaviour change, before the gate opens.
7. **Child-local opt-out.** The TypeScript Child reads `linkResponsesWebsocketOptOut` (owner decision D4); `ocx-child` needs the same, read once when `serve` starts and checked before the advertisement, with a way for the Home or an operator to set it.
8. **Platforms.** macOS and Windows runs of the crate and the real-binary tests. In the full cross-platform run on dev `726bd713a6` (run 43413601225, hosted runners), macOS passed both Cargo wrapper tests (`link-ocx-child-ws-gate` in 18 s, `link-ocx-child-ws-feature` in 5 s). On Windows the crate built (about 30 s) and the `link_websocket` integration target did not finish inside the wrapper's 100 s bound. The log kept only Cargo's stderr, so which case hung is unknown; the gate file did not appear in any Windows shard's log. Both Cargo wrapper tests now skip Windows (`ocxChildLinkWsCargoSkipped`), as `link-ocx-child-e2e.test.ts` already did. Only the run with the feature was seen to hang; skipping the gate file's run without the feature there is a precaution, not an observed failure. The gate it proves is a compile-time cfg, the same on every platform, and Linux and macOS keep proving it. The conformance Cargo run (`link-ocx-child-conformance.test.ts`) still builds and runs ocx-child on Windows and passed in that run. The wrapper now also reports libtest's stdout when the bound ends a run. The harness in `native/ocx-child/tests/link_websocket.rs` waits without a bound in several places (the Codex-side socket reads, the mock Home's close channel, the relay's exit after the attested shutdown), so a difference on Windows hangs instead of failing. The link WebSocket ends sockets by `shutdown(Shutdown::Both)` on a cloned socket to wake a read or write blocked in another thread; whether that wakes such a call on Windows has not been verified. Making ocx-child's link WebSocket work, and tested, on Windows is part of this item.
9. **User docs.** The guide pages that describe the link WebSocket on a lightweight Child, with the Spanish mirror rule.
10. **CI path filter.** `tests/fixtures/link/link-ws-state-proof.json` is outside the Rust CI path filter in `.github/workflows/ci.yml`, so a change to the vectors alone does not run the Rust tests. Add it the next time `ci.yml` is edited (an edit needs the release-evidence re-pin).
11. **No answer yet means try.** `ocx-child` tries an upgrade only when the Home's "on" has been applied for the current link (`link_ws_advert::advertised`, checked on the relay's WebSocket route in `relay.rs`), so a freshly started or newly linked `ocx-child` answers 426 until a preflight teaches it, and Codex then stays on HTTP for that session. The TypeScript Child's rule, landed in #8682, is to try when no answer has been applied since start, letting the upgrade's own preflight decide, while a closed gate, the opt-out and (outside a restart drain, where it gets the transient 503) a cached off keep the 426 with no network traffic. `ocx-child` needs the same rule, with the same tests.

## TypeScript Child

1. **Gate preconditions.** The framer's client conformance run and the Child's memory acceptance, which `linkWebsocketChildReady()` names as its own preconditions.
2. **Pinned Codex.** The reviewed digest in `tests/fixtures/link-gate-codex.json`, then a release-gate run with the pinned codex-rs.
3. **A real Child restart.** Measured with the pinned codex-rs (88c5856): a 503, a refused WebSocket connection and an upgrade closed before its 101 all spend the same stream retry budget, after which the session moves to HTTP for good. After a cut mid-turn, Codex keeps retrying on the WebSocket for about 1.4 s at 3 retries, the gate's setting (`stream_max_retries = 3` in the Codex provider config that `runGateCodex` in `tests/helpers/link-gate-codex.ts` writes for the gate runs), and about 6.0 s at 5, Codex's default (`codex-rs/model-provider-info/src/lib.rs` at 88c5856); only a request already on HTTP retries a refused connection without limit. Today the old listener can stay bound for up to the 5 s TERM window while the tunnel supervisor stops, so at the gate's 3 retries a restart ends the running turn's WebSocket session unless the replacement is accepting within that budget. Closing the listener when the drain starts changes no turn's transport. After the drain the window is refused connections: the restart controller (`src/client/runtime-restart.ts`) spawns the replacement `ocx start` only after the old listener's drain has ended, while Bun 1.4.4 releases the listening socket as soon as `server.stop(false)` is called (a connect is refused, and a second listener can bind the same port while the first still drains), so connections are refused from that call until the replacement binds. That window is not measured yet. Two ways to shorten it, to choose once it is measured: spawn the replacement as soon as the old listener stops accepting and let the drain continue alongside it (the success path and a rollback then wait for the drain), which removes the drain time but not the replacement's start; or start the replacement before anything stops and let it wait for the port, as `bindClientListener` already does, which leaves about one 100 ms poll but changes the order of the restart contract. Until one of them is built and measured, the claim at the gate's 3 retries is: a Child restart ends a running turn's WebSocket session unless the replacement accepts the upgrade within that budget, and Codex then sends that turn over HTTP instead. Codex retries a refused HTTP connection without limit, but an attempt that still reaches the old listener during the tunnel stop gets the relay's 503 `home_unreachable` with Retry-After, and how Codex retries that 503 over HTTP was read from the Codex source at 88c5856, not measured: Codex retries such a 503 at the request level and then the turn level, waiting for Retry-After each time, and fails the turn once both budgets run out, and a 5 s window fits inside that budget both at Codex's defaults (5 turn-level and 4 request-level retries) and at the gate's settings (3 and 1); so the request reaches the replacement only if those retries outlast the old listener's 503s, and whether it then completes depends on the replacement's tunnel and the Home, as for any relayed HTTP request. A later session can return to the WebSocket when the replacement's cache holds on for the link, or no answer yet under item 4's rule (landed in #8682), and that upgrade's own preflight answers on.
4. **The first upgrade after a restart.** A restarted Child starts with the Home's advertisement unknown, and nothing teaches it before the listener accepts; after that, any preflight can bring the first answer, for example a relayed request, an upgrade's own preflight, the parity report, the `/readyz` readiness probe or the route-intent watch's first poll once the tunnel is up. Since #8682 landed, an unknown state tries and the upgrade's own preflight decides; the opt-out and, outside a restart drain where it gets the 503, a cached off keep the 426 with no traffic. Measured with the pinned codex-rs (lane G, #8681, which already runs these restart scenarios under #8682's rule, through test seams: the restart is modelled in process and the rule runs through the relay's default path): this rule keeps the turn on the WebSocket whenever the restart fits the remaining budget (every 1 s restart, and a 5.5 s restart at 5 retries). Left for the gate-opening change: the same scenarios through the real runtime's supervisor, which #8681 does not drive.
5. **Diagnostics table.** Show the `link_ws_*` events (open, close reasons, fallback reasons including `draining`) in the dashboard's diagnostics table.
6. **Wording and counting.** Three comments in `src/client/link-websocket.ts` (on the `HomeLeg` class, in `finish`, and at the failed `server.upgrade` in `upgrade`) still say a failed local upgrade counts nothing; one that threw after Bun had opened Codex's socket also counts as a stop, as the comment on `abandon` and `structure/remote-link.md` already say. The comment in `localGone` says a 1006 is counted as the Home counts the same socket, which is wrong for Bun's own oversized-message 1006: the Home receives 1011 and counts it complete. The Child counts a 1015 close as complete where the Home's rule (#8647) does not: `finish("client", code !== 1006 && code !== 1015)`, with a test.
7. **Platforms and docs.** macOS and Windows runs, and the user guide pages, with the Spanish mirror rule.

On 2026-11-13 the owner decided that the design's 9.2 controlled validation and the U15 measurement are skipped and not measured; any text that opens a gate must say so.
