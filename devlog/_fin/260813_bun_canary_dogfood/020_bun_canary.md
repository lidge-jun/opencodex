# WP-1B — Bun Canary Installation and Reproducible Pin

## Goal

Install the latest Bun canary into the user's Bun installation, capture its exact semantic version and source revision, represent that runtime reproducibly in the root package metadata, regenerate `bun.lock`, and prove TypeScript compatibility before any memory patch is attempted.

Canary is moving and officially untested. Never write `"canary"`, `"latest"`, or an assumed future version into `package.json`.

## Step 1 — Install canary exactly as requested

```bash
cd /Users/jun/Developer/opencodex

curl -fsSL https://bun.sh/install | bash -s "bun-canary"
export PATH="$HOME/.bun/bin:$PATH"

command -v bun
bun --version
bun --revision
```

If the installer rejects `bun-canary`, do not retry arbitrary labels. Use the official two-step equivalent and record the deviation:

```bash
curl -fsSL https://bun.sh/install | bash
export PATH="$HOME/.bun/bin:$PATH"
bun upgrade --canary
bun --version
bun --revision
```

Capture immutable values without reusing common shell/system variables:

```bash
BUN_CANARY_VERSION="$(bun --version)"
BUN_CANARY_REVISION="$(bun --revision)"
test -n "$BUN_CANARY_VERSION"
test -n "$BUN_CANARY_REVISION"
printf 'version=%s\nrevision=%s\n' "$BUN_CANARY_VERSION" "$BUN_CANARY_REVISION"
```

The revision, not merely the semantic version, is the dogfood identity.

## Step 2 — Prove npm package availability before editing

The root manifest currently pins both `bun` and `@types/bun` to `1.3.14`. The requested target is the exact installed canary version for both packages. Verify that those versions exist:

```bash
npm view "bun@${BUN_CANARY_VERSION}" version --json
npm view "@types/bun@${BUN_CANARY_VERSION}" version --json
```

Both commands must print exactly `BUN_CANARY_VERSION`. If either returns `E404` or a different version, stop WP-1B. Do not:

- use a stale npm `canary` dist-tag;
- pin the binary package to one version and types to 1.3.14 while claiming parity;
- fabricate an `@types/bun` version;
- regenerate the lockfile from an unresolved manifest.

Escalation options, requiring maintainer choice, are:

1. Keep `@types/bun` at the newest published compatible version and document intentional runtime/type skew.
2. Replace `@types/bun` with a verified Bun-provided types source at an immutable commit/tarball.
3. Delay the package pin and run the canary only through `OPENCODEX_BUN_PATH` as a local experiment.

This roadmap recommends option 3 until an exact types package exists because it keeps committed dependency metadata honest.

## Step 3 — Exact `package.json` diff when both packages exist

File: `/Users/jun/Developer/opencodex/package.json`  
Operation: MODIFY

Apply only after Step 2 succeeds. Substitute the captured literal version; do not leave the shell placeholder in JSON.

```diff
@@ dependencies
-    "bun": "1.3.14",
+    "bun": "<BUN_CANARY_VERSION>",
@@ devDependencies
-    "@types/bun": "1.3.14",
+    "@types/bun": "<BUN_CANARY_VERSION>",
```

Mechanical application that preserves JSON formatting:

```bash
python3 - "$BUN_CANARY_VERSION" <<'PY'
import json
import pathlib
import sys

path = pathlib.Path("package.json")
version = sys.argv[1]
data = json.loads(path.read_text())
assert data["dependencies"]["bun"] == "1.3.14"
assert data["devDependencies"]["@types/bun"] == "1.3.14"
data["dependencies"]["bun"] = version
data["devDependencies"]["@types/bun"] = version
path.write_text(json.dumps(data, indent=2, ensure_ascii=False) + "\n")
PY
```

The implementation agent may use `apply_patch` instead; the resulting diff must be identical.

## Step 4 — Regenerate and verify `bun.lock`

File: `/Users/jun/Developer/opencodex/bun.lock`  
Operation: MODIFY, generated by Bun; never hand-edit

```bash
bun install
git diff -- package.json bun.lock

bun install --frozen-lockfile
bun pm ls | rg '(^| )bun@|@types/bun@'
```

Required lockfile review:

- only dependency graph changes caused by the two explicit pins are accepted;
- no registry URL, unrelated dependency, lifecycle-script authorization, or workspace lockfile changes are bundled;
- root `bun.lock` changes, not `gui/bun.lock` or `docs-site/bun.lock`;
- a second `bun install --frozen-lockfile` makes no diff.

```bash
git diff --exit-code -- gui/bun.lock docs-site/bun.lock
git diff --check
```


Run the full gates before committing the runtime pin:

```bash
bun run test

```

Record command, exit code, canary version, canary revision, source SHA, and elapsed time. Do not call a timeout, crash, or hang a type incompatibility.

## Canary-specific compatibility watch list

For every difference, rerun the same command under Bun 1.3.14 before attributing it to canary.

- JavaScriptCore GC cadence and heap sizing, especially differences with `--smol`.
- `process.memoryUsage()` values (`rss`, `heapUsed`, `heapTotal`, `external`, `arrayBuffers`) and `bun:jsc` heap statistics.
- `Bun.Image` decode/resize/JPEG buffers and native/external memory release in `src/adapters/anthropic-image-normalize.ts`.
- `Bun.serve` HTTP, SSE, WebSocket upgrade, cancellation, and stream backpressure behavior.
- Timer `.unref()`, AbortSignal listener cleanup, fetch cancellation, and closed-socket release.
- `Buffer`, `Blob`, `ArrayBuffer`, `Uint8Array`, and `Response` body lifetime after streaming.
- `bun:test` fake timers, process isolation, open handles, snapshots, and test ordering.
- Type declaration changes for `Bun.Image`, `Bun.serve`, WebSocket handlers, `Bun.generateHeapSnapshot`, and `bun:jsc`.
- Lockfile format or installer changes that prevent older Bun from reading the regenerated lock.
- Crash-report behavior: canary automatically uploads crash reports according to Bun's documentation. Do not run a privacy-sensitive reproduction until that consequence is accepted.

## Commit and rollback boundary

Commit only `package.json` and root `bun.lock`:

```bash
git diff --name-only
git diff --check
git add package.json bun.lock
git diff --cached --name-only
git commit -m "build(bun): pin dogfood canary runtime"
```

Do not push.

The pin rollback is an ordinary revert of this isolated commit, followed by `bun install --frozen-lockfile`. The installed binary/service rollback is specified in `040_verification_deploy.md`.
