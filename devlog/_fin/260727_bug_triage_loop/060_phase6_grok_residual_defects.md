# 060 — WP5: #511 잔여 결함 판정

근거: `004_grok_orphan_adjacency_defect.md`, WP2 A단계 감사
대상: WP2에서 범위 밖으로 미룬 3건 + EOF 경계 1건

모두 **재현으로 확인**했다. 판정과 수정 방향까지가 이 phase의 범위이며, 구현은 각각
독립 결정이 필요해 착수하지 않는다.

## 1. 문서가 안내하는 수동 레시피가 삭제된다 (High)

`docs-site/src/content/docs/guides/grok-build.md:78-88`이 사용자에게 이렇게 안내한다:

> If you manage `~/.grok/config.toml` yourself — or opencodex is on a non-loopback bind —
> add per-model tables with **direct fields**, outside the `# >>> opencodex managed block` markers:
>
> ```toml
> [model.ocx-opus]
> model = "anthropic/claude-opus-4-8"
> base_url = "http://127.0.0.1:10100/v1"
> api_backend = "chat_completions"
> api_key = "opencodex-loopback"
> ```

이 형태가 정확히 sweep의 소유권 조건이다: 평범한 `[model.x]` 헤더 + `api_key`가
`opencodex-loopback` + loopback `base_url`. 문서를 그대로 따른 사용자의 설정이 다음
sync에 삭제된다.

재현:

```
문서 레시피 테이블 생존: false
남은 model 테이블: [model.ocx-gpt-5-6-sol]
```

소유권 판정식 자체는 의도대로 동작한다. 문제는 **우리가 사용자에게 우리 소유 표식을
직접 쓰라고 시켰다는 것**이다. 외부 모델에 대한 오탐이 아니라, 우리가 시켜서 만든
테이블에 대한 정탐이다.

### 범위 한정: 같은 문서의 두 번째 예시는 살아남는다

`grok-build.md`는 예시를 두 개 준다. 두 번째는 네트워크로 도달 가능한 주소를 쓴다:

```toml
base_url = "http://192.168.1.10:10100/v1"   # the reachable host, not 127.0.0.1
```

이건 삭제되지 않는다:

```
네트워크 base_url 예시 생존: true
```

`isLoopbackBaseUrl`이 거짓이므로 소유권 조건이 성립하지 않기 때문이다. 즉 피해 범위는
**loopback 예시를 따른 사용자**로 좁혀진다. 문서가 "opencodex가 non-loopback 바인드일 때"를
두 번째 예시의 조건으로 제시하므로, 로컬에서 수동 관리하는 사용자가 정확히 첫 번째
예시를 쓰게 된다 — 그리고 그들이 피해자다.

감사가 확인한 전체 조합:

| 구성 | 레시피 테이블 |
|------|---------------|
| 레시피 #1, loopback 바인드 | **삭제** |
| 레시피 #2 (`192.168.1.10` + 실제 토큰) | 생존 |
| 레시피 #1, non-loopback 바인드 | 생존 (`skippedReason: non-loopback`으로 sweep 이전 반환) |
| 레시피 #1, 포트 불일치 `10999` | **삭제** — 포트는 판정식에 없다 |
| 레시피 #1에서 `api_backend` 제거 | **삭제** |

문서는 레시피 #1을 두 독자에게 준다: "파일을 직접 관리한다" **또는** "opencodex가
non-loopback 바인드다". 두 번째 독자는 구조적으로 안전하다 — `injectGrokConfig`가
non-loopback 가드에서 `findOpencodexOrphans` 이전에 반환한다.

반대로 초안이 놓친 것: **포트가 달라도 안전하지 않다.** `isLoopbackBaseUrl`은 호스트만
검사하므로, `127.0.0.1:10999`의 다른 프록시 인스턴스를 가리키는 사용자도 쓸려나간다.

또한 fence를 담은 릴리스는 `v2.7.41` 하나뿐이므로 노출 기간도 짧다. 그럼에도 High를
유지하는 이유는 도달 범위가 아니라 **사용자 데이터를 조용히 지운다는 신뢰 비용** 때문이다.

### 수정 방향

두 갈래이며 어느 쪽이든 한쪽만 골라야 한다.

- **문서를 고친다.** 수동 레시피가 `api_key = "opencodex-loopback"`을 쓰지 않도록 바꾼다.
  가장 단순하지만, 이미 그 문서를 따른 사용자의 설정은 여전히 지워진다.
- **판정식에 변별자를 넣는다.** 관리 블록이 생성하는 엔트리에만 있는 표식(예:
  `extra_headers`의 `x-opencodex-grok`)을 추가 조건으로 요구한다. 기존 사용자를 보호하지만
  판정식이 복잡해지고, 낡은 자동 생성 엔트리가 그 표식을 안 가질 수 있다.

### 변별자 방안은 #511을 되돌린다

"낡은 엔트리가 표식을 안 가질 수 있다"는 우려는 가정이 아니라 **확정 사실**이다.
이슈 #511이 인용한 실제 orphan을 보면:

```toml
[model.ocx-gpt-5-6-sol]              # line 23, OUTSIDE the managed block
model = "gpt-5.6-sol"
name = "OCX gpt-5.6-sol"
# no context_window  -> Grok falls back to 200k
```

`extra_headers`가 없다. `x-opencodex-grok`은 `src/grok/inject.ts:322`에서 관리 블록을
**생성할 때** 쓰는 라인이고, orphan은 정의상 그 라인이 존재하기 이전 버전이 쓴 것이다.

따라서 변별자를 필수 조건으로 걸면 #511이 보고한 바로 그 orphan을 더 이상 채택하지
못한다. **수정이 원래 버그를 되살린다.** 이 방안은 폐기한다.

### 남은 선택지

실질적으로 **문서를 고치는 쪽**만 남는다. 수동 레시피가 `api_key = "opencodex-loopback"`
대신 다른 값을 쓰도록 안내하고, 그 값이 소유권 조건을 만족하지 않게 한다. 이미 문서를
따른 사용자는 여전히 잃지만, WP2에서 백업을 넓혔으므로 `config.toml.bak-opencodex`에서
복구할 수 있다.

대안으로 관리 블록 밖의 opencodex 소유 엔트리를 **삭제 대신 이동**(fence 안으로 흡수)
하는 방법이 있다. 채택의 본래 의도에 더 부합하나 구현 범위가 커진다.

## 2. `ocx stop` 후 `default`가 사라진 테이블을 가리킨다 (Medium)

inject가 orphan을 채택해 삭제한 뒤 `stripGrokConfig`가 관리 블록을 걷어내면, `default`가
가리키던 별칭이 파일에서 사라진다.

재현:

```
[strip 후] default=ocx-gpt-5-6-sol / 존재 테이블=(없음) / dangling=true
```

inject는 살아남은 별칭으로 `default`를 재지정하지만, strip은 그 반대 작업을 하지 않는다.
`ocx stop` 이후 Grok은 존재하지 않는 모델을 기본값으로 들고 있게 된다.

**선재 결함이며 WP2 클램프가 악화시키지 않았다.** WP2 이전에도 SEPARATED 레이아웃에서
동일하게 발생했다. 다만 클램프로 ADJACENT 레이아웃이 정상 수렴하게 되면서, 예전에는
fence 손상에 먼저 부딪히던 경로가 이제 여기까지 도달한다.

### 수정 방향

`stripGrokConfig`가 블록을 제거할 때 `default`(및 `fork_secondary_model`)가 제거 대상
별칭을 가리키면 함께 정리한다. 다만 "무엇으로 되돌릴지"가 자명하지 않다 — 원래 사용자
값은 이미 유실됐을 수 있다. 백업 파일에서 복원하는 방안이 있으나 strip의 계약을 넓힌다.

## 3. orphan이 뒤따르는 주석과 자유 텍스트를 삼킨다 (High — 감사에서 상향)

`bodyEnd`가 **다음 헤더 인덱스**까지이므로, orphan과 다음 테이블 사이의 모든 것이
orphan의 span에 들어간다.

초안은 "뒤따르는 것이 테이블이면 안전하다"고 적었다. **틀렸다.** 테이블 자체는 살아남지만
그 테이블에 붙은 주석은 삭제된다:

```
[cli] 생존: true
OPS-4412 주석 생존: false
```

즉 사용자가 `[cli]` 위에 `# do not change — OPS-4412`를 달아 두면, orphan이 그 위에
있을 때 한 번의 `ocx start`가 주석만 조용히 지운다. 테이블이 멀쩡하니 눈에 띄지도 않는다.
**사용자가 가장 아끼는 종류의 주석이 정확히 이 위치에 있다.**

손실 범위(감사 확인):

| 대상 | 결과 |
|------|------|
| EOF까지 뒤따르는 주석 | 삭제 |
| EOF의 자유 텍스트 / 맨 키=값 | 삭제 |
| **다음 테이블 앞의 주석** | **삭제** |
| 다음 테이블 자체 | 보존 |

**선재 결함이며 WP2 클램프와 무관하다.** 클램프는 fence 위쪽 경계만 다룬다. 현재
코드와 모든 수정 변형이 동일하게 삭제한다.

### 수정 방향

span의 끝을 "다음 헤더"가 아니라 **"orphan 본문의 마지막 키=값 줄 다음"**으로 잡아야
한다. 그러면 EOF 주석과 테이블 간 주석이 모두 보존된다. WP2의 fence 클램프는 위쪽
경계만 다뤘으므로 이건 별개의 수정이다.

**백업에 의존하는 대안은 성립하지 않는다** — 아래 참조.

## 백업 복구 경로는 존재하지 않는다 (감사 블로커 2)

초안은 결함 2·3의 완화책으로 "WP2에서 백업 조건을 넓혔으니 `config.toml.bak-opencodex`에서
복구할 수 있다"고 적었다. **거짓이다.**

`copyBackupOnce`(`src/grok/inject.ts:261-262`)가 백업 파일이 이미 있으면 즉시 반환한다:

```ts
function copyBackupOnce(configPath: string, backupPath: string): void {
  if (existsSync(backupPath)) return;
  ...
}
```

즉 백업은 **최초 1회 스냅샷**이지 sweep 직전 스냅샷이 아니다. 현실적 시퀀스로 확인:

```
1) 사용자가 평범한 설정만 가진 상태 -> 첫 inject -> 백업 생성: true
2) 그 뒤 사용자가 문서 레시피를 추가
3) 두 번째 inject -> 레시피 생존: false
   백업이 삭제된 레시피를 담고 있나: false
```

WP2에서 조건을 `configExisted && (!region || orphans.length > 0)`으로 넓힌 것은 **호출
횟수만 늘렸을 뿐 내용을 보장하지 않는다.** 첫 백업이 이미 존재하면 아무 일도 일어나지
않는다.

따라서 결함 2와 3의 완화책을 **철회한다.** 진짜 복구 경로를 원하면 백업을 sweep 직전
스냅샷으로 바꿔야 하며(예: 별도 파일명 또는 세대 관리), 그건 WP2가 한 일이 아니다.

이 사실은 WP2의 커밋 메시지가 주장한 "safety net"도 약화시킨다. 최초 fence 쓰기 시점의
백업은 여전히 유효하지만, sweep이 지우는 내용을 담는다는 보장은 없다.

## 4. 분리된 하위 테이블이 유령 모델을 만든다 (Medium — 감사에서 누락 지적)

`004` 항목 #5를 060 초안이 판정 없이 빠뜨렸다. HEAD에서 재현된다.

자식 스캔이 첫 불일치 헤더에서 `break`하므로, 부모와 하위 테이블 사이에 `[cli]` 같은
다른 테이블이 끼면 하위 테이블이 쓸리지 않는다. 부모만 삭제되고 이것이 남는다:

```toml
[model.ocx-old.extra_headers]
x-opencodex-grok = "1"
```

TOML에서 이건 `[model.ocx-old]`를 **암묵적으로 재생성한다** — `model`, `base_url`,
`api_key`가 전부 없는 채로. Grok은 목록에 뜨지만 아무 데도 라우팅되지 않는 모델을
갖게 된다.

`004`가 예측한 `-2` 중복보다 나쁘다. 게다가 수렴하므로(`run2 changed=false`) 반복
실패 신호조차 없이 조용히 모델 목록을 오염시킨다.

수정 방향: 자식 스캔이 `break`하지 말고 **같은 부모의 하위 테이블을 파일 전체에서**
찾아야 한다. 다만 부모-자식 인접을 가정한 현재 구조를 바꾸는 일이라 범위가 있다.

## 5. 주석 꼬리 / 작은따옴표 리터럴 (Low — 감사에서 확정)

`004`가 예측한 것은 "영구 `-2` 중복"이었으나 **틀렸다.** 감사가 두 변형을 실행한 결과
`orphan parent swept: false`, 별칭은 `ocx-gpt-5-6-sol`, `-2 pinned: false`다.

즉 과다 sweep이 아니라 **과소 sweep**이다. `api_key = "opencodex-loopback" # ours`나
작은따옴표 리터럴은 `tableBodyKeys`를 통과하지 못해 소유권 판정이 실패하고, 낡은
엔트리가 그대로 남는다 — #511의 원래 200k 증상이다.

판정식을 넓히면 해결되나 오탐 위험이 커진다. 그 교환은 결함 1의 수정 방향과 함께
결정해야 한다.

## 종합 판정 (감사 반영 후 재조정)

| # | 심각도 | 상태 | 이번 루프 조치 |
|---|--------|------|----------------|
| 3 | **High** | 재현됨 | 판정만 — span 종료 조건 수정 필요 |
| 1 | **High** | 재현됨 | 판정만 — 문서 수정이 유일한 실질 선택지 |
| 4 | Medium | 재현됨 | 판정만 — 자식 스캔 구조 변경 필요 |
| 2 | **Low** (하향) | 재현됨 | 판정만 — 대부분 자기 치유 |
| 5 | Low | 확정됨 | 기록만 — 과소 sweep, 예측과 반대 |

초안의 순서(1 > 2 ≈ 3)를 감사가 뒤집었고 그 근거가 타당하다.

**3번을 1번과 나란히 High로 올린다.** 조건 없이, 되돌릴 수 없이, 자기 치유 없이 사용자가
직접 쓴 내용을 지운다. 게다가 복구 경로로 내세운 백업이 실제로는 그 내용을 담지 않는다.
1번이 테이블 삭제라 High라면 3번도 같은 등급이다.

**2번을 Low로 내린다.** 잃는 것은 `[models] default`의 문자열 하나뿐이고, 모델이 카탈로그에
남아 있으면 다음 `ocx start`에 자기 치유된다. 사용자 내용은 한 바이트도 잃지 않는다.

**1번의 도달 범위는 초안보다 좁다.** non-loopback 바인드는 sweep 이전에 조기 반환하고,
문서의 두 번째(LAN) 예시도 살아남는다. 실제 피해자는 loopback 바인드에서 파일을 직접
관리하는 사용자다. 다만 포트가 달라도 삭제된다 — `isLoopbackBaseUrl`은 호스트만 본다.

### 트리거 정정 (감사 블로커 5)

2번의 제목을 "`ocx stop` 후"로 단 것은 틀렸다. `ocx stop` 없이 **inject만으로도** 발생한다
— orphan의 모델이 카탈로그에서 빠졌으면 한 번의 inject로 `default`가 존재하지 않는
테이블을 가리킨다. strip만 고치면 이 경로가 남는다.

### WP2 클램프의 영향 (감사 확인)

"2·3번을 WP2가 악화시키지 않았다"는 주장은 3번에는 참이나 2번에는 **한 가지 단서**가
붙는다. 감사가 `8390cdb3^`와 HEAD를 비교한 결과, fence 인접 레이아웃에서는 클램프 이전에
