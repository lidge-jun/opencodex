### `src/providers/model-discovery.ts` — shared behavior change (AUDIT FOCUS)

This is the one part of the PR that is **not** additive. `resolveProviderModelDiscovery`
currently returns a spec only when the provider's own NAME matches a registry
entry AND the transport matches. The PR rewrites it to:

```ts
const namedEntry = getProviderRegistryEntry(providerName);
const entry = namedEntry
  ? (providerMatchesRegistryTransport(providerName, provider) ? namedEntry : undefined)
  : registryEntryForProviderDestination(provider);
```

Effect: a canonical preset saved under a DIFFERENT name now recovers its
registry-owned discovery policy by destination. This is the same class of fix as
the merged Volcengine work (`registryEntryForProviderDestination` exists on dev
at `src/providers/registry.ts:1907`).

Audit must confirm three things about this branch, because it widens who gets a
discovery spec:

1. A provider whose name DOES match a registry entry but whose transport does
   not still gets `undefined` — no fallback to destination lookup. (Reading the
   ternary: `namedEntry` truthy + transport mismatch -> `undefined`. Correct.)
2. `registryEntryForProviderDestination` refuses OAuth rows, template/overridable
   destinations, and non-`key` auth modes, so a renamed row cannot inherit an
   OAuth provider's discovery URL.
3. No caller of `resolveProviderModelDiscovery` treats a present spec as
   authorization to send credentials somewhere new. Note the precise invariant:
   a spec normally resolves relative to the configured `baseUrl`, but an
   absolute `spec.url` overrides it (`model-discovery.ts:160`). The guarantee is
   therefore **same-origin**, not same-URL — see the A5 section below and
   B-phase test 5, which pins it.

### Absolute `spec.url`: origin guarantee, not exact-URL guarantee (Amendment A5)

An absolute `spec.url` overrides the configured base
(`src/providers/model-discovery.ts:160`). The earlier instruction to "confirm no
reachable entry carries an absolute `spec.url`" was disproved and is removed —
`deepinfra` does carry one and IS fallback-eligible.

Measured inventory: only `command-code` (`authKind: "oauth"`, therefore not
fallback-eligible) and `deepinfra` (eligible) have absolute discovery URLs, and
both are same-origin with their own `baseUrl`. `deepinfra` discovers at
`https://api.deepinfra.com/v1/models` while its base is
`https://api.deepinfra.com/v1/openai` — different path, same origin.

Independently confirmed: `registryEntryForProviderDestination`
(`src/providers/registry.ts:1907`) requires an equal normalized URL plus exact
adapter and key-mode match, and `normalizedProviderEndpoint`
(`src/providers/registry.ts:1860`) equates only benign variants — whitespace,
host case, default `:443`, trailing slashes, dot-path normalization. A
non-default port, query, fragment, adapter mismatch, or OAuth mode does not
match. No configuration yields cross-origin key delivery through this fallback.

State the invariant as an **origin** guarantee. Test 5 above pins it so a future
entry cannot introduce a cross-origin discovery URL without failing.
