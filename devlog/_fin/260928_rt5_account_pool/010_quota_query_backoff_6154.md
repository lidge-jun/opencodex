## Review blockers and disposition

1. **Duplicate authenticated reads.** PR `quota-query-backoff.ts:21-25` records `after: 0` before `fetch`, so a second same-key caller passes while the first is in flight. PR `codex-quota-query-backoff.test.ts:88-129` even asserts two concurrent same-key dispatches. Keep an in-flight state until the response has been handled, admit only one dispatch per key, and return a deferred result to other callers without dispatch evidence. Main's shared-read claim is not a single-flight guarantee, and pool's existing flight map does not cover every caller/forced replay (`pool-quota-probe.ts:455-471`). Replace those race cases with no-duplicate, same/different credential, and completion-order tests. If the 256-entry cache fills, never evict an active entry merely to admit another request.
2. **Long `Retry-After` still enters recovery work.** PR `pool-mode-gate.ts:110-120` stores only its 5-minute first recovery delay when the WHAM response is 429, while `quota-query-backoff.ts:30` may defer dispatch for 15 minutes or up to 24 hours. Subsequent minute ticks take the profile lease and enter token preparation, then skip WHAM. Expose the shared next-eligible deadline without credential material; after the actual response, set the recovery attempt deadline to the later of its capped blocked-recovery delay and the shared query deadline. Before lease acquisition, honor that deadline only after reconciling the currently owned physical credential/generation; a replacement must get an immediate chance. Keep the in-lease generation recheck and late-result fence. Add a 15-minute and bounded-24-hour `Retry-After` sweep test that observes no repeated profile/token preparation before due time.
3. **HTTP 200 with an invalid body clears failure pacing too early.** PR `quota-query-backoff.ts:36-38` clears on HTTP success before main parses at `main-account-probe.ts:249-256` or pool commits at `pool-quota-probe.ts:397-401`. The maintainer's public PR comment leaves the behavior for a decision. Recommend treating an unusable 200 body as a failed usage read, since it produced no quota proof. Give the shared dispatch helper a completion/settlement result: keep the key in flight through body validation, clear only after a usable parse/commit, and record the normal failure delay on invalid body. Ensure every exit settles, including exceptions and 401 replay; stale completions must not overwrite newer-generation state. Test malformed main and pool responses followed by a forced refresh inside and after the delay. If the maintainer elects to retain status-only pacing, document that narrower contract explicitly and remove claims that every failed usage read is paced.
4. **Review and readiness.** `gh api .../pulls/6154/reviews` and `/comments` returned empty arrays; the public owner issue comment asks for focused interleaving tests and exact-head CI. The PR is draft with 0/4 readiness boxes, has no completed required test CI for `b3e68de`, and its own description reports focused tests but no full suite or independent security review. Preserve draft until fixes, relevant validation, security review per `MAINTAINERS.md`, current-head CI, and the required checklist are complete. Ignore CodeRabbit automation as a review decision.
5. **Structure noise.** Only `structure/providers/openai-tiers.md:300-315` owns the hard-lock/WHAM contract. The PR adds the same link across 11 other structure docs; additions in `dashboard-and-usage.md`, `providers/openai-accounts.md`, and `transports/responses-failover.md` break their opening sentences. Drop the blanket edits; retain a precise owner paragraph in `openai-tiers.md` and, if useful, a short contextual cross-link near the existing pool-observation paragraph in `openai-accounts.md:408-415`.
